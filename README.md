## 추가 화면 조정

- 홈·산업 화면에서는 사이드바를 숨깁니다. 기업 진입은 산업의 비교표/주가 카드에서 하며, 기업 상세에서만 같은 섹터의 기업을 오가는 사이드바를 표시합니다.
- 지표 설명은 상단 요약 리포트의 별도 단락으로 합쳤습니다.
- 핵심 지표 제목 옆 연도 선택은 기업 막대·가중평균·비교표를 함께 갱신합니다. 비율의 전년 변화는 %p로 표시하며, 전년 값 누락 또는 연결/별도 전환이면 계산하지 않습니다. 왼쪽 작은 연도별 그래프는 제거했습니다.
- 막대는 낮은 값부터 정렬하고 간격을 줄였습니다. 투자 비중의 크기는 좋고 나쁨을 뜻하지 않으므로 별도로 안내합니다.
- ‘최근 DART 공시 동향’에 본문 기반 사업 변화와 기업 간 차이를 통합했습니다. 별도의 중복 사업 변화/비교 서술 영역은 제거했습니다. 기존 2021-2025년 본문 분석을 재사용하며 2026년 목록을 본문 분석으로 오인하지 않도록 분석 범위를 표시합니다.
- 화면 변경은 Gemini를 호출하지 않습니다. 브라우저 새로고침으로 적용됩니다. UI 테스트: `node tests/test_ui.cjs`.

## 분석 방식과 한계

금액은 원 단위로 계산하고 화면에서 억 원으로 표시합니다. 연결재무제표를 우선하고 없으면 별도재무제표를 사용합니다. 계정 ID와 명시적 한글 계정명으로 매핑하며 충돌·누락은 빈 값으로 둡니다. 재무제표 기준이 전년과 다르면 증가율을 계산하지 않습니다.

- 매출 성장률: `(당기 매출 - 전기 매출) / 전기 매출 × 100`.
- 영업이익률: `영업이익 / 매출 × 100`.
- CAPEX: 현금흐름표의 유형자산 취득액. 무형자산·비현금 취득은 제외한 간소화 지표입니다.
- 단순 FCF: `영업활동현금흐름 - 유형자산 취득액`.
- 산업 수치: 유효 기업별 값의 중앙값. 화면에 유효 표본 수를 표시합니다.
- 상대 위치: `(더 작은 값 기업 수 + 동일 값 기업 수 × 0.5) / 유효 기업 수 × 100`. 큰 값이 우수하다는 의미는 아닙니다.

분석 순서:

1. 사업·반기·분기보고서 모두의 사업 내용에서 수요·AI 제품·생산 투자·위험 관련 문단을 주제별로 선별합니다. 보고서당 최대 20개, 문단당 최대 1,050자로 입력 크기를 제한합니다. 직전 보고서와 문구가 달라진 주제 문단에 최대 4개 자리를 배정하고, 보고 기간·종류·접수번호를 함께 전달합니다. 문구 차이는 새 사건으로 확정하지 않습니다.
2. Python 계산 재무수치, 5년 표본 중앙값, 기업별 상대 위치를 함께 전달합니다.
3. 기업별 요약과 `확인 내용 → 신호 → 해석 → 재무·현금흐름 영향 → 조건과 불확실성` 카드를 생성합니다.
4. 같은 모델의 별도 검토 호출로 공시의 계획/실행/실적 구분, 회사 주장 귀속, 수치와 조건부 해석을 다시 점검합니다.
5. 5개 기업의 분석과 선별된 공시 문단을 함께 사용하여 산업의 공통 흐름과 기업별 차이를 생성·검토합니다.
6. 응답 형식, 근거 ID 존재 여부, 연도별 근거 일치 여부를 검사한 후 `data/reports.json`을 교체합니다. 모든 결과가 준비되기 전에는 기존 보고서를 유지합니다.

화면에는 핵심 사업 요약, 기회·위험, 분석 카드, 기업 간 비교, 2021-2025년 변화와 공시 서술 단계, 앞으로 확인할 조건이 표시됩니다. 기업 차트에서 영업이익률·매출 성장률의 **상대 위치 변화**도 선택할 수 있습니다. 원문 보기·출처 연결·기준 시점·아웃라이어·밸류체인 기능은 추가하지 않았습니다.

`data/opendart/llm_cache`에 입력·모델·프롬프트별 결과를 저장하므로 같은 자료로 다시 실행하면 API를 재호출하지 않습니다. 중간 실패 시 완료한 기업의 결과를 재사용합니다. 초안 생성과 검토의 토큰 사용량은 캐시에 남습니다. 최종 `llm_meta`는 결과별 검토 호출 사용량을 기록합니다.

```powershell
# 저장된 AI 결과를 무시하고 새로 생성·검토 (API 사용량 발생)
python -B -X utf8 -m snapdart.analyze --refresh-llm

# API 호출 없이 규칙 기반 보고서로 교체
python -B -X utf8 -m snapdart.analyze --offline
```

LLM은 선별한 문단만 읽으며, 임베딩 기반 검색이나 전체 공시의 완전한 검토는 아닙니다. 서술 단계와 인과관계는 AI 해석입니다. 같은 모델의 재검토와 형식 검증이 사실 정확성을 보장하지는 않습니다. 중간 보고서의 중요한 변화는 기존 변화 카드와 연도별 요약에 반영하도록 지시합니다. 선별 방식이므로 모든 중요 변화의 포착을 보장하지 않습니다. 뉴스·자동 알림·투자 메모는 이번 REPORT 구현 범위에 포함하지 않습니다. 키는 Python에서만 읽고 브라우저에 보내지 않습니다.

## 향후 SQL 연동

1. 회사(companies), 공시(filings), 문단(passages), 재무(financial_facts), 분석(analysis_runs)을 분리합니다. 회사 고유번호와 접수번호는 문자열로 보존하고 외래 키로 연결합니다.
2. 공시는 회사·보고 대상 기간·보고서 종류와 접수번호를 구분합니다. 정정본도 보존하며 현재 사용할 버전을 별도로 지정합니다. 원본 ZIP은 파일로 두고 DB에는 경로·해시·수집 상태를 저장할 수 있습니다.
3. 문단에는 공시 ID·섹션·순서·텍스트·전처리 버전을, 재무에는 회계연도·보고서 코드·연결/별도·계정·통화·단위·누적/당분기 구분을 저장합니다. 금액은 DECIMAL, 누락은 NULL로 관리합니다.
4. collect/analyze/retrieval의 직접 파일 읽기를 저장소 계층으로 분리하고 SQLAlchemy 또는 DB 드라이버로 구현합니다. 기존 JSON과 ZIP을 초기 이관한 뒤 건수·금액·문단을 대조합니다.
5. 접수번호의 유일성, 회사·기간·보고서 종류 검색 인덱스, 트랜잭션, 재시도, 증분 수집을 적용합니다. 정정 시 관련 재무·문단·분석 캐시를 함께 갱신합니다.
6. 분석 결과에는 입력 공시 버전·모델·프롬프트 버전·입력 해시를 남겨 재현하고, 비밀번호는 환경변수로 관리합니다. 브라우저는 DB에 직접 연결하지 않고 현재 Python API를 통해 읽습니다.

SQL 자체의 연동은 아직 구현하지 않았습니다. [MySQL 외래 키 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)를 참고할 수 있습니다.

## 입력 토큰 제한 대응

생성·검토 호출 전에 공식 countTokens API로 시스템 지시와 입력을 계산합니다. 기본 GEMINI_TPM_BUDGET은 225000이며, 계산량에 5%와 1024토큰 여유를 더해 61초 이동 구간으로 관리합니다. 시작 시 61초 대기하여 즉시 재실행으로 인한 중첩을 줄입니다. 실패한 생성 요청도 보수적으로 사용량에 포함합니다. 단일 요청이 예산을 초과하면 생성 전에 중단하므로 입력 분할 또는 실제 계정 한도 확인이 필요합니다. 이 제어는 한 프로세스 안에서 동작하며 다른 프로그램의 동일 프로젝트 API 사용량은 알 수 없습니다. 동시에 여러 분석을 실행하지 마세요.

같은 기업의 완전히 동일한 선별 문단은 한 번만 전송하고 나머지는 text_ref로 참조합니다. 각 공시의 기간과 근거 ID는 유지하며 숫자나 표현이 달라진 문단 및 다른 기업 문단은 합치지 않습니다. 기존 완료 캐시는 보존·재사용합니다. 명령은 기존과 같습니다: `python -X utf8 -m snapdart.analyze`.

## 기업·연도·분기별 분할 분석

현재 LLM 경로는 선별된 문단 → 기업/연도/분기별 묶음 → 연간 요약 → 기업 보고서 → 산업 보고서입니다. 기존 주제별 선별 원칙을 유지하며 공시 전체를 추가로 보내지 않습니다. 선별 문단을 최대 1000자로 추가 분할하고 메타데이터 포함 약 16000자 단위로 묶습니다. 글자 수는 1차 기준이며 각 호출은 countTokens로 실제 토큰을 다시 확인합니다. 중간 묶음이 예산을 넘으면 둘로 나눠 재시도합니다. 기업·산업 단계에는 연간 요약과 Python 재무자료를 전달하고 원문 전체를 다시 합치지 않습니다.

중간 요약은 항목당 650자, 최대 6개로 제한합니다. 분기 변화·계획/실행 구분·불확실성·입력 근거 ID를 유지하도록 지시합니다. 요약은 원문이 아니며 요약 과정에서 세부 내용이 생략될 수 있습니다. 최종 생성·검토와 연간 재무 계산 및 화면 구성은 유지합니다. 중간 결과는 data/opendart/llm_cache/chunks에 입력과 근거 연결을 함께 저장합니다. 실패하면 동일 명령으로 재개하며 완료 묶음을 재사용합니다. 새 구조의 첫 실행은 이전 최종 캐시와 별도로 생성합니다.

기본 안전 예산은 225000 TPM, 생성 요청은 61초 구간당 최대 12회입니다. 429 발생 시 61초 대기 후 제한된 횟수로 재시도합니다. countTokens의 일시 오류도 재시도합니다. 일일 한도 초과는 대기로 바로 해결되지 않으므로 초기화 후 재실행해야 합니다. 분할로 호출 수와 첫 실행 시간이 늘어납니다. 다른 프로그램/동시 프로세스의 사용량까지 통제하지는 않습니다.

## 근거 ID 검증과 복구

각 요청의 응답 스키마는 현재 입력의 근거 ID만 enum으로 허용합니다. source_ids와 parent_id는 로컬 추적 자료로 보존하되 모델 입력에서는 제거합니다. 기존 연도·개수·ID 검증은 유지합니다. 검증 실패 시 data/opendart/llm_errors에 응답과 오류 및 허용 ID를 기록하고 한 차례 교정 요청을 보냅니다. 교정 호출에도 토큰 계산과 대기 제한을 적용합니다. 다시 실패하면 최종 보고서를 교체하지 않고 중단합니다. 완료된 기존 중간 캐시는 그대로 재사용합니다.

## Intel 내장 GPU 실행 설정

- GPU 기본: OLLAMA_IGPU_ENABLE=1, OLLAMA_VULKAN=1
- Flash Attention 해제, KV 캐시 f16, 문맥 131072, 배치 32, 최대 출력 8192
- `.env`의 OLLAMA_NUM_BATCH와 OLLAMA_NUM_PREDICT로 요청 설정을 조정합니다. 배치는 한 번에 계산하는 입력 토큰 수이며 문맥 길이와 별개입니다.
- 기존 서버에 설정을 적용하려면 분석이 끝난 뒤 `powershell -ExecutionPolicy Bypass -File scripts/start_ollama.ps1 -Restart`를 실행합니다. 이 스크립트는 11434 포트를 사용하는 이 프로젝트의 Ollama만 재시작합니다.
- CPU로 복귀: `powershell -ExecutionPolicy Bypass -File scripts/start_ollama.ps1 -Cpu -Restart`
- 모델 재다운로드나 드라이버 변경은 하지 않았습니다. 기존 분할, 근거 검증, 자동 교정, 캐시 처리는 유지됩니다.
