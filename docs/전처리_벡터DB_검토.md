# 공시 전처리와 벡터 검색 적용 검토

후속 구현 안내: 이 문서는 최초 구조 조사와 전략 검토 기록이다. 이후 안전한 XML 추출, 수치 CSV, 문단별 1,000글자·무중첩 청킹을 `dart_pipeline.preprocess`에 구현했다. 현재 실행 방법과 저장 형식은 `README.md`를 기준으로 한다. 아래의 토큰 단위 청킹·SQL·임베딩 제안은 현재 구현과 구분해야 한다.

## 1. 이번에 수행한 작업

기존 BOOTCAMP_MINI_PROTO를 변경하지 않고 새 BOOTCAMP_MINI에 독립적인 수집·검토 모듈을 만들었다. 3개년은 이전 구상안과 일치하는 **2023-2025 사업연도**로 정했다. 2025년 사업보고서는 2026년 제출본이다. 단순히 접수일이 2023-2025인 문서만 선택하지 않는다.

삼성전자(005930), SK하이닉스(000660), 한미반도체(042700), 주성엔지니어링(036930), 원익IPS(240810) 각각 3년 × 4종(1분기·반기·3분기·사업보고서), 총 60건을 저장했다. 기존에 받은 ZIP은 복사해 재사용하되 OpenDART 공시목록을 새로 조회해 기간별 최신 정정본 선택과 누락 여부를 확인했다. 누락은 0건이다. ZIP 내부 CRC 검사와 접수번호와 같은 이름의 본문 XML 존재를 60건 모두 확인하고 SHA256을 기록했다. 기존 연간 전체 재무제표 JSON 15건도 보조 자료로 복사했다. 이는 분기 재무제표 API 자료 60건을 추가 수집한 것과는 다르다.

원본은 data/opendart, 검토용 문단·표 블록은 data/inspection/blocks.jsonl에 저장했다. inspection 파일은 검토용 일반 데이터이지 완성된 재무지표 DB가 아니다. 이번 단계에서 임베딩 모델 다운로드, 임베딩 생성, 벡터 DB 설치 또는 Gemini 호출은 하지 않았다.

## 2. 실제 원문에서 확인한 사항

60건 전체 본문을 HTMLParser로 읽어 표·문단·제목을 분리했다. XML 전체를 문자열로 펼친 후 글자 수만으로 자르는 방식은 쓰지 않았다. 일부 원본은 ElementTree의 엄격한 XML 파싱에서 invalid token 오류가 발생했다. 원본 ZIP은 수정하지 않고 관대한 마크업 파서로 내용을 조사했다. 별첨 감사보고서가 본문보다 커질 수 있으므로 가장 큰 XML이 아니라 접수번호.xml을 본문으로 선택한다.

전체 검토 분류는 자연어 후보 14,035개, 수치·자연어 혼합 후보 1,860개, 수치 후보 269개, 표 요소 62,825개, 제목 6,115개, 기타 12,134개다. 표 요소 수에는 머리말·단위·서식용 표도 포함하므로 재무표 개수로 해석하지 않는다.

초기 검색 범위로 적합한 **II. 사업의 내용**에서는 자연어 후보 3,169개, 혼합 후보 671개, 수치 후보 37개, 표 요소 2,567개를 확인했다. 문단 길이 중앙값 44자, 95백분위 395자, 최대 3,509자였다. 단순히 문단 하나를 벡터 하나로 만들면 제목·짧은 주석·단편 문장이 많이 생긴다.

같은 기업 안에서 정규화한 블록 텍스트가 동일하게 반복된 중복 출현은 60,816개였다. 표·제목·문단을 모두 포함한 값이다. 이를 문서 유사도나 사건 반복 횟수로 해석해서는 안 된다. 블록을 문서에서 삭제하지 않고 원문 출현 위치는 모두 보존하되, 동일한 임베딩 입력의 계산만 재사용하는 근거로 활용한다.

위 분류는 수치 단위·문장 표현에 따른 규칙 기반 후보 분류다. 전수 사람이 정답을 붙인 결과가 아니며, 수치가 문단에 있다는 사실과 검증된 지표를 추출했다는 사실은 다르다. 날짜·제품명·계약기간·근사값·범위값의 추가 검증이 필요하다.

### 실제 사례

- SK하이닉스 2023년 1분기, ‘주요 제품 및 서비스’ 문단은 DRAM ASP의 ‘약 10% 후반’ 하락과 NAND의 ‘약 10%’ 하락을 설명하면서, 고객 재고 조정과 보수적인 판매 실행을 함께 서술한다. 숫자가 있다는 이유로 벡터 검색에서 제외하면 가격 변화의 맥락을 잃는다. ‘10% 후반’을 정확한 10% 또는 임의의 18%로 저장해서도 안 된다. 원문 위치: 20230515001677.xml의 645행 부근.
- 주성엔지니어링 2023년 1분기 ‘사업의 개요’ 표에는 반도체·디스플레이·태양전지 장비와 제품명이 들어 있다. 표라고 해서 모두 수치 DB 전용으로 보내면 주력 사업 정보가 검색에서 사라진다. 원문 위치: 20230515002578.xml의 1465행 부근.
- 삼성전자 사업 개요는 법인 수와 사업부문·판매법인 설명이 섞여 있다. 회사 전체의 법인 수를 반도체 사업부문의 생산 지표로 잘못 해석하지 않도록 사업 범위를 별도로 저장해야 한다.

## 3. 분리 원칙: 두 갈래가 아니라 세 갈래

| 분류 | 일반 데이터 저장 | 벡터 검색 대상 |
|---|---|---|
| 정량 중심 | 검증된 수치·단위·기간·계정·연결/별도·사업범위·원문 위치 | 필요 시 표 제목·항목 설명만 연결 |
| 정성 중심 | 원문과 문서/문단 메타데이터 | 제목·인접 문맥을 포함한 문단 묶음 |
| 수치와 설명 혼합 | 수치 후보를 별도 추출하되 검증 전 상태 표시 | 숫자를 제거하지 않은 전체 설명 문단 |
| 설명 중심 표 | 원표와 행·열·병합 정보 | 표 제목 + 머리글 + 의미 단위 행 묶음 |

수치 포함 여부는 저장 위치를 결정하는 유일한 기준이 아니라 문단에 붙는 속성으로 다룬다. 혼합 자료는 동일 block_id를 통해 정형 데이터와 벡터가 연결된다. 벡터는 검색을 위한 표현이며 원문 저장을 대체하지 않는다. 모든 자료의 원문은 일반 저장소에 남긴다.

정형 수치에는 OpenDART 전체 재무제표 API를 우선한다. 사업부문 매출·생산능력·가동률·수주잔고처럼 표준 재무계정 밖의 지표는 원문 표에서 추가 추출한다. 셀 값만 저장하지 않고 표 제목, 단위, 행/열 머리글, 주석, 전사/부문 범위, 연결/별도, 기준 기간, 누적/분기 여부를 함께 저장한다. 숫자는 Decimal 기반으로 관리하며 '-'와 빈칸은 0으로 바꾸지 않는다. 반기 누적액을 독립 분기값처럼 다루지 않는다. 분기값을 차감 계산할 때는 연결 기준·기간·정정 여부의 일치부터 확인한다.

## 4. 권장 처리 순서

1. ZIP 원본 불변 보관 → SHA256·접수번호·보고대상기간·접수일·정정 상태 기록.
2. 본문 XML 선택 → 대분류/소제목 경로, 문단, 표, 표 주석 분리. 목차·반복 서식·페이지 구분 요소는 검색에서 제외하되 원본을 지우지 않음.
3. 각 블록에 숫자 포함·정성 설명 포함·표 여부·사업범위·검증 상태를 독립적으로 부여.
4. 정량 자료는 재무 API와 표 파서로 구조화 → 단위·기간·계정 검증 → SQL 저장. 혼합 문단에서 추출한 후보는 사람 또는 결정론적 규칙 검증 전에는 확정 지표에 포함하지 않음.
5. 정성·혼합 블록은 같은 기업·보고서·소제목 내에서 짧은 인접 문단을 합침. 서로 다른 기업, 분기, 연결/별도 범위를 하나의 청크로 섞지 않음.
6. 실제 임베딩 토크나이저 기준 **400-700토큰 목표, 1,000토큰 상한, 긴 문단 경계에만 50-100토큰 겹침**을 시작 실험값으로 사용. 고정된 정답이 아니므로 검색 평가 후 조정. 짧은 문단을 무조건 개별 청크로 만들지 않음. 표는 행 중간에서 자르지 않고 각 묶음에 머리글·단위를 반복 부착.
7. 벡터에는 회사·기간·소제목을 포함한 텍스트를 입력. 캐시 키는 모델 리비전 + 전처리 버전 + 전체 입력 텍스트 해시. 텍스트가 같더라도 기간을 포함한 임베딩 입력이 다르면 무조건 같은 벡터를 재사용하지 않음. 원문 출현 기록과 임베딩 내용을 분리 관리.
8. 질문의 기업·기간·사업범위를 먼저 확정 → 정형 SQL 조회와 정성 검색 병행 → 원문 근거와 계산 결과만 LLM에 전달. 수치 계산은 Python/SQL에서 수행.

과거와 현재의 사업 변화를 묻는 질문은 최신 문단만 top-k로 검색하지 않고 동일 주제의 전후 기간 자료를 각각 검색한다. 새 표현의 등장·삭제를 바로 신규 투자·철회·위험 해소로 단정하지 않는다. 보고대상기간과 접수일은 별개로 필터링한다.

## 5. DB와 임베딩 선택

새 파이프라인의 목표 구조는 **PostgreSQL + pgvector**를 우선 권장한다. 정량 지표와 원문·벡터를 같은 데이터베이스에 두면 공시 ID를 기준으로 조인하고 정정본·검증 상태를 한 트랜잭션으로 관리하기 쉽다. Windows에서는 Docker Desktop/WSL2 환경 준비가 선행된다. 지금 설치된 것으로 가정하지 않는다.

최소 테이블은 documents(문서/버전), blocks(원문/경로), tables/cells(표 구조), facts(검증된 지표), chunks(검색 문맥/모델 버전), chunk_blocks(원문 연결), embeddings(벡터)로 구성한다. 기업·기간·접수일·정정본 활성 여부에 B-tree 인덱스를 둔다. 초기 60문서 규모에서는 기업·기간 필터 후 정확 벡터 검색을 먼저 측정하고, 청크 규모가 커져 지연이 문제일 때 HNSW를 적용한다. pgvector의 근사 검색은 필터 뒤 반환 수가 부족할 수 있으므로 iterative scan과 실제 재현율을 검증한다.

별도 벡터 엔진을 선택해야 한다면 Qdrant가 대안이다. 필터용 payload 인덱스가 있으며 의미 벡터와 키워드 검색을 결합할 수 있다. 다만 SQL과 별도 운영 시 두 저장소의 삭제·정정·동기화를 관리해야 한다. 이 프로젝트는 정량/정성 결합이 중요하므로 처음부터 엔진을 두 개 늘릴 필요는 없다.

임베딩 후보는 한국어와 영문 제품명이 섞인 문서에 사용할 수 있는 **BAAI/bge-m3**다. 공식 모델 카드 기준 다국어·1024차원·최대 8192토큰 입력을 지원한다. 이 수치는 모델 능력이며 권장 청크 크기가 아니다. CPU 소량 배치부터 속도/메모리를 측정하고 모델·토크나이저 리비전을 고정한다. 기존 Qwen 생성모델과 임베딩모델의 역할은 다르며, Ollama에서 Intel GPU가 동작했다고 해당 임베딩 프레임워크에서도 자동 가속되는 것은 아니다.

벡터 검색만으로 HBM3E, TC Bonder, 특정 공장명과 수치를 정확히 찾기 어려울 수 있다. 의미 검색과 키워드 검색을 결합한 뒤 중복 근거를 제거한다. 한국어 키워드 검색은 기본 영문 토큰화에 의존하지 말고 한국어 형태소/문자열 검색을 함께 평가한다. 재순위화 모델은 기본 검색 평가 후 필요한 경우에만 추가한다.

## 6. 검증과 구현 순서

1차: ‘사업의 내용’에서 기업별 1개 연도·사업/반기/분기 자료를 대상으로 100-200개 블록에 사람이 정량/정성/혼합/제외 정답을 부여한다. 짧은 문장, 제품명의 숫자, 근사값, 설명 표를 반드시 포함한다.

2차: 공시에서 정답 근거를 표시한 30-50개 질문으로 기업·연도 오검색, 정량 정답률, Recall@5/10, 문장/표 잘림, 인용 위치 복원, 처리시간을 측정한다. 최신과 과거 비교 질문을 포함한다. 현재는 이러한 검색 품질 실험을 수행하지 않았다.

3차: 검증된 정량 경로와 청킹·임베딩 경로를 60건으로 확장한다. 필요 시 재무 주석/경영진단으로 범위를 넓히고 정정본 이력을 보존한다. 이번 수집은 기간별 최신 정정본을 선택했으므로 엄밀한 과거 시점 백테스트용 전체 공시 버전 이력은 별도 확보해야 한다.

4차: 검색 결과의 토큰을 합산해 Gemini 예산 내에 넣고 요청 간격·재시도·청크 캐시를 적용한다. 임베딩을 로컬로 수행하면 Gemini 생성 API에 문서 전체를 보내지 않아도 된다. 다만 권한 차단·일일 할당량 같은 서버 측 오류를 전처리로 완전히 예방할 수는 없다.
