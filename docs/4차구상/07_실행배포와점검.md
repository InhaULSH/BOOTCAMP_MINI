# 07. 실행·배포·캐시와 점검

[문서 목록](README.md) · 기준: 2026-10-08

## 이 문서에서는 무엇을 알아보는가

앞 문서에서는 DB 조회부터 화면 출력까지의 흐름을 알아보았다. 이번에는 이 흐름을 실제로 시작하는 방법과, 작업이 실패했을 때 어느 부분을 확인해야 하는지 설명한다. 아래 명령은 실행 방법을 보여주는 것이며, 문서 작성 중 실제 클라우드 배포나 유료 Gemini 분석을 수행했다는 뜻은 아니다.

가장 먼저 기억할 점은 **보고서를 만드는 프로그램과 웹페이지를 보여주는 프로그램이 별개**라는 것이다. 분석 명령은 DB를 읽고 결과를 만든 뒤 끝난다. 웹 서버는 실행 상태를 유지하면서 브라우저 요청에 응답한다. 보고서를 만들었다고 웹 서버까지 자동으로 켜지지는 않는다.

## 첫째, 각 연결이 무엇에 필요한지 확인한다

DB 접속은 원천 공시·재무·벡터·원본을 읽는 데 필요하다. BGE-M3는 내 PC 또는 서버에서 질문을 벡터로 바꾸는 검색 모델이다. Gemini API는 근거를 전달받아 설명을 작성하는 외부 서비스다. KRX API는 공식 지수·전체 시가총액을 읽는 데 사용한다.

따라서 Gemini 키가 있어도 DB 연결과 BGE-M3 준비가 안 되어 있으면 기본 의미 검색을 진행할 수 없다. 반대로 Gemini를 호출하지 않는 발췌 보고서에서도 DB와 기본 검색 모델이 필요할 수 있다. “오프라인”이라는 옵션 이름이 모든 연결이 불필요하다는 뜻은 아니다.

연결 주소와 인증키 같은 설정은 환경변수로 전달한다. 환경변수는 코드 내용에 값을 고정하지 않고 실행 환경에서 제공하는 설정값이다. 로컬의 `.env` 파일도 이러한 설정을 읽기 위한 수단이다. 이미 실행 환경에 지정한 값은 파일의 값보다 우선할 수 있다.

정확한 설정 이름과 기본값은 뒤의 표에 정리했다. 처음에는 이름을 모두 외우기보다 어떤 설정이 DB·검색·AI·시세 중 어느 연결에 쓰이는지 구별하면 된다.

## 둘째, 로컬에서 보고서를 생성한다

프로젝트 루트에서 준비된 Python 환경으로 분석 명령을 실행한다. 여기서 `-m`은 지정한 Python 모듈을 프로그램으로 실행한다는 뜻이다. `--sector` 뒤에는 분석할 산업을 넣고, `--llm`은 Gemini 설명을 생성하는 경로를 선택한다.

```powershell
python -X utf8 -m snapdart.analyze --llm --sector 반도체 --prompt-version new
```

이 명령은 반도체 자료 범위를 확인하고, 재무 조회·공시 검색·워드클라우드 계산·Gemini 생성·검증·저장을 이어서 실행한다. 산업이나 기업별 작업이 진행되어도 최종 보고서 저장이 끝나야 화면이 새 결과를 사용할 수 있다.

기업과 연도를 추가로 제한할 수 있다. 지정하지 않으면 현재 운영 가능한 기업과 DB에 있는 전체 연도를 사용한다. 같은 자료·프롬프트의 유효한 생성 캐시가 있으면 재사용할 수 있으므로 `--llm`이 항상 모든 문장을 새 API 호출로 작성한다는 뜻은 아니다.

`--refresh-llm`을 사용하면 해당 생성 결과 재사용을 생략한다. 이전 프롬프트로 비교하려면 `--prompt-version old`를 명시한다. 이 옵션은 문체·내용·근거 선정 지침을 바꾸는 것이며 DB나 벡터 모델까지 과거 상태로 바꾸지는 않는다.

Gemini 없이 실행하는 분석도 새 보고서를 저장할 수 있다. 따라서 비용이 들지 않는다는 이유로 이를 단순 접속 점검 명령처럼 사용하면 기존 AI 보고서가 발췌 보고서로 바뀔 수 있다. 분석 실행과 연결 점검은 다른 작업이다.

## 셋째, 웹 서버를 별도로 실행한다

보고서가 준비되면 웹 서버 프로그램을 실행한다. 로컬에서는 다음 명령이다.

```powershell
python -X utf8 app.py
```

서버가 실행된 상태에서 브라우저로 `http://127.0.0.1:8501`에 접속한다. `127.0.0.1`은 지금 사용 중인 PC 자신을 뜻하며, 8501은 서버 프로그램의 접속 포트다. 포트는 같은 컴퓨터에서 어느 서버 프로그램에 요청할지 구별하는 번호다.

웹 서버는 저장 결과를 읽어 화면에 제공한다. 서버가 켜졌다는 것과 모든 산업 보고서가 준비됐다는 것은 다르다. DB 연결이나 보고서 기준이 맞지 않으면 특정 산업 화면만 준비되지 않은 상태일 수 있다.

기본 실행은 시세 수집도 뒤에서 한 번 시작한다. 이를 생략하려면 `python -X utf8 app.py --no-market-refresh`를 사용한다. 이 옵션은 시세 갱신만 생략하며 DB 조회와 보고서 읽기는 계속 필요하다. 보고서 생성 옵션과 웹 실행 옵션을 서로 바꿔서 쓰지 않는다.

## 넷째, 저장 결과와 캐시가 무엇인지 이해한다

서비스는 반복 작업을 줄이기 위해 중간 결과를 보관한다. 이를 캐시라고 한다. 예를 들어 DB에서 읽은 벡터, 다운로드한 검색 모델, 같은 질문의 벡터, Gemini 생성 결과, 워드클라우드 계산 결과를 다시 사용할 수 있다.

캐시마다 담는 내용과 구분 기준이 다르다. 원천 자료 버전이 바뀌면 벡터 연결을 다시 확인해야 하고, 프롬프트가 바뀌면 같은 공시라도 생성 결과를 다시 구분해야 한다. 워드클라우드 규칙이 바뀌면 단어 계산도 이전 결과와 구분한다.

이번 워드클라우드 변경에서는 산업 확산 계산과 기업 문맥 다양성 엔진이 캐시 구분에 포함되어 있다. 현재 코드는 변경된 계산 결과를 연결하지만, 새로 표시된 모든 단어의 Gemini 설명까지 페이지 조회 중 자동 생성하지는 않는다. 단어가 보여도 설명은 아직 없을 수 있는 이유다.

최종 보고서는 현재 화면이 읽는 결과이며, 원천 DB와 다른 저장소에 보관한다. 캐시를 재사용하는 것, 보고서를 새로 생성하는 것, 브라우저 화면을 새로고침하는 것은 다른 동작이다. 화면 새로고침만으로 원천 데이터 적재나 AI 재생성까지 이루어지지는 않는다.

## 다섯째, 클라우드에서도 같은 두 프로그램을 실행한다

배포는 이 프로그램을 내 PC 대신 클라우드 컴퓨터에서 실행하도록 준비하는 일이다. 현재 배포 버전은 Linux에서 Docker로 실행한다. Docker 이미지는 코드와 필요한 라이브러리를 묶은 실행 환경이고, 컨테이너는 그 이미지를 실제로 실행한 상태다.

코드 파일을 서버에 복사했더라도 이미 실행 중인 컨테이너는 이전 이미지의 코드를 사용할 수 있다. 코드 변경을 반영하려면 새 이미지를 만들고 컨테이너를 교체해야 한다. 보고서 내용도 달라져야 하는 변경이라면 새 코드로 분석 명령을 실행하여 결과를 다시 저장한다.

보고서와 모델 캐시는 컨테이너 교체 후에도 남아야 한다. 그래서 현재 구성은 Docker 볼륨에 저장한다. 볼륨은 컨테이너의 임시 파일과 구별되는 보관 공간이다. 실행 프로그램을 바꾸는 것과 저장 자료를 지우는 것은 분리되어 있다.

배포에서도 보고서 생성은 일회성 명령이고 웹 서버는 계속 실행되는 프로그램이다. 뒤의 배포 명령에서 `cloudapp.cli build --llm`은 분석 결과를 만드는 명령이고, `docker compose up -d`는 웹 서비스를 계속 실행하는 명령이다. `build`라는 단어가 들어가더라도 Docker 이미지 빌드와 보고서 빌드는 목적이 다르다.

## 여섯째, 서버에서 DB로 가는 연결 경로를 구별한다

현재 Naver Cloud 배포 설정은 Linux 서버의 `127.0.0.1:13306`을 통해 DB에 접근한다. 여기에 DB가 직접 설치되었다는 뜻은 아니다. DB에 접근할 수 있는 내부 PC가 SSH 터널을 유지하고, 서버의 해당 포트로 들어온 요청을 내부 DB 경로로 전달하는 구성이다.

SSH 터널은 정해진 연결을 통해 다른 위치의 포트로 통신을 전달하는 방식이다. 여기서는 서버와 내부 PC 사이의 역방향 터널을 사용한다. Docker는 서버 호스트 네트워크를 사용하여 이 터널 포트에 접근한다.

```text
브라우저 → 클라우드 웹 서버 → 서버의 터널 포트
         → DB 접근 가능한 내부 PC → MySQL
```

따라서 브라우저가 열리는지, 웹 서버가 실행 중인지, 터널이 유지되는지, MySQL이 인증을 받아주는지는 서로 다른 확인 사항이다. 같은 “접속 실패”라도 어느 구간이 실패했는지 알아야 해결할 설정을 찾을 수 있다.

## 일곱째, 오류가 난 단계를 먼저 찾는다

분석이 시작되기 전에 연결 오류가 난다면 DB 주소·포트·터널·인증을 먼저 확인한다. 자료를 읽은 뒤 청크·벡터 버전 오류가 나면 공시 본문과 벡터가 같은 게시 상태인지 확인한다. Gemini가 응답한 뒤 근거 ID 오류가 나면 모델 결과가 입력 목록과 검증 규칙을 지켰는지 확인한다.

페이지가 열리는데 산업 화면만 준비되지 않았다면 현재 기준 보고서 유무와 해당 산업 자료를 확인한다. 설명은 보이지만 각주 원문이 안 열리면 원본 문서 연결과 인용 위치를 확인한다. 주가만 안 보이면 시세 수집 경로를 확인한다. 이러한 문제를 전부 Gemini 키 문제로 취급하지 않는다.

일시적인 사용량 제한은 기다림으로 해결될 수 있지만, 요청 하나가 예산보다 크거나 권한이 없는 경우에는 대기만으로 해결되지 않는다. 검사 기준을 낮춰 오류를 숨기기보다 그 오류가 어떤 단계의 조건을 지키려는 것인지 먼저 이해해야 한다.

뒤의 오류 표와 테스트 목록은 각 단계를 확인할 때 사용하는 참고 자료다. 테스트 통과와 실제 원격 DB·API·클라우드 가동 확인도 구별한다. 작성된 명령이 있다는 사실만으로 실제 배포가 완료된 것은 아니다.

## 이 문서에서 실행 방법을 읽는 순서

로컬은 설정과 연결을 준비하고, 보고서를 생성하고, 웹 서버를 실행하고, 브라우저로 확인한다. 배포는 서버 연결 환경과 이미지를 준비하고, 서버에서 보고서를 생성하고, 웹 서비스를 실행한다. 문제가 생기면 DB 조회·검색·AI 생성·저장·화면·출처·시세 중 어디에서 멈췄는지 찾는다.

이 순서를 이해한 뒤 아래의 정확한 옵션·명령·캐시 위치를 참고하면, 실행 명령을 외우기보다 각 명령의 역할을 판단하면서 사용할 수 있다.

## 구현 상세: 파일과 정확한 처리 기준

앞부분의 흐름을 이해한 뒤필요한 항목을 찾아 읽는 참고 영역이다. 처음 읽을 때 모든 함수명과 설정값을 외울 필요는 없다.

### 구현 의도: 원천 조회·생성·서비스 운영을 분리한다

원격 공시 DB는 읽기만 하고, 앱 결과는 별도 저장소에 보존한다. 관리자는 분석 명령으로 보고서를 만들며 웹 서버는 그 결과를 조회한다. API 비용이 드는 생성 작업과 일반 화면 요청을 분리하고, 코드 변경·원천 버전 변경·시세 실패를 다른 문제로 진단할 수 있게 한 구조다.

현재 서비스는 Windows 로컬 환경과 Linux Docker 배포 환경을 지원한다. 생성·검색·근거·화면 원칙은 공통이고 HTTP 실행과 사용량 공유·저장 환경이 다르다. 이 문서는 실행 절차를 설명하며 실제 클라우드 서버가 배포·가동됐다고 주장하지 않는다.

### 실행 전 필요한 조건과 설정

| 설정·조건 | 역할과 코드 기본값 |
| --- | --- |
| `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` | 원격 MySQL 연결. `SQL_HOST_NAME`, `SQL_PORT`, `SQL_DEFAULT_SCHEMA`, `SQL_USER_NAME`, `SQL_PSWD` 별칭 지원 |
| `DB_POOL_SIZE` | 기본 5, 추가 연결 0으로 연결 풀 사용 |
| 현재 `data_versions`와 연결된 자료 | 하나의 검증된 현재 버전, 청크·벡터·원본 연결 정합성 |
| `SEARCH_BACKEND` | Windows `numpy`, Linux `faiss`; `keyword`는 명시 선택 |
| `BGE_M3_DEVICE`, `BGE_M3_CACHE_DIR` | 질문 모델 장치 기본 CPU와 모델 파일 위치 |
| `HF_TOKEN` 또는 `HUGGINGFACE_TOKEN` | Hugging Face 모델 다운로드 환경에서 사용할 선택 인증 |
| `GEMINI_API_KEY` 또는 `GOOGLE_API_KEY` | 설명 생성과 모호한 원문 위치 평가 인증 |
| `GEMINI_MODEL` | 코드 기본 `gemini-3.5-flash-lite`; 실제 계정 권한은 별도 확인 |
| `GEMINI_TPM_BUDGET`, `GEMINI_RPM_BUDGET` | 자체 안전 한도 기본 225,000·10, 공급자 계정 한도가 아님 |
| `GEMINI_CONCURRENCY` | 기본 4, 1-4로 제한 |
| `CITATION_INPUT_CHAR_BUDGET` | 생성 공시 후보 기본 48,000자·코드 최소 4,000자, 실제 토큰 수 검사와 별개 |
| `LLM_PROMPT_VERSION` | `new`/`new2`/`old`; CLI의 `--prompt-version` 기본은 `new`이고 CLI 옵션이 환경변수보다 우선 |
| `CITATION_CONTEXT_CHAR_BUDGET` | 문장 앞뒤 보충 문맥 총량 기본 4,000자, 0-8,000자로 제한 |
| `KRX_API` | KRX 공식 지수·전체 시가총액. 키와 해당 API 이용 승인 필요 |
| `SERVICE_CACHE_DIR`, `DART_CACHE_DIR` | 앱 결과와 벡터 캐시 저장 위치 |
| `SERVICE_GCS_BUCKET` | 선택 공유 객체 저장소. 현재 Naver Compose는 비워 둠 |
| `NO_MARKET_REFRESH` | 배포 웹 시작 시 시세 수집 생략 여부, `1`이면 생략 |

`.env`는 로컬 설정을 제공하고 이미 지정된 환경변수를 덮어쓰지 않는다. 실제 키·비밀번호는 문서·이미지·화면 JSON에 기록하지 않는다. 배포 설정 양식은 [deploy/.env.example](../../deploy/.env.example)을 참고한다. 현재 루트에는 같은 이름의 양식이 있다고 가정하지 않는다.

BGE-M3는 Gemini와 별개로 로컬에서 실행된다. 첫 검색은 모델 다운로드·전체 벡터 스냅샷 읽기·표본 재임베딩 때문에 느릴 수 있다. 캐시가 없고 모델 서버에 접근할 수 없으면 단순히 Gemini 키만 준비해서 동작하는 서비스가 아니다.

### 로컬 생성과 웹 실행

프로젝트 루트에서 같은 Python 환경을 사용한다. 아래는 설치·실행 방법이며 문서 작성 과정에서 유료 분석을 실행했다는 뜻은 아니다.

```powershell
python -m pip install -r requirements.txt
python -X utf8 -m snapdart.analyze --llm --sector 반도체 --prompt-version new
python -X utf8 app.py
```

주소는 `http://127.0.0.1:8501`이다. 기본 서버는 loopback에만 바인딩한다. `app.py`만 실행해도 분석 보고서가 자동 생성되는 것은 아니다.

| 분석 옵션 | 동작 |
| --- | --- |
| `--sector` 생략 | 현재 자료가 구축된 산업 전체를 순차 처리 |
| `--companies` | 해당 산업 안의 기업명·종목코드·기업번호로 범위 제한 |
| `--years` 생략 | 현재 DB에 있는 전체 연도 |
| `--years 2023 2024 2025` | 그 연도들이 실제 현재 버전에 있을 때 지정 범위 분석 |
| `--llm` | 기존 유효 생성 캐시를 활용해 Gemini 설명 생성 |
| `--refresh-llm` | 생성 캐시 재사용 없이 새 Gemini 작업 |
| `--offline` | Gemini 생성 없이 발췌 보고서. DB와 기본 의미 검색 모델은 필요 |
| `--prompt-version old` | 이전 프롬프트·근거 평가로 생성 |

아무 LLM 옵션 없이 `analyze`를 실행해도 현재 DB로 발췌 보고서를 만들 수 있다. 그 결과는 산업의 기존 AI 보고서를 교체할 수 있으므로, 비용 없는 단순 연결 검사와 구별한다. 웹 실행의 `--no-market-refresh`는 시세 수집만 생략하고 보고서 조회·DB 조회를 생략하지 않는다.

질문 조회 도구는 다음과 같다. `--llm` 없이는 Gemini를 호출하지 않지만 의미 검색용 BGE-M3는 사용할 수 있다.

```powershell
python -X utf8 -m snapdart.query --sector 반도체 --company 삼성전자 --year 2025 --question "HBM 수요 변화"
```

### Naver Cloud Linux 배포 구조

현재 [compose.yaml](../../deploy/compose.yaml)은 Linux host 네트워크를 사용한다. DB 연결은 **서버 호스트의 `127.0.0.1:13306`**으로 고정하고, Cloud SQL·GCS 설정은 비운다. Docker가 호스트 네트워크를 사용하기 때문에 이 loopback 터널에 접근할 수 있다.

```text
사용자 브라우저
  → Linux 서버 공인 IP:8080의 FastAPI
  → 같은 서버 127.0.0.1:13306 터널
  → DB에 접근 가능한 내부 PC
  → 원격 MySQL:3306
```

이 터널은 내부 PC에서 연결을 유지하는 역방향 SSH 구성이다. 서버에 DB가 자동 설치되거나 모든 PC가 원격 DB에 바로 접근할 수 있다는 뜻은 아니다. 실제 접속 정보·터널 실행은 [deploy/README.md](../../deploy/README.md)의 환경에 맞춘다. 13306 포트를 공인 DB 포트처럼 노출할 필요는 없다.

Dockerfile은 Python 3.12 Linux 환경, CPU용 모델·FAISS·고정 의존성과 비특권 서비스 사용자를 준비한다. `service_home` 볼륨은 `/home/service`에 보고서·시세·벡터·모델 캐시를 보존한다. 컨테이너를 교체해도 이 볼륨을 유지하면 데이터를 재사용할 수 있다.

Linux 서버의 배포 디렉터리에서 사용하는 명령은 다음과 같다.

```bash
docker compose build app
docker compose run --rm app python -m cloudapp.cli check
docker compose run --rm app python -m cloudapp.cli build --llm --sector 반도체 --prompt-version new
docker compose up -d --build --force-recreate
docker compose logs --tail=100 app
```

`cli build --llm`은 보고서 생성, `up -d`는 상시 웹 실행이다. 공인 IP·8080 접속에는 클라우드·서버 방화벽 허용과 실행 서비스가 필요하다. 파일을 서버에 올리는 것만으로 기존 이미지의 코드가 바뀌지 않으므로 새 이미지를 먼저 만든다.

배포 기업 옵션은 `--codes`이며 로컬 `--companies`와 이름이 다르다. 연도는 동일하게 `--years`다. 배포 웹 직접 실행은 `python -m cloudapp.serve`, 시세 생략은 `--no-market-refresh` 또는 `NO_MARKET_REFRESH=1`이다. 서버는 기본 0.0.0.0:8080·워커 1개다.

GCP용 `CLOUD_SQL_INSTANCE`·GCS 코드도 존재하지만 현재 Naver Compose 구성을 Cloud Run의 필수 설정으로 설명하지 않는다. Cloud Run에서는 임시 컨테이너 파일 대신 지속 결과·공유 예약을 위한 GCS 환경을 준비해야 한다.

### 캐시별로 무엇을 저장하고 언제 달라지는가

| 저장 계층 | 보관 내용 | 구분 기준·현재 위치 |
| --- | --- | --- |
| 원격 MySQL | 원천 수치·청크·벡터·원본 | 자료 구축 측 버전 관리, 앱은 읽기만 |
| 벡터 NPZ | 전체 검색 벡터·메타데이터 | DB 대상·버전·모델·개수·해시; 기본 `.dart_cache` |
| BGE 모델 파일 | 고정 revision 모델 | `BGE_M3_CACHE_DIR` 또는 모델 라이브러리 캐시 |
| 질문 벡터 | 동일 질문의 임베딩 | 프로세스 메모리 최대 128개 |
| 토큰 수 | 같은 실제 요청의 입력 토큰 수 | 프로세스 메모리 최대 256개 |
| 워드클라우드 | 범위별 선정 단어·점수 | 자료 지문·연도·기업·규칙 해시 |
| Gemini 생성 결과 | 원문 근거 스냅샷·응답·평가 | 프롬프트·입력·모델 해시; 산업 폴더의 `llm/` |
| 최종 보고서·시세 | 화면이 읽는 현재 결과 | 산업별 `report/current`, `market/current` |

로컬 앱 결과의 기본 루트는 `data/service/remote`다. 산업별 종류·키를 URL 안전하게 인코딩한 JSON 경로로 저장한다. `SERVICE_CACHE_DIR`로 바꿀 수 있다. 원격 DB에는 보고서 캐시를 쓰지 않는다.

GCS가 지정되면 공통 artifacts의 보고서·시세·워드클라우드 저장과 읽기는 객체 저장소를 사용한다. 메타데이터 generation을 확인해 읽고, 예약 경쟁 시 같은 generation 조건으로 갱신한다. 모든 캐시가 GCS로 바뀌는 것은 아니다. BGE·NPZ·개별 `llm/` 생성 캐시는 해당 실행 환경의 파일 저장 경로를 사용한다.

파일 저장은 완성한 임시 파일을 교체하는 방식으로 부분 JSON을 읽는 일을 줄인다. 여러 분석 프로세스가 같은 산업을 동시에 만드는 것을 막는 산업별 작업 잠금은 없다. 같은 산업의 최종 보고서는 나중 저장 결과로 바뀔 수 있다. 배포 공유 한도와 최종 보고서 동시 작성 관리는 다른 문제다.

### 로컬·배포 사용량 제어의 차이

로컬 Gemini 예약은 프로세스 메모리의 잠금을 사용한다. 같은 프로세스의 최대 4개 생성 작업은 합쳐서 제어되지만 서로 다른 Python 실행·외부 앱까지 공유하지 않는다.

배포는 공통 `artifacts.reserve()`를 사용한다. GCS가 없으면 앱 저장소의 `quota.sqlite3`에서 즉시 쓰기 트랜잭션으로 예약한다. 같은 저장소를 사용하는 컨테이너끼리 예약을 공유할 수 있다. GCS가 있으면 generation 조건부 갱신으로 예약 경쟁을 처리한다. 예약 기간은 최근 약 61초이며 기본 안전량 공식은 로컬과 같다.

Cloud Run 환경에서 GCS 없이 프로세스별 로컬 예약을 공유한 것처럼 동작하지 않도록 오류를 내는 경로가 있다. 일일 사용량 제한이나 다른 앱이 같은 프로젝트 키를 쓰는 전체 사용량까지 대신 관리하지는 않는다.

### 오류를 어느 단계에서 구분해야 하는가

| 증상 | 의미와 먼저 확인할 부분 |
| --- | --- |
| 연결 거부 | 대상 주소·포트에 리스너가 없을 가능성. 서버 터널부터 확인 |
| timeout/reset | 라우팅·방화벽·터널·원격 접근 상태. 비밀번호 수정 전에 통신 확인 |
| Access denied | 통신 후 DB 인증/사용자 접근 정책에서 거절 |
| 현재 버전 없음·여러 개·미검증 | 자료 게시 상태가 서비스의 계약을 충족하지 않음 |
| 청크·벡터 개수/ID/버전 불일치 | 동기화되지 않은 자료를 의미 검색에 사용하지 않도록 중단 |
| 모델 표본 검증 실패 | 모델 revision·라이브러리·청크 입력 방식·정규화 확인 |
| Gemini 403 | 키·프로젝트·모델 권한/접근 제한; 반복 대기로 해결되는 오류가 아님 |
| Gemini 429 | RPM·TPM·기타 계정 한도와 별도 앱 사용 확인 |
| 단일 요청 안전 예산 초과 | 대기로 요청 크기가 줄지 않음. 선정 예산·실제 한도 검토 |
| 입력에 없는 근거 ID·부적격 평가 | 모델 JSON이 입력·선정 계약을 어김. 수정 요청 실패 시 생성 중단 |
| 보고서 없음·자료 지문 변경 | 현재 자료로 생성이 필요. 페이지 열기가 자동 생성하지 않음 |
| 원문 위치 실패 | 원본 연결·버전·해시·인용 위치 또는 중복 위치 평가 확인 |
| 주가·지수 미표시 | 외부 통신, KRX 인증/승인·정확한 지수명·이전 두 거래일 자료 확인 |

`/healthz`는 배포 프로세스 응답 확인, `/readyz`는 DB 간단 조회와 산업 목록 확인이다. ready 성공이 모든 산업 보고서·벡터·Gemini·KRX가 정상이라는 뜻은 아니다. 공개 API 오류는 민감한 연결 정보가 그대로 노출되지 않도록 정리한다.

### 테스트로 확인하는 조건과 운영에서 확인하는 조건

테스트는 입력·출력 계약과 실패 처리의 회귀를 잡는다. 원격 DB 상태와 실제 API 권한을 모두 검증하는 것은 아니다.

```powershell
python -X utf8 -m unittest discover -s tests
python -X utf8 -m unittest dart_remote.test_signal_sector_isolation
node tests/test_profit_chart.cjs
node tests/test_wordcloud_layout.cjs
```

배포 전용 검사는 `deploy/`에서 `python -m unittest discover -s tests`로 실행한다. 브라우저 상호작용 검사는 해당 테스트의 서버·브라우저 준비 조건을 따른다. 단순 문서 개정에 유료 보고서 재생성을 자동으로 붙이지 않는다.

| 검증 대상 | 주요 회귀 테스트 |
| --- | --- |
| 산업·범위·기간 | `test_sector_repository`, `test_analysis_years`, `test_sector_availability` |
| 벡터 계약·질문 모델 | `test_mysql_vectors` |
| 프롬프트·근거·사용량 오류 | `test_prompt_contract`, `test_citation_selection`, `test_current_llm`, `test_gemini_errors` |
| 병렬·캐시 | `test_generation_concurrency`, `test_consolidated_paths` |
| 신호와 산업/기업 분리 | `test_wordcloud_signal`, `test_wordcloud_adapter`, `dart_remote.test_signal_sector_isolation`, `dart_remote.test_industry_spread_hot`, `dart_remote.test_company_signal_wordcloud`, `dart_remote.test_company_context_diversity` |
| 수치·분기·XML | `test_dashboard`, `test_storyboard_data`, `test_graph_metrics`, `test_xml_financials` |
| 시장과 전체 시가총액 | `test_market_api`, `test_krx_capitalization`, `test_sector_market_cap` |
| 화면·배포 대응 | `test_deploy_parity`, 배포 `test_service`, 프런트 CJS 테스트 |

[scripts/check_service.py](../../scripts/check_service.py)는 실제 MySQL·저장 보고서·로컬 모델을 사용하는 별도 서비스 점검이다. 운영 연결을 실행하지 않았다면 테스트 결과만으로 성공을 단정하지 않는다.

로컬·배포 `dart_remote`, `web`, `config`와 기본 프롬프트의 대응은 [test_deploy_parity.py](../../tests/test_deploy_parity.py)가 검사한다. 다만 로컬/배포 시장 이력 초기 수집, HTTP 서버, 예약 저장소처럼 의도적인 차이는 이 비교 대상과 구분한다.

인사이트 생성·근거 처리·재무 이력·원자적 캐시 저장 함수의 로컬/배포 대응도 검사한다. XML 기반 오프라인 테스트로 배포의 캐시 경로 및 저장 함수 누락을 재현하여 로컬과 같은 방식으로 보완했다. 현재 코드의 테스트 방법과 실제로 확인한 범위는 [08](08_XML기반오프라인통합검증.md)을 참조한다. 폐기된 별도 `search_server` 모듈의 테스트는 제거했으며 현재 FAISS/NumPy 경로의 검증은 유지한다.

### 다른 개발자가 변경할 때 지켜야 할 설계 경계

새 산업을 붙일 때는 DB 현재 구성기업·운영 상태·coverage·공식 지수 정보를 먼저 준비하고, 그 산업의 계정·목차·어휘·검색 주제를 실제 문서로 확인한다. 데이터·벡터 모델 revision·인덱스 버전·원본 연결은 같은 게시 상태여야 한다. 서비스가 실패하면 원천 자료를 앱 안에서 고쳐 쓰기보다 적재 측 정합성을 확인한다.

설명 문체를 바꿀 때는 프롬프트와 정의서·버전·회귀 조건을 함께 맞춘다. F/U/C/T 가중치와 워드클라우드 50/30/20 점수는 서로 다른 목적이므로 동시에 바뀌는 상수로 취급하지 않는다.

화면 수치를 바꿀 때는 연간 생성 입력, 개별 분기 계산, 실제 화면 산식, 원문 구성요소의 기간을 각각 확인한다. 산업 중앙값·공식 지수·전체 시가총액·대표기업 가중치는 다른 자료다. 하나의 값으로 대체하면 서비스 의미가 바뀐다.

공통 기능을 수정하면 배포본과 화면 계약을 함께 맞춘다. 코드·문서·테스트가 구현 사실을 다르게 설명하지 않게 하되, 알려진 한계를 완료 기능처럼 써서 숨기지 않는 것이 이 설명서의 유지 기준이다.

### 섹터별 그래프 변경을 적용하고 확인하는 방법

웹 서버를 재시작하고 브라우저를 새로고침하면 현재 섹터별 지표 계산과 제목·도움말이 적용된다. 그래프 변경만을 위해 `snapdart.analyze --refresh-llm`을 실행할 필요는 없다. 기존 저장 보고서와 현재 DB 자료는 페이지 조회에 계속 필요하다.

로컬과 배포 모두 공통 `dart_remote/graph_metrics.py`와 대응하는 `ui_project.py`, 동일한 웹 자산을 사용한다. DB 정합성이 일시적으로 맞지 않아도 코드 계산은 가상 데이터로 검증할 수 있으며, DB의 버전·접수번호 확인 조건을 임의로 해제하지 않는다. 테스트 통과가 원격 데이터의 정상 상태까지 보증하는 것은 아니다.

`test_graph_metrics`는 전년 동분기 비교, 헬스케어 R&D, 음수 FCF, 은행 연환산·평균 잔액, CFS/OFS·비교 범위 분리, 승인·원화·출처 연결 조건, 누적 차감 및 결측을 가상 자료로 검사한다. 실제 DB 연결 없이 실행하려면 다음 명령을 사용한다.

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests -p test_graph_metrics.py
node tests/test_ui.cjs
node tests/test_profit_chart.cjs
```


## 웹 조회·파일 읽기 최적화

DB 스키마는 변경하지 않습니다. 산업 목록은 현재 버전·지수 목록·전체 구성기업을 일괄 조회하는 방식으로 읽습니다. 웹 요청의 산업 목록은 기본 30초 동안 프로세스 메모리에서 재사용하며, 요청 안의 반복 호출도 공유합니다. CLI 분석은 이 산업 목록 시간 캐시를 사용하지 않습니다. `CATALOG_CACHE_SECONDS=0`으로 웹 목록 캐시를 끌 수 있습니다. 구성기업·운영 상태·DB 버전 변경은 최대 이 유효기간 뒤 새 조회에 반영되며, 설정 파일 변경은 다음 요청부터 반영합니다.

로컬 파일은 수정 시각·생성/변경 시각·크기·파일 식별자가 같으면 JSON 변환 결과를 재사용합니다. 첫 화면은 기업 ID와 보고서 준비 여부·지수·시가총액만 보관한 별도 메모리 요약을 사용하여 전체 보고서를 반복 복사하지 않습니다. 요약은 원본 보고서·시세 파일 변경과 한국 날짜 변경에 따라 다시 읽습니다. 기존 파일 구조와 쓰기 방식은 유지합니다.

화면 응답은 기본 30초 캐시입니다(`UI_CACHE_SECONDS`, 0이면 비활성화). 선택 산업·카탈로그·파일 변경을 구분하고, 준비되지 않은 화면이나 예외는 보관하지 않습니다. DB 수치가 같은 버전 안에서 변경되면 응답 캐시 만료 뒤 반영합니다. GCS는 객체 generation을 조회하고 JSON 본문을 재사용하며 로컬 파일용 응답/첫 화면 요약 캐시는 사용하지 않습니다.

같은 웹 요청에서 동일 SQL·파라미터 조회는 제한된 크기의 결과만 재사용합니다. XML BLOB·벡터 등 바이너리 결과는 이 캐시에 넣지 않으며 SQL 결과는 다음 요청으로 넘어가지 않습니다. Gemini 사용량 예약은 JSON 캐시를 우회합니다. 원격 읽기 전용 트랜잭션, 버전·출처 검사, 지표 계산, 근거 선정 기능은 유지합니다.

캐시는 프로세스별로 존재하며 항목 수·메모리 사용량을 제한하고, 반환값은 복사하여 다른 요청의 수정을 막습니다. 같은 캐시 항목에 동시 요청이 몰리면 한 번만 읽습니다. 서버 재시작 후 첫 요청은 실제 읽기를 수행합니다. `dart_remote.db`·`dart_remote.runtime_cache`·화면 adapter 로거를 DEBUG로 설정하면 SQL 소요 시간, 요청당 실제/재사용 SQL 횟수와 화면 구성 시간을 확인할 수 있습니다. SQL 본문·비밀번호·파라미터는 기록하지 않습니다.

적용하려면 로컬 서버를 재시작하거나 배포 이미지를 다시 빌드하여 컨테이너를 재생성합니다. 보고서/LLM 분석 재생성은 이 최적화만을 위해 필요하지 않습니다. 실제 운영 응답 시간은 서버에서 별도로 측정해야 합니다.

## 첫 화면 준비와 성능 점검 (2026-10-10)

로컬 서버 시작과 배포 Compose 실행은 첫 화면에 필요한 저장 결과를 별도 작업으로 미리 읽는다. 서버 시작 완료를 기다리게 하거나 LLM 분석을 새로 실행하지 않는다. `UI_PREWARM=0`이면 끌 수 있다. 배포 앱을 Compose 없이 실행하면 기본적으로 꺼져 있으므로 필요하면 `UI_PREWARM=1`을 지정한다. 준비에 실패해도 서버는 시작하며 다음 사용자 요청에서 재시도한다.

변경 이후에도 기존 분석 명령과 서비스 실행 명령은 동일하다. 캐시는 프로세스별로 독립적이며 서버 재시작 시 비워진다. 보고서·시세 파일 변경과 기존 최신성 확인을 유지한다. 속도 개선 검증은 가상 자료와 자동 테스트로 실시하며 원격 DB 데이터나 스키마는 변경하지 않는다. 운영 서버에서 실제 개선 폭은 첫 요청·반복 요청의 Network 시간과 서버 로그를 비교해야 한다.

현재 서비스의 배포 테스트는 `test_service.py`를 기준으로 실행한다. 배포 테스트 폴더의 과거 `test_search_server.py`는 현재 제거된 별도 검색 서버를 참조하여 전체 폴더 탐색 시 가져오기 오류가 발생한다. 이는 이번 최적화에 따른 API 오류와 구분해야 한다.


## 화면에 표시할 프롬프트 버전 선택

분석 생성 옵션 `--prompt-version`과 화면 표시 설정 `REPORT_PROMPT_VERSION`은 독립적입니다. 기본 표시 버전은 `new`입니다. 분석 전체와 데이터 버전 검증이 성공한 후에만 섹터별 `report/prompt-new.json`, `report/prompt-new2.json`, `report/prompt-old.json`을 갱신합니다. 기존 `report/current.json`도 호환성을 위해 유지합니다. DB 스키마, 검색, 프롬프트, 화면의 응답 구조는 변경하지 않습니다. 각 보고서의 문장과 각주 근거는 함께 저장됩니다.

기존 `llm` 폴더의 개별 응답 캐시는 그대로 재사용합니다. 과거에 덮어써진 완성 보고서는 개별 캐시만으로 앱 시작 시 자동 조립하지 않습니다. 필요한 버전으로 분석을 한 번 실행하면 유효한 캐시를 재사용하여 완성 보고서를 저장합니다. 누락되거나 현재 입력·검증 규칙에 맞지 않는 캐시는 기존 정책대로 다시 생성됩니다. 이때 `--refresh-llm`을 지정하면 캐시를 강제로 다시 생성하므로 재사용 목적이라면 지정하지 않습니다.

기존 완성 보고서는 인사이트에 기록된 프롬프트 버전이 명확하게 일치할 때만 읽습니다. 이후 분석을 실행할 때 기존 완성 보고서도 해당 버전의 저장 공간이 비어 있다면 보존합니다. 이미 덮어써져 없는 과거 보고서를 복구하지는 않습니다. 요청 버전의 보고서가 없으면 그 섹터는 분석 결과 없음으로 처리하며 다른 버전으로 대체하지 않습니다. 기존 데이터 지문 검사도 유지하므로 DB가 바뀌었다면 분석을 다시 수행해야 합니다. LLM 없이 만든 공시 발췌 보고서는 버전별 성공 AI 보고서를 덮어쓰지 않습니다.

로컬 실행 예시:

```powershell
python -X utf8 app.py --prompt-version new2
```

배포 환경에서는 `deploy/.env`에 다음 값을 설정한 뒤 앱 컨테이너를 다시 생성합니다. 이미 실행 중인 앱의 환경설정은 재시작 과정에서 적용합니다.

```dotenv
REPORT_PROMPT_VERSION=new2
```

```bash
docker compose up -d --force-recreate app
```

코드 변경을 처음 반영할 때는 `docker compose build app`으로 이미지를 먼저 다시 빌드합니다. 분석 생성은 기존과 같이 `python -m snapdart.analyze --llm --prompt-version new2` 또는 `docker compose run --rm app python -m cloudapp.cli build --llm --prompt-version new2`로 실행합니다. 선택 버전은 산업·기업·워드 클라우드·각주 조회·홈 화면의 보고서 준비 상태에 일관되게 적용됩니다. 시세 캐시는 버전 간 공용입니다.
