# 실행 배포와 점검

확인 기준일: 2026-10-08. [문서 목록](README.md)

## 구현 의도와 실행 전 조건

로컬은 Windows의 Python 3.12 환경, 배포는 Linux Docker 환경을 기준으로 한다. 웹 서버와 질문 임베딩을 해당 환경에서 실행하되 재무·공시 원천은 읽기 전용 원격 MySQL을 공유한다. 분석 결과와 모델·벡터 캐시는 원천 DB와 별도로 저장한다.

MySQL 접속 경로와 현재 데이터 버전이 준비되어 있어야 한다. Gemini 생성은 API 키와 모델 권한, 시세 수집은 KRX 키와 외부 통신이 필요하다. BGE-M3 첫 실행은 모델 다운로드 또는 미리 준비한 모델 캐시가 필요하다. 키·비밀번호의 실제 값은 이 문서에 적지 않는다.

| 환경설정 | 역할 |
| --- | --- |
| MYSQL_HOST, MYSQL_PORT, MYSQL_DATABASE 등 | 원격 DB 접속; SQL_* 별칭도 연결 코드에서 지원 |
| GEMINI_API_KEY 또는 GOOGLE_API_KEY | Gemini 생성 인증 |
| GEMINI_MODEL | 생성 모델; 코드 미지정 기본 gemini-3.5-flash-lite |
| GEMINI_TPM_BUDGET, GEMINI_RPM_BUDGET | 실제 계정 한도에 맞춘 자체 사용량 예약 |
| GEMINI_CONCURRENCY | 인사이트 병렬 작업 수, 기본 4·범위 1-4 |
| SEARCH_BACKEND | Windows 기본 numpy, Linux 기본 faiss; keyword는 명시 선택 |
| BGE_M3_DEVICE, BGE_M3_CACHE_DIR | 질문 임베딩 장치와 모델 캐시 |
| DART_CACHE_DIR, SERVICE_CACHE_DIR | 벡터 스냅샷과 앱 결과 저장 위치 |
| KRX_API | 공식 KRX 지수·시가총액 수집 인증 |

## 로컬 실행

프로젝트 루트에서 해당 Python 환경으로 실행한다. 설치에는 루트 `requirements.txt`를 사용한다.

```powershell
python -m pip install -r requirements.txt
python -X utf8 -m snapdart.analyze --llm --sector 반도체 --prompt-version new
python -X utf8 app.py
```

브라우저 주소는 `http://127.0.0.1:8501`이다. 서버 실행은 분석 생성과 별도다. `--sector`를 생략해 분석하면 현재 데이터가 구축된 전체 산업을 순차 처리한다. `--years`를 생략하면 현재 DB의 전체 연도다.

```powershell
python -X utf8 -m snapdart.analyze --llm --sector 반도체 --companies 삼성전자 SK하이닉스 --years 2023 2024 2025
python -X utf8 -m snapdart.analyze --llm --sector 반도체 --prompt-version old
python -X utf8 -m snapdart.analyze --refresh-llm --sector 반도체 --prompt-version new
python -X utf8 app.py --no-market-refresh
```

기업·연도 예시는 해당 값이 현재 DB에 있을 때 사용한다. `--refresh-llm`은 Gemini 캐시를 재사용하지 않고 다시 생성한다. `--offline`은 Gemini 호출을 하지 않는 발췌 보고서 생성이며 MySQL 조회와 기본 의미 검색에 필요한 로컬 모델까지 생략하는 옵션은 아니다. 기존 AI 보고서를 발췌 보고서로 바꿀 목적이 있을 때만 사용한다.

검색과 재무 조회 문맥을 확인하는 별도 명령은 다음과 같다. `--llm`을 추가하지 않으면 Gemini를 호출하지 않는다.

```powershell
python -X utf8 -m snapdart.query --sector 반도체 --company 삼성전자 --year 2025 --question "HBM 수요 변화"
```

## Linux 배포 실행과 변경 반영

`deploy/`의 Dockerfile·requirements.txt·compose.yaml이 배포 묶음이다. 현재 Compose는 Linux host 네트워크를 사용하고 MySQL 접속을 호스트 `127.0.0.1:13306` 터널에 연결하도록 설정한다. 따라서 호스트의 터널이 실제 원격 DB에 연결되어 있어야 한다. 이 주소에 DB가 자동으로 생성되는 것은 아니다.

현재 `service_home` 볼륨은 보고서·시세·모델·벡터 캐시를 보존한다. 파일을 바꾸었으면 서버의 배포 디렉터리에 변경 내용을 반영하고 이미지를 다시 만든다. 아래 명령은 Linux 서버의 `deploy`에 해당하는 실행 디렉터리에서 사용한다.

```bash
docker compose build app
docker compose run --rm app python -m cloudapp.cli check
docker compose run --rm app python -m cloudapp.cli build --llm --sector 반도체 --prompt-version new
docker compose up -d --build --force-recreate
docker compose logs --tail=100 app
```

`build --llm`은 보고서 생성 명령이며 웹 서버 상시 실행은 `up -d`가 맡는다. 기본 포트는 8080이다. 외부 접속은 공인 IP, 서버·클라우드 방화벽의 해당 포트 허용이 준비되어야 한다. 코드를 교체한 뒤 분석 명령부터 실행하려면 먼저 `docker compose build app`으로 새 이미지를 만들어야 한다. 이미지의 기존 코드와 서버의 새 파일을 혼동하지 않는다.

배포의 연도 지정은 `--years`, 기업 지정은 로컬 `--companies`와 달리 `--codes`다. 시세 자동 갱신을 생략하는 직접 실행 옵션은 `python -m cloudapp.serve --no-market-refresh`이며 `NO_MARKET_REFRESH=1` 환경설정도 지원한다. Compose에서 적용하려면 해당 설정을 전달한 뒤 서비스를 다시 생성한다.

GCP용 GCS·Cloud SQL 관련 코드도 있지만 현재 Naver Cloud Compose는 GCS 설정을 비우고 호스트 터널을 사용하는 구성이다. 두 배포 환경의 필수 조건을 한 가지로 설명하지 않는다. 상세 배포 리소스는 [deploy/README.md](../../deploy/README.md)와 [compose.yaml](../../deploy/compose.yaml)을 확인한다.

## 오류를 구분하는 방법

| 증상 | 먼저 확인할 부분 |
| --- | --- |
| MySQL 접속 timeout | 호스트·포트, VPN/SSH 터널, 라우팅·방화벽; 인증 검사보다 통신 경로부터 확인 |
| 청크·벡터 개수/ID/버전 불일치 | 원천 DB 동기화와 current/validated·embedding 메타데이터 |
| Gemini 403 | 해당 키·프로젝트의 모델 권한, API 제한과 실제 오류 메시지 |
| Gemini 429 | RPM·TPM·일일 사용량과 다른 프로그램의 사용; 입력이 자체 단일 예산을 넘는지 구분 |
| 입력에 없는 근거 ID·검증 실패 | 실제 입력 ID와 응답, 프롬프트 버전, 인용 문장·위치·등급 조건 |
| 보고서 없음 또는 DB 버전 변경 | 해당 산업으로 분석을 성공시킨 뒤 웹 조회; 기존 결과 자동 재생성은 하지 않음 |
| 지수·주가 미표시 | KRX 키 승인·지수 이름·외부 통신·전일 이전 거래일 자료와 저장된 시세 상태 |

## 점검 범위

프로젝트 회귀 검사는 다음과 같다. 테스트가 통과했다고 원격 DB·실제 Gemini·KRX의 운영 호출까지 모두 검증한 것은 아니다.

```powershell
python -X utf8 -m unittest discover -s tests
```

배포 전용 테스트는 `deploy/`에서 다음 명령으로 실행한다.

```bash
python -m unittest discover -s tests
```

루트의 [test_deploy_parity.py](../../tests/test_deploy_parity.py)는 공통 코드·화면·프롬프트 등의 대응을 검사한다. [scripts/check_service.py](../../scripts/check_service.py)는 저장된 보고서와 실제 MySQL·로컬 모델을 사용해 로컬 HTTP 경로를 확인한다. 문서·테스트를 변경하는 작업에서 실제 API 분석 재생성까지 자동으로 수행할 필요는 없다.
