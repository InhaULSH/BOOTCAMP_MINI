# 02. 공시 검색과 벡터 검증

[문서 목록](README.md) · [앞: 데이터 조회](01_서비스구조와데이터조회.md) · 기준: 2026-10-08

## 이 문서에서는 무엇을 알아보는가

앞 문서에서는 분석할 산업·기업·기간을 정하고, DB에서 숫자와 공시 문장을 각각 꺼낸다는 큰 흐름을 살펴보았다. 이번에는 공시 문장을 꺼내는 부분을 자세히 알아본다. DB에 문단이 많이 저장되어 있다고 해서 그 문단을 전부 Gemini에 보내지는 않는다. 먼저 필요한 문단을 찾고, 그중 설명에 사용할 자료를 고른다.

예시는 가상의 A기업이다. A기업의 2025년 사업보고서에 “서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.”라는 문장이 저장되어 있다고 하자. 서비스가 서버용 제품 수요와 투자를 설명하려면 이 문장이 검색 결과에 들어와야 한다. 아래의 설명은 이 문장을 어떻게 찾고 다음 단계로 전달하는지 따라간다. 실제 기업의 공시나 현재 DB 내용이라는 뜻은 아니다.

## 첫째, 어디에서 찾을지 먼저 정한다

검색에는 두 가지 질문이 있다. 하나는 “어느 기업의 어느 보고서에서 찾을 것인가?”이고, 다른 하나는 “그 보고서에서 어떤 내용이 필요한가?”이다. 현재 코드는 이 두 질문을 나누어 처리한다.

먼저 A기업·2025년·사업보고서라는 조건으로 DB를 조회한다. 이때 사용하는 SQL은 DB에 자료를 요청하는 언어다. 서비스 코드가 정해진 조회문에 기업 코드와 연도 등의 조건을 넣는다. Gemini가 임의의 SQL을 만들거나 DB 전체를 돌아다니는 방식은 아니다.

이 과정을 거치면 다른 기업과 다른 기간의 문단은 검색 후보에서 빠진다. 예를 들어 B기업이 같은 제품을 설명했더라도 A기업만 분석하는 요청에는 섞이지 않는다. 사업 내용만 필요한 경로에서는 보고서의 “II. 사업의 내용” 범위로 후보를 더 좁힌다. 이렇게 먼저 범위를 정해야 의미가 비슷하다는 이유만으로 엉뚱한 기업의 설명을 가져오는 일을 줄일 수 있다.

## 둘째, 찾고 싶은 내용과 각 문단의 의미를 비교한다

기업과 기간을 정해도 후보 문단은 여러 개일 수 있다. “서버용 제품 수요와 투자”를 찾을 때 문서가 꼭 이 표현을 그대로 썼으리라는 보장도 없다. “생산능력 확대”, “설비 증설 계획”처럼 다른 말로 관련 활동을 설명할 수 있다.

그래서 현재 기본 검색은 문장의 의미를 숫자로 표현하는 BGE-M3라는 모델을 사용한다. 이러한 숫자 묶음을 벡터라고 하고, 문장을 벡터로 바꾸는 처리를 임베딩이라고 한다. 벡터의 숫자 하나하나를 사람이 “수요 점수”, “투자 점수”처럼 읽는 것은 아니다. 모델이 문장의 특징을 여러 숫자에 나누어 표현한 결과다.

공시 문단의 벡터는 DB에 이미 저장되어 있다. 검색할 때는 “서버용 제품 수요와 투자”라는 질문도 같은 모델로 벡터로 바꾼다. 질문과 문단이 서로 다른 모델의 숫자로 표현되면 비교 기준이 달라지므로, 현재 코드는 모델과 버전이 같은지도 확인한다. 실제 BGE-M3 벡터는 1,024개의 숫자로 이루어져 있지만, 이 개수를 외울 필요는 없다. 중요한 것은 **질문과 공시를 같은 기준으로 숫자로 표현한 뒤 비교한다**는 점이다.

질문에서 기업명과 이미 조건으로 정한 단일 연도는 정리할 수 있다. 기업과 기간은 SQL에서 제한했으므로, 의미 비교에서는 “수요와 투자”라는 사업 내용에 집중하게 하려는 것이다.

## 셋째, 관련성이 높은 문단부터 결과로 돌려준다

코드는 질문 벡터와 각 후보 문단의 벡터를 비교하여 점수를 계산한다. 현재 기본 경로에서는 코사인 유사도라는 비교값을 사용한다. 쉽게 말하면 두 숫자 묶음이 비슷한 방향을 나타내는 정도다. 점수가 높은 문단부터 검색 결과에 넣는다.

가상의 검색 결과에 생산능력 확대 계획 문단, 제품 구성 문단, 위험 설명 문단이 들어왔다고 하자. 검색 결과에는 문장만 담기는 것이 아니다. 기업명, 연도, 보고서 종류, 목차, DB에서 해당 문단을 구별하는 청크 ID, 원문 본문, 검색 점수를 함께 돌려준다. 청크는 검색을 위해 문서를 나눈 작은 본문 단위이며, 청크 ID는 그 본문을 다시 찾을 수 있는 고유 번호다.

이 정보가 있어야 다음 단계에서 “어느 기업의 어느 시점 이야기인지”를 알 수 있다. 나중에 원문을 보여줄 때도 같은 ID로 원본과 연결한다. 일반 검색 API는 기본적으로 상위 5개를 반환한다. 이것은 화면 인사이트에 무조건 다섯 문단을 사용한다는 뜻은 아니다.

검색 점수는 **질문과 얼마나 관련되어 보이는지**를 나타낸다. “확대를 계획한다”는 문단이 높은 점수를 받았다고 해서 실제 증설이 완료되었다는 뜻은 아니다. 그 문단이 생성하려는 설명을 직접 뒷받침하는지는 다음 문서에서 설명할 별도의 근거 평가가 판단한다.

## 넷째, 보고서 설명에 필요한 기간을 고르게 남긴다

보고서 생성에서는 일반적인 검색 결과를 그대로 모두 사용하지 않는다. 산업 설정에 들어 있는 사업·투자·위험 주제로 기업별 자료를 검색한 다음, 연도와 보고서 종류별로 후보를 남긴다. 화면에 자유로운 채팅 검색이 있다는 의미가 아니라, 현재 보고서 생성 코드가 필요한 주제를 정해 검색한다는 뜻이다.

이렇게 하는 이유는 변화 설명에 과거와 현재가 모두 필요하기 때문이다. 전체 기간에서 점수만 높은 문단을 몇 개 고르면 최신 보고서만 남고 과거 자료가 빠질 수 있다. A기업의 생산능력 확대 계획이 새롭게 등장한 것인지, 여러 해 계속 반복한 것인지 살펴볼 기회가 줄어드는 것이다.

현재 파이프라인은 검색 후 최신 연도 보고서별 최대 2개, 과거 연도 보고서별 최대 1개를 입력 후보로 사용하고, 뒤에서 문장 조건과 입력 크기 제한을 더 적용한다. 이 마지막 선택은 기간과 청크 ID로 정리된 목록에서 이루어진다. 모든 관련 문단 중 가장 좋은 근거가 반드시 남는다는 보장은 없다. 기간을 고르게 다루면서 입력을 제한하는 현재 구현의 선택이다.

워드클라우드의 특정 단어 설명은 별도 경로다. 선택한 단어와 관련된 최신 분석 연도의 사업 내용 문단을 찾는다. 따라서 여러 해의 단어 변화 통계와, 그 단어에 붙는 최신 공시 설명은 자료 범위가 서로 다를 수 있다.

## 다섯째, 문단과 벡터가 제대로 짝지어졌는지 확인한다

문단의 내용이 바뀌었는데 이전 내용의 벡터가 남아 있으면, 검색 점수는 이전 내용을 기준으로 계산하고 화면에는 새 내용을 보여주는 문제가 생길 수 있다. 문단 A의 ID에 문단 B의 벡터가 연결된 경우도 마찬가지다. 이런 결과는 문장이 자연스러워도 검색 자체를 믿기 어렵다.

그래서 코드는 검색 전후에 현재 데이터 버전을 확인하고, 청크와 벡터의 ID·개수·모델·버전 등이 맞는지 검사한다. 버전은 함께 사용해야 하는 자료 묶음을 구별하는 표시다. 처음 사용할 때에는 일부 문단을 같은 방식으로 다시 임베딩하여 저장 벡터와 매우 비슷한지도 확인한다. 일부를 확인하는 표본 검사이므로 전체 문단의 내용을 모두 검증한다는 뜻은 아니다.

조건이 맞지 않으면 의미 검색을 중단한다. 다른 산업 자료나 예전 벡터를 조용히 대신 쓰지 않는다. 이 검사는 현재 전체 자료의 연결 상태를 포함하므로, 다른 산업의 동기화 문제 때문에 지금 검색하는 산업도 중단될 수 있다.

## 반복 검색에서는 무엇을 다시 사용하나

벡터를 검색할 때마다 DB에서 전부 다시 내려받으면 시간이 오래 걸린다. 코드는 한 번 읽어 검증한 벡터 묶음을 파일과 메모리에 보관하고, 같은 자료를 다시 찾을 때 재사용한다. 이렇게 반복 작업을 줄이기 위해 보관하는 자료를 캐시라고 한다. 캐시를 사용해도 실제 본문은 DB의 현재 후보와 연결하여 확인한다.

Windows에서는 NumPy라는 숫자 계산 도구로 후보를 비교하고, Linux에서는 FAISS라는 벡터 검색 도구를 기본으로 사용한다. 현재 둘 다 정해진 후보를 모두 비교한다. FAISS를 쓴다고 해서 이 서비스가 외부 검색 서버에 질문을 맡기는 것은 아니다. 서비스가 MySQL에서 벡터를 읽어 자기 메모리에서 비교하는 구조다.

이 방식은 운영할 서버 종류를 줄이지만, 자료가 늘수록 서비스가 보관하고 비교할 벡터도 많아진다. 따라서 검색을 정확하게 연결하는 장점과 메모리·계산 비용을 함께 고려한 설계다.

## 이 단계가 끝나면 무엇이 남는가

공시 검색의 결과는 관련 문단과 그 문단의 기업·시점·원문 연결 정보다. 아직 사용자에게 보여줄 설명 문장은 완성되지 않았다. 다음 [03. 인사이트 생성과 프롬프트](03_인사이트생성과프롬프트.md)에서는 이 자료를 어떻게 줄여 Gemini에 전달하고, 생성한 설명을 어떤 조건으로 받아들이는지 살펴본다.

## 구현 상세: 파일과 정확한 처리 기준

앞부분의 흐름을 이해한 뒤 필요한 항목을 찾아 읽는 참고 영역이다. 처음 읽을 때 모든 함수명과 설정값을 외울 필요는 없다.

### 구현 의도: 대상은 SQL로 제한하고 의미는 벡터로 비교한다

“HBM 수요”를 찾을 때 같은 단어가 반복된 문단과 실제 제품 수요를 설명하는 문단은 다를 수 있다. 기업·기간을 무시하면 다른 기업의 계획이나 오래된 문구가 섞일 수도 있다. 현재 검색은 먼저 SQL로 산업·기업·기간·보고서 범위를 고정하고, 그 안에서 BGE-M3 의미 유사도를 계산한다.

BGE-M3는 입력 문장을 1,024개 숫자로 표현한다. 질문과 공시를 같은 모델·전처리 기준으로 표현해야 비교가 의미를 가진다. 단순히 차원이 같다는 이유로 다른 모델의 벡터를 섞지 않도록 데이터 검증을 검색 앞에 둔다.

### 담당 코드와 입력·출력

| 파일·주요 함수 | 역할 |
| --- | --- |
| [repository.py](../../dart_remote/repository.py)의 `chunks`, `search`, `select_evidence` | SQL 후보 조회, 일반 검색, 보고서 생성용 기간별 근거 선정 |
| [mysql_vectors.py](../../dart_remote/mysql_vectors.py)의 `contract`, `snapshot`, `rank` | 자료 계약 검사, 저장 벡터 캐시, 질문 임베딩·순위 계산 |
| [vector.py](../../dart_remote/vector.py) | 명시적으로 선택한 키워드 검색 경로 |
| [query.py](../../snapdart/data_access/query.py)의 `Query`, `retrieve` | 질문의 재무/공시/혼합 의도를 정한 조회 결과 |

입력은 질문과 산업, 선택 기업, 선택 연도·보고서, `top_k`다. 출력은 원문 청크 목록과 검색 상태다. 각 청크는 기업·연도·보고서·접수번호·목차·청크 ID·본문·검색 점수를 포함한다. 웹 검색 API의 기본 `top_k`는 5, 허용 범위는 1-40이다.

### 질문 하나의 실제 처리 순서

1. Repository가 요청 기업을 해당 산업의 현재 운영 기업으로 확인한다.
2. 현재 버전에서 활성·검색 가능 청크를 읽는다. 기업·연도·보고서 조건을 SQL에 넣는다. `business_only`이면 `II.%` 목차로 제한한다.
3. 현재 데이터·인덱스·임베딩 메타데이터가 일치하는지 검사한다.
4. 저장 벡터 스냅샷에서 후보 청크와 같은 벡터를 골라낸다. 본문 해시와 식별자도 비교한다.
5. 질문에서 후보 기업명과, 후보가 단일 연도일 때 그 연도 숫자를 제거하고 공백을 정리한다. 이미 SQL로 정한 조건이 의미 검색을 지나치게 지배하지 않게 한다.
6. 질문을 고정 버전의 BGE-M3로 임베딩하고 길이가 1인 벡터로 정규화한다.
7. 후보 벡터와 질문 벡터의 내적을 계산해 높은 순서로 반환한다.
8. 검색 종료 때 현재 버전을 다시 검사한다. 도중에 변경됐다면 결과를 사용하지 않는다.

질문이 기업명·연도만 있어서 정리 후 비어 있으면 오류다. 내부 질문 한도는 8,000자와 모델 토크나이저 기준 8,192토큰이며, 배포 HTTP 검색 API는 별도로 질문 2,000자 제한을 적용한다.

### 유사도는 무엇이며 어떻게 순위를 정하는가

정규화한 질문 벡터를 `q`, 청크 벡터를 `v`라고 하면 점수는 `q·v`다. 두 벡터의 길이가 1이므로 내적이 코사인 유사도와 같다. 숫자가 높을수록 모델이 표현한 의미 방향이 가깝다는 뜻이다. 사실이 참이거나 문장의 인용 근거로 충분하다는 확률은 아니다.

Windows 기본 `numpy`는 후보 행렬에 질문 벡터를 곱한다. Linux 기본 `faiss`는 해당 후보들로 메모리의 `IndexFlatIP`를 만들어 같은 내적 검색을 수행한다. 둘 다 후보 전체를 비교하는 정확 검색이다. HNSW·IVF 같은 근사 검색이나 별도 재순위 모델은 현재 사용하지 않는다. [FAISS 공식 거리 설명](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances), [인덱스 종류](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes).

현재 런타임은 MySQL의 벡터 BLOB으로 검색한다. 외부에서 제공한 `.faiss` 파일을 `FAISS_INDEX_PATH`로 열어 검색 서버에 연결하는 방식이 아니다. DB 메타데이터에 FAISS 파일 해시나 원천 인덱스 종류가 있어도 런타임 인덱스 방식과 구별해야 한다.

### 저장 벡터가 질문과 비교 가능한지 확인하는 과정

#### 데이터 계약 검사

`contract()`가 확인하는 주요 조건은 다음과 같다.

| 검사 | 막으려는 문제 |
| --- | --- |
| 현재·검증된 데이터 버전이 하나 | 동기화 중 여러 현재 버전을 섞는 문제 |
| 현재 임베딩 메타데이터의 버전 일치 | 새 본문에 이전 벡터를 연결하는 문제 |
| 모델 `BAAI/bge-m3`, 고정 revision, 차원 1,024, 정규화 설정 | 다른 모델·형식의 벡터를 비교하는 문제 |
| 메타데이터 개수와 실제 검색 가능 청크·벡터 연결 개수 일치 | 부분 적재·누락 벡터 |
| 벡터 ID의 유일성, 청크/벡터의 ID·모델 일치와 검증된 내용 해시 기반 버전 호환 | 중복·잘못된 연결 |

고정 모델 revision은 `5617a9f61b028005a4858fdac845db406aefb181`이다. 단순 모델 이름만 같고 다운로드 시점에 따라 파일이 달라지는 상황을 줄이기 위한 고정값이다.

전체 연결 검사 결과는 같은 계약이면 30초간 재사용한다. 현재 버전은 각 검색에서 확인한다. 이 검사는 검색 범위 밖의 자료까지 포함하므로 다른 산업에 연결 오류가 있어도 현재 산업의 의미 검색이 중단될 수 있다. 자료 전체의 정합성을 우선한 설계다.

#### 벡터 자체와 본문 연결 검사

BLOB은 32비트 실수 1,024개, 즉 4,096바이트로 읽는다. 배열 모양·유한값·벡터 길이·고유 ID를 검사한다. 후보 청크를 캐시에 대응시킬 때 `vector_id`, 데이터·인덱스 버전, `content_hash`, 모델·revision·차원이 같아야 한다.

첫 사용에는 스냅샷의 앞 최대 5개 청크를 다시 임베딩한다. 원천의 임베딩 입력 방식에 맞춰 **목차 + 소제목 + 본문**을 공백으로 이어 붙이고, 저장 벡터와 유사도가 0.999 이상인지 확인한다. 이는 모델·라이브러리·입력 방식이 크게 달라졌는지 확인하는 표본 검사다. 모든 청크를 재임베딩하거나 문장의 사실성을 검증하는 과정은 아니다.

BGE-M3 공식 모델은 dense·sparse·다중 벡터 검색을 지원하지만, 현재 서비스는 단일 dense 벡터만 사용한다. 공식 모델의 차원과 길이 설명은 [BAAI 모델 카드](https://huggingface.co/BAAI/bge-m3)를 참고한다.

### 캐시가 속도를 줄이는 방식과 비용

벡터 스냅샷은 현재 검색 가능한 전체 자료를 DB에서 읽어 `.dart_cache` 또는 `DART_CACHE_DIR`에 NPZ로 보관한다. 최초 적재는 `vector_id` 기준으로 2,000행씩 읽는다. 큰 OFFSET을 반복하는 대신 마지막 ID 이후를 조회한다.

캐시 키에는 DB 접속 대상, 데이터·인덱스 버전, 모델·차원·개수, 원천 해시가 들어간다. 파일 내부에는 행렬과 메타데이터의 검증 해시가 있고, 불일치하면 다시 읽는다. NumPy 로드 시 pickle을 허용하지 않는다. 완료된 파일을 임시 파일에서 교체하므로 중간 파일을 완성 캐시처럼 사용하지 않는다.

같은 프로세스는 스냅샷과 모델을 재사용하며 질문 벡터는 최대 128개 보관한다. 모델 접근을 잠금으로 보호하므로 여러 Gemini 작업이 동시에 실행돼도 질문 임베딩이 무제한 병렬로 수행되지는 않는다.

이 방식은 별도 벡터 서버 운영을 줄이는 대신, 서비스 프로세스가 전체 저장 벡터를 메모리에 들고 있어야 한다. N개 벡터만의 원시 메모리 크기는 `N × 1,024 × 4바이트`이며 메타데이터·후보 배열·모델 메모리는 추가다. SQL 후보 본문 조회도 필요하다. 자료가 크게 늘면 캐시·정확 검색 비용을 다시 평가해야 한다.

### 보고서 생성용 근거 검색은 일반 top_k와 어떻게 다른가

일반 검색은 질문 한 번의 유사도 순위를 반환한다. `select_evidence()`는 산업 설정의 사업·투자·위험 주제를 기업별로 검색한 뒤 연도·보고서마다 근거를 남긴다. 최신 문서의 높은 점수가 과거 자료를 모두 밀어내면 변화 설명이 어려워지기 때문이다.

의미 검색에서는 기업별 각 주제를 전체 기간 후보에 대해 한 번 비교한 뒤 결과를 기간별로 나눈다. 주제별로 기간당 일정 개수를 골라 중복을 제거하고 기간당 최대 8개를 남긴다. 파이프라인은 그중 최신 연도 보고서별 최대 2개, 과거 연도 보고서별 최대 1개를 입력 후보로 사용한다.

주의할 점은 파이프라인으로 전달할 최종 목록이 기간·청크 ID 순으로 정리된다는 것이다. 마지막 1개·2개 선택까지 전체 후보 중 유사도 최대값을 다시 찾는 방식은 아니다. 기간별 균형과 입력 크기를 제한하는 구조이며, 최적 근거를 모두 포함한다는 보장은 없다. 이후 자연어 문장 필터와 입력 예산이 한 번 더 적용된다.

키워드 인사이트는 선택 키워드로 최신 분석 연도의 사업 내용 청크를 최대 16개 검색한다. new/new2에서는 같은 기업·키워드·보고서 종류의 이전 분석 연도 근거를 최대 4개 검색 범위에서 각 1개 보충한다. 이후 글자 수 예산이 적용되어 일부 자료는 제외될 수 있다. 최신 자료가 설명의 중심이고 이전 자료는 비교 참고용이다. 워드 클라우드의 단어 선정·통계 계산을 바꾸는 변경은 아니다. 요청 문맥에는 자연어 문장 앞뒤의 제한적인 원문도 추가하며 각주 문장 ID와 원문 위치는 유지한다. 자세한 처리와 한계는 [03](03_인사이트생성과프롬프트.md)의 new2 및 문맥 보충 항목을 참고한다.

### 예시와 검색 실패의 의미

가상으로 A기업의 2025년 FY에서 “서버용 메모리 수요와 투자”를 검색한다고 하자. SQL은 A기업·2025·FY의 현재 검색 가능 청크만 후보로 만들고, 질문에서 A기업 이름과 2025를 제거한 뒤 사업 의미를 비교한다. 수요·투자를 설명하는 청크가 높은 점수로 반환될 수 있다. 그 청크가 실제 설명의 원인·시점을 뒷받침하는지는 이후 Gemini 근거 평가와 코드 검증으로 확인한다.

후보 0개, 관련성이 약한 후보, 청크·벡터 연결 오류는 서로 다르다. 후보 0개는 빈 결과가 될 수 있지만 내용 해시가 다른 버전이나 검증되지 않은 버전은 검색을 중단한다. 이름만 다른 버전은 두 자산 해시가 같을 때에만 허용한다. 서비스가 임의로 과거 벡터나 다른 산업 자료로 대체하지 않는다.

`SEARCH_BACKEND=keyword`를 명시하면 기존 어휘 빈도·별칭 기반 검색을 사용할 수 있다. 이것은 의미 검색 오류 시 자동 우회하는 기능이 아니다. 현재 기본 검색에는 과거의 “키워드 상위 청크 벡터를 평균해 질문 벡터로 사용”하거나 키워드 점수와 코사인 점수를 가중합하는 경로가 없다.

관련 검증: [test_mysql_vectors.py](../../tests/test_mysql_vectors.py), [test_sector_repository.py](../../tests/test_sector_repository.py), [test_provided_client.py](../../tests/test_provided_client.py). 생성 단계에서 검색 근거를 어떻게 줄이고 검증하는지는 [03](03_인사이트생성과프롬프트.md)을 참고한다.


### 2026-10-09: 재무 버전과 공시 자산의 버전 구분

재무 자료가 v11로 바뀌어도 공시 본문과 벡터가 그대로라면 벡터의 생성 버전은 이전 이름으로 남을 수 있다. `asset_versions.py`는 검증된 `data_versions`에서 현재 버전과 `vector_sqlite_sha256`, `faiss_sha256`이 모두 같은 버전만 호환 대상으로 선택한다. 둘 중 하나가 다르거나 해시가 없으면 이전 버전은 허용하지 않는다. 현재 임베딩 메타데이터의 해시도 현재 등록값과 일치해야 한다. 이름 비교를 없앤 것이 아니라, 내용이 같은 자산에만 제한적으로 재사용을 허용한 것이다.

청크·재무·coverage는 여전히 현재 버전에서만 조회한다. 벡터 다운로드에서는 호환되는 데이터/인덱스 버전의 짝, 청크 ID, 벡터 ID, 모델·리비전·차원·바이트 길이를 검사한다. 캐시 계약에는 호환 버전 목록이 추가되며 형식을 2로 바꾸어 이전 캐시를 구분한다. 행렬 전체의 유한값과 정규화 검사 및 BGE-M3 재임베딩 표본 검사는 그대로 유지한다. 등록 해시는 데이터 담당자의 검증 기록이므로 서비스가 외부 SQLite/FAISS 파일 전체를 직접 다운로드해 재검증하는 것은 아니다.
