# 03. 인사이트 생성과 프롬프트

[문서 목록](README.md) · [앞: 공시 검색](02_공시검색과벡터검증.md) · 코드 확인 기준: 2026-10-12

## 이 문서는 무엇을 설명하는가

검색은 관련 있어 보이는 공시를 찾는 단계다. 인사이트 생성은 그 자료를 읽고 사용자가 이해할 수 있는 짧은 설명으로 만드는 단계다. 이 둘을 연결하는 것은 Python 코드이며, Gemini가 직접 MySQL을 조회하는 것은 아니다.

이 문서에서는 입력 자료 구성 → 단일 Gemini 생성 요청 → 응답·출처 확인 → 저장·화면 출력의 순서로 설명한다. **기본 mvp는 출처 연결 중심이고, strict는 점수와 수치까지 정밀 검사한다.** 아래에서 두 모드를 구분한다. 지침에 적힌 제한과 코드가 실행 실패 조건으로 강제하는 제한은 서로 같지 않을 수 있다.

## 1. 설명에 필요한 자료부터 모은다

가상 A기업의 공시에 “서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.”라는 문장이 있다고 하자. 설명할 수 있는 것은 수요 대응을 위한 생산능력 확대 계획이다. 완료나 실적 개선 효과까지 확인된 것은 아니다. 이를 구별하도록 글쓰기 지침과 근거 연결 규칙을 전달한다.

산업·기업 인사이트는 기업별 검색 주제와 보고서 시점에서 확보한 공시 후보를 사용한다. 최신 분석 연도뿐 아니라 과거 비교 자료도 제한적으로 넣는다. 키워드 설명은 선정 단어로 최신 연도의 사업 내용을 검색하고, new·new2는 필요한 이전 기간·인접 문맥을 보충한다.

후보 청크에서 인용 가능한 자연어 문장 `passages`를 만든다. 표·숫자 나열·짧은 문구 등은 보수적으로 제외한다. 기업별로 번갈아 담으며 기본 48,000자의 원래 청크 길이 예산 안에서 선택한다. 같은 기업의 긴 자료만 요청을 채우지 않게 하려는 것이다.

내부에서는 전체 청크와 원문 위치를 보존한다. 실제 API 전송 직전에는 `llm.model_context()`가 passages가 있는 공시 항목의 전체 text를 제거하고 문장 목록을 보낸다. 따라서 내부 보존 자료와 전송 자료는 다르다. 공시 전문이나 검색용 벡터를 Gemini에 보내는 방식은 아니다.

## 2. 숫자와 공시를 다른 이름표로 연결한다

공시 청크에는 `t1`, 그 안의 문장에는 `t1-p1`, 재무 근거에는 `f1` 같은 임시 ID를 붙인다. ID는 이번 요청의 이름표이며 DB 고유 청크 ID가 아니다. 코드가 문장의 실제 시작·끝 위치를 알고 있으므로 모델은 제공된 문장 ID를 선택하면 된다.

new는 연간 재무 이력과 최신 연도의 분기·반기 누적 자료를 보조 입력으로 받는다. new2의 산업·기업 경로는 `financial_evidence.prepare()`가 항목·기업·기간·단위·회계 기준·원자료 출처를 붙인 재무 근거를 준비한다. 최신 연도와 직전 연도의 중간 보고서도 포함한다. 출처를 확인하지 못한 값은 적격 재무 근거로 만들지 않는다.

new2는 매출액·이익·CAPEX·현금흐름과 필요한 비율을 계산하고, 은행·헬스케어는 승인된 추가 계정 조회를 재사용한다. 그래프에 있는 모든 지표가 같은 정의로 LLM 입력에도 존재하는 것은 아니다. 예를 들어 순이자이익을 순이자마진으로, 전체 순이익을 지배주주 순이익으로 바꾸어 사용할 수 없다.

비교 정보는 기업·항목·보고서 종류·연간/누적·연결/별도 기준이 같고 정확히 1년 차이인 값에서 만든다. 분모가 양수일 때만 증감률을 계산하고, 비율의 변화는 %p로 구분한다. 이전 값이 0이나 음수라고 임의의 성장률을 만들지 않는다. CAPEX 검증과 XML 추정 상태는 유지한다.

## 3. 지원하는 프롬프트는 new·new2·old다

| 버전 | 내용·입력의 의도 | 근거와 화면 |
| --- | --- | --- |
| new, 기본값 | 재무를 참고하면서 자연어 공시의 사업 현황과 흐름을 쉽게 설명 | 공시 문장 근거가 중심 |
| new2 | 의미 있는 재무 흐름과 실제 사업 움직임을 함께 종합, 근거 없는 인과관계 금지 | 재무 ID는 내부 근거로, 고객 각주는 자연어 공시만 표시 |
| old | 이전 문체·근거 선정 기준 보존 | 기존 공시 평가와 출력 방식 유지 |

new2는 산업·기업 인사이트의 공통·전용 지침을 바꾼다. 기업 지침만 교체하는 과거 방식은 아니다. 산업 지침은 기업명 나열이나 특정 기업에만 국한된 설명을 금지하며 필요한 경우 사업군으로 범위를 좁힌다. 단순 사실 나열보다 사용자가 중요 흐름의 의미를 이해하도록 설명하게 한다.

최종 생성 요청은 지침 + 해당 기능의 작업 내용 + 선택 버전 근거 선정 지침 + 공통 출력 안내로 구성된다. new2의 산업·기업에는 숫자마다 항목·기간을 명확히 붙이라는 추가 지침도 들어간다. 산업·기업은 1-3문장, 키워드는 1-2문장이라는 현재 new·new2 지침과 스키마를 사용한다. old 기업 경로는 기존 상한 정책을 보존한다.

new2의 키워드 설명은 new와 같은 공통·키워드 지침과 공시 선정 경로를 사용한다. 모든 버전에서 별도 사실 정리 LLM을 먼저 호출하는 방식은 아니다. 정상 생성은 한 요청이며 검증 교정·통신 재시도는 별도다.

프롬프트는 코드 상수에 들어 있다. [new 원문](프롬프트_정의서_new.md), [new2 원문](프롬프트_정의서_new2.md)은 코드와 맞춘 설명 문서이며 런타임에 직접 읽어 실행하는 파일은 아니다. new2의 밑줄은 new에 비해 직접 달라진 부분을 표시한다.

## 4. 글쓰기 지침과 승인 모드를 구별한다

`INSIGHT_VALIDATION_MODE`를 생략하면 mvp다. 값이 strict이면 정밀 검증한다. 프롬프트 버전과 검증 모드는 별개의 설정이다. **mvp에서 짧거나 점수가 낮은 설명이 코드 검사로 무조건 거부되는 것은 아니다.** JSON Schema와 프롬프트는 계속 전달하지만 Python의 승인 조건은 아래와 같다.

| 검사 | mvp: new·new2 경로 | strict: new·new2 경로 |
| --- | --- | --- |
| 문장 객체·문장 문자열·입력 근거 ID | 확인, 없는 근거 ID 차단 | 확인 |
| 중복 ID | 중복 제거 | 오류로 처리 |
| 공시의 실제 제공 문장 ID·위치 | 유효한 선택만 표시, 위치가 없는 각주는 제외 | 부적격 연결을 오류로 처리 |
| 공시 F/U/C/T 등급·점수·적격성 | 점수 미달을 승인 실패 조건으로 사용하지 않음, 점수는 None | 등급·suitable·감점·점수 기준 검사 |
| 응답 문장 수·빈 이유 | 길이를 추가 승인 조건으로 사용하지 않음, 필요한 부족 이유 보완 | 지정 범위와 부족 이유 확인 |
| new2 재무 수치·비교·두 근거 종류 균형 | 진단 검사, 실패 내용은 validation_warnings에 기록 | 불일치 시 교정·실패 |
| DB 버전·벡터·재무 원자료 승인 | 유지 | 유지 |

mvp는 원문 위치가 확인된 인용만 각주에 연결하며 공시 평가가 없으면 관련 인용을 제외한다. 표시 가능한 공시 위치가 하나도 없는 문장은 생략한다. new2의 재무 ID는 별도 허용하므로 재무만 연결된 문장이 남을 수 있다. 빈 결과에는 부족 이유를 넣는다. 원문 위치를 임의로 만들거나 빠진 평가 등급을 높은 값으로 채우지는 않는다.

이 완화는 생성 응답의 승인 단계다. MySQL 무결성·재무 원자료 승인·CAPEX·XML 추출 검증까지 해제한 것은 아니다. old의 기존 선정 검증 함수도 이 작업에서 바꾸지 않았다. old를 선택했다고 new·new2용 mvp 근거 점수 완화가 그대로 적용되는 것은 아니다. 다만 개별 생성 예외의 격리와 수치 후처리 여부 등 공통 파이프라인 설정은 모드의 영향을 받는다.

mvp가 확인한 것은 주로 형식과 출처 연결이다. “AI 생성 · 출처 연결 확인 (MVP)” 결과를 모든 수치와 의미가 검증된 분석으로 설명하면 안 된다. 등급도 같은 Gemini 요청에서 나온 판단이므로 별도 모델이나 전문가의 독립 심사라고 부르지 않는다.

## 5. strict에서는 무엇을 더 확인하는가

### 자연어 공시 근거

F는 사실 부합도, U는 사업 이해 도움, C는 명확성, T는 시점 적합성이다. 0-4 등급을 받고 new·new2는 40%·30%·20%·10%로 계산한다. 불필요한 내용과 반복에 감점이 있다. F≥3, C≥3, 점수≥75, 적합성 등 조건을 확인한다. old는 이전 가중치와 검증을 보존한다.

ID와 평가 누락, 실제 기준 미달을 구분한 진단을 만든다. 근거 점수만 올려 통과하지 말고 주장을 좁히거나 직접적인 원문을 다시 선택하도록 교정한다. 점수가 높아도 사업 의미의 정확성을 코드가 완전히 증명한 것은 아니다.

### new2의 재무 문장

숫자는 문장이 선택한 재무 ID 안에서 대조한다. 기업·기간·연결/별도·항목·단위와 금액·비율·증감률·방향을 확인한다. 최신 개선은 다음과 같다.

- 항목명이 숫자 앞뿐 아니라 뒤에 붙은 “215억원의 CAPEX”, “32.3%의 CAPEX/매출액”도 해석한다. 다른 문장의 항목명까지 끌어오지는 않는다.
- 같은 절의 “영업이익·순이익 각각 17%, 13%”는 항목·숫자의 순서를 제한적으로 연결한다. 기업·기간·회계 기준이 여러 개면 모호한 것으로 처리한다. 지침 자체는 항목별 명시를 요청한다.
- “전년 150억원”은 현재 값의 검증된 전년 비교 연결을 따라 해석한다. 괄호 안에 끝난 전년 비교가 주절 전체의 연도를 바꾸지 않도록 한다.
- H1 누적값을 단일 Q2로, 전년 동기 변화율을 전분기 변화율로 바꾸지 않는다. 이익률 수준 %와 변화 %p를 구별한다.
- 순이자이익과 NIM, 전체 순이익과 지배주주 순이익 등 입력에 없는 지표를 대신 사용하지 않는다.
- 비교에 필요한 전년 ID가 빠졌어도 현재 ID가 이미 선택되어 있고 동일 기업·항목·기간·기준의 직접 비교 연결이 검증되면 그 전년 ID만 보완할 수 있다. 일치하는 금액을 전체 근거에서 찾아 붙이는 방식은 아니다. 기존 llm_refs와 보완 기록을 남기며 실패 응답의 부분 보완이 누적되지 않도록 사본을 검증한다.

비어 있지 않은 new2 문단에 재무·공시 근거가 모두 있는지도 확인한다. 추정 자료 사용 시 단서를 확인한다. mvp는 이 재무 검사를 진단으로 실행하고 결과가 맞지 않아도 경고만 남긴다. 자연어의 모든 수치 표현이나 산업 전체 일반화·인과관계를 완전히 검사하는 범용 언어 이해 기능은 아니다.

## 6. 토큰·재시도·병렬 실행은 어떻게 관리하는가

실제 요청 직전에 지침·자료·응답 스키마까지 포함한 토큰 수를 계산하고 캐시로 재사용한다. 기본 자체 예산은 TPM 225,000, RPM 10이며 환경에 맞춰 조정할 수 있다. 서비스 예산이 Google 계정 전체의 다른 작업 사용량까지 알지는 못한다.

요청 하나가 예산을 초과하면 대기로 해결할 수 없다. 현재 경로는 오류를 반환하며 자동 재청킹하지 않는다. 일시적인 408·429·500·502·503·504나 통신 오류는 제한된 재시도를 수행한다. 응답 형식·검증 실패에는 진단을 주어 한 차례 교정할 수 있다. 정상 종료 여부·빈 후보·정책 차단도 구별한다.

`generation.generate_all()`은 산업·기업 인사이트와 키워드 설명을 기본 최대 4개씩 진행한다. 같은 분석 내 financial/search/select_evidence 조회와 전체 무결성 검증을 재사용한다. Gemini에는 공통 예산을 적용한다. 응답이 늦으면 30초마다 완료 수와 처리 중 작업 수를 출력하여 대기 상태를 알린다.

## 7. 실패하면 무엇을 저장하는가

mvp에서 개별 산업·기업 설명의 RuntimeError·ValueError·OSError는 설명 준비 실패 안내와 빈 문장 목록으로 격리하고 나머지 그래프·설명 처리를 이어갈 수 있다. DB 연결이나 보고서 준비 단계의 모든 오류를 무시한다는 뜻은 아니다. strict에서는 주요 인사이트 예외가 발생하면 불완전한 새 완성 보고서를 발행하지 않는다. 키워드 실패는 기존 fallback 정책을 사용한다.

교정 후에도 실패하면 해당 모드의 처리 정책을 따른다. 실험용 문장 수·점수 완화가 기존 성공 보고서를 즉시 덮어쓰는 것은 아니다. 전체 보고서 생성·데이터 지문 확인을 완료한 뒤에만 publish_report가 호출된다. mvp의 완성 보고서에는 일부 AI 설명 대신 안내가 들어갈 수 있다.

직전 대화에서 제안한 “100자 미만 또는 공통 근거 부족일 때 산업·기업 탐색 문구로 교체”는 **아직 구현되지 않았다**. 현재는 생성 예외나 빈 문장 결과의 부족 이유를 표시한다. 단순 길이 기준이나 공통성 판단으로 성공한 AI 문장을 교체하는 기능과는 다르다.

## 8. 각주·캐시·화면의 경계

코드는 선택 문장 ID를 원래 청크의 시작·끝 위치로 변환하고 화면용 text·source_refs를 만든다. new2의 재무 ID는 내부 수치 검증에 남지만 고객 각주에는 넣지 않는다. 재무만 설명한 문장에는 각주가 없을 수 있고 관련 없는 공시 각주를 억지로 붙이지 않는다. 그래프의 원문 출처 기능은 별도다.

개별 LLM 캐시는 입력·프롬프트·검증 버전·모델·스키마와 validation_mode로 구분한다. 모드를 바꾼 뒤 이미 발행된 완성 보고서를 조회하기만 하면 설명이 재검증·재생성되는 것은 아니다. 새 모드 결과가 필요하면 분석을 실행해야 한다.

완성 보고서는 섹터별 new·new2·old의 마지막 성공 결과를 보관한다. 분석 --prompt-version과 화면 REPORT_PROMPT_VERSION은 독립적이다. 다른 버전의 결과를 자동 대체하지 않는다. 보고서 지문과 현재 DB 조건이 다르면 재분석이 필요하다. --llm은 유효한 개별 캐시를 재사용하고 --refresh-llm은 다시 생성한다.

지원 종료된 프롬프트 결과는 new 결과로 잘못 분류하지 않는다. 기존 분석 산출물은 자동 삭제하지 않으며 현재 지원하는 버전으로 다시 생성하면 된다. 전달받은 정의서 원본 자료도 실행 코드와 구별하여 보존한다.

## 실행 예시

```powershell
# 기본 mvp로 new2 분석
python -X utf8 -m snapdart.analyze --llm --prompt-version new2

# 정밀 검사 모드로 생성하려면
$env:INSIGHT_VALIDATION_MODE = "strict"
python -X utf8 -m snapdart.analyze --llm --prompt-version new2

# 저장한 결과를 조회
python -X utf8 app.py --prompt-version new2 --ui-version new
```

배포에서는 `.env`의 INSIGHT_VALIDATION_MODE와 REPORT_PROMPT_VERSION을 설정한다. 코드 교체 후 docker compose build app, 필요한 분석 실행, docker compose up -d --force-recreate app 순서로 반영한다. 환경변수나 문서 수정만으로 이미 실행 중인 프로세스가 바뀌지는 않는다. [Python argparse 공식 설명](https://docs.python.org/3.12/howto/argparse.html)의 choices 방식처럼 지원하지 않는 --prompt-version은 실행 전에 거부한다.
