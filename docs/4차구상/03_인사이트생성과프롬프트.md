# 03. 인사이트 생성과 프롬프트

[문서 목록](README.md) · [앞: 공시 검색](02_공시검색과벡터검증.md) · 기준: 2026-10-08

## 이 문서에서는 무엇을 알아보는가

검색 단계가 끝났다고 해서 화면 설명이 바로 완성되는 것은 아니다. 검색 결과는 “관련 있어 보이는 원문”이고, 화면에 필요한 것은 “그 원문이 말하는 사업 상황을 짧고 이해하기 쉽게 설명한 문장”이다. 이번에는 원문을 Gemini에 전달하고, 결과를 검사하여 각주가 붙은 설명으로 저장하는 과정을 알아본다.

앞 문서의 가상 A기업 문장을 계속 사용한다. “서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.”라는 원문을 찾았다고 하자. 이 원문으로 설명할 수 있는 것은 수요 대응을 위한 생산능력 확대 **계획**이다. 확대가 완료되었다거나, 그 결과 매출이 늘었다고 단정하면 입력 자료보다 더 많은 사실을 만들어낸 것이다. 현재 생성 과정은 이러한 차이를 지키도록 설계되어 있다.

## 첫째, Gemini가 읽을 자료 묶음을 만든다

Gemini에 자료를 보내는 주체는 Python 코드다. Gemini가 DB에 직접 접속하는 방식은 아니다. 코드는 DB에서 꺼낸 재무 수치, 검색한 공시 문장, 산업·기업·시점 정보를 정리하여 요청에 넣는다. 따라서 “DB 검색을 잘하는 것”과 “Gemini가 설명을 잘 쓰는 것”은 서로 다른 단계다.

재무 수치는 사업 변화의 규모를 이해하는 보조 자료다. 코드가 계산한 연간 변화율과 비율, 최신 분석 연도의 분기·반기 누적 수치를 기준 정보와 함께 전달한다. 화면 그래프의 계산을 Gemini에 맡기지는 않는다. 현재 섹터별 4슬롯 산식은 별도의 Python 화면 계층에서 계산한다. 은행 그래프용 승인 계정이나 R&D 추가 조회가 곧바로 같은 형태의 LLM 입력 추가를 의미하지는 않는다. 이번 그래프 변경에서는 기존 인사이트 생성 프롬프트·근거 문장 선정 규칙을 유지했다. 예를 들어 코드가 계산한 매출과 영업이익률을 참고하여 사업 설명을 쓸 수는 있지만, Gemini가 추정한 숫자로 그래프를 새로 그리지 않는다.

공시 검색 결과에서는 설명 문장으로 사용할 자연어 부분을 다시 고른다. 현재 규칙은 표 형태와 독립적인 수치가 들어간 문장을 보수적으로 제외한다. 숫자를 정확한 단위·기간으로 다루는 경로와, 자연어를 인용하는 경로를 나누려는 것이다. 이 때문에 숫자가 포함된 유용한 문장도 인용 후보에서 빠질 수 있다.

내부에서는 원래 청크와 문장의 위치를 보관하지만, 실제 Gemini 요청에는 자연어 문장 목록이 있는 공시 항목의 전체 청크 본문을 제거한다. 사업보고서 전체를 그대로 한 번에 보내는 방식이 아니다. 저장된 벡터도 Gemini에 보내지 않는다. 벡터는 앞 단계의 검색에 쓰이고, Gemini는 검색 후 고른 문장을 읽는다.

## 둘째, 자료를 다시 가리킬 수 있는 이름표를 붙인다

Gemini가 “첫 번째 문단을 근거로 사용했다”고 말해도 정확히 어떤 자료인지 알아낼 수 있어야 한다. 그래서 코드가 입력 자료에 임시 ID를 붙인다. ID는 자료를 구별하는 이름표라고 이해하면 된다.

공시 입력에는 `t1`, `t2` 같은 이름표가 붙는다. 그 안의 첫 번째 인용 가능 문장에는 `t1-p1`처럼 이름표가 붙는다. 재무 입력은 `f1`처럼 다른 이름표로 구별한다. 이 임시 ID들은 한 번의 요청 안에서 자료를 가리키는 용도이며, DB에 저장된 고유 청크 ID와는 다르다.

A기업의 예시 원문이 첫 문장이라면 코드가 본문 안의 시작·끝 위치까지 함께 보관한다. Gemini에게 위치를 새로 추측하게 하지 않는다. 모델은 이미 주어진 문장 ID를 선택하고, 코드는 그 ID가 실제 어느 원문 부분인지 알고 있다.

현재 화면 인사이트의 공개 각주는 공시 입력에만 연결한다. 재무 수치가 분석의 보조 자료로 전달되더라도 그 재무 행을 자연어 공시 인용인 것처럼 붙이지 않는다. 그래프의 수치 출처를 보여주는 기능은 [05. 재무 지표와 원문 출처](05_재무지표와원문출처.md)의 별도 경로다.

## 셋째, 자료와 함께 글쓰기 지침을 전달한다

모델에게 어떤 역할과 제한을 따르도록 보내는 지침을 프롬프트라고 한다. 현재 프롬프트는 세 부분으로 합쳐진다. 모든 설명에 적용하는 공통 원칙, 산업·기업·키워드 중 해당 기능의 글쓰기 원칙, 문장에 연결할 공시 근거를 고르는 원칙이다.

공통 원칙은 입력 밖의 기업 사실과 전망을 만들지 말고, 시점과 계획·진행·완료를 구별하며, 쉬운 한국어로 쓰도록 한다. 산업 설명은 공통된 사업 방향을 우선하되 자료가 일부 기업에 한정되면 그 범위를 밝혀야 한다. 기업 설명은 선택 기업의 상황을 다룬다. 키워드 설명은 용어의 뜻에 더해 그 용어와 관련하여 공시에서 확인되는 사업 상황을 전달해야 한다.

따라서 가상의 A기업 원문으로는 “A기업은 서버용 제품 수요에 대응하기 위해 생산능력 확대를 계획하고 있습니다.”처럼 쓸 수 있다. 다른 기업의 자료 없이 “산업 전체가 증설을 완료했습니다.”라고 확대해서는 안 된다. “기업마다 기준이 다릅니다” 같은 막연한 말만으로 설명을 채우지 않도록 하는 지침도 들어 있다.

현재 기본 버전은 산업·기업 설명을 1-3문장, 키워드 설명을 1-2문장으로 제한한다. 자료가 부족하면 부족한 이유와 빈 문장 목록을 반환할 수 있다. 문장을 반드시 채우기 위해 내용을 만들어내는 것보다 설명을 보류하는 결과를 허용한다. 이전 프롬프트를 선택하는 기능도 있으나, 검색과 숫자 처리까지 과거 시스템으로 바꾸는 기능은 아니다.

## 넷째, 요청 크기를 확인하고 필요하면 기다린다

모델은 글자를 그대로 세어 사용량을 계산하지 않는다. 문장을 처리하기 위해 나누는 단위를 토큰이라고 하며, 한 글자와 한 토큰이 항상 대응하지는 않는다. 그래서 글자 수 제한과 토큰 수 제한은 서로 다른 관리 장치다.

코드는 먼저 공시 입력 후보를 글자 수 예산 안에서 고른다. 이어 실제 요청 직전에는 Gemini의 토큰 계산 기능으로 지침·자료·응답 형식을 포함한 전체 입력 크기를 확인한다. 여러 요청을 동시에 시작하더라도 최근 1분간 입력 토큰 수와 요청 수에 대한 자체 한도를 적용한다.

1분 동안 여러 요청을 보내서 한도를 넘는 경우에는 기다린 뒤 보낼 수 있다. 그러나 요청 하나가 자체 토큰 예산보다 큰 경우에는 기다려도 작아지지 않는다. 현재 경로는 그 오류를 내며, 자동으로 다시 청킹하여 계속 진행하지 않는다. 이 경우에는 자료 선정 예산과 실제 계정 한도를 살펴봐야 한다.

일시적인 통신 오류와 사용량 제한에는 정해진 횟수만큼 재시도한다. 키나 권한이 잘못된 경우에는 같은 요청을 반복하지 않는다. 이 제어는 Gemini 계정 전체의 다른 프로그램 사용량까지 완전히 알 수 있는 기능은 아니다.

## 다섯째, 설명과 근거 평가를 함께 돌려받는다

Gemini는 완성 문장만 돌려주지 않는다. 문장, 사용한 자료 ID, 근거가 얼마나 적절한지에 대한 평가를 정해진 항목으로 반환한다. 이런 항목별 데이터를 표현하는 형식이 JSON이다. 화면용 문장과 프로그램이 검사할 정보를 한 응답에 나누어 담는 방식이라고 이해하면 된다.

근거 평가는 네 가지를 본다. 사실이 설명을 직접 뒷받침하는지, 초보자가 사업을 이해하는 데 도움이 되는지, 주체와 맥락이 명확한지, 시점과 계획·진행·완료가 맞는지다. 코드에서는 이 항목을 각각 F·U·C·T라고 부른다. 단어를 외우기보다 평가하려는 내용에 주목하면 된다.

Gemini는 각 항목에 0-4점 등급을 준다. 현재 기본 지침에서는 사실 부합도 40%, 이해 도움 30%, 명확성 20%, 시점 일치 10%를 반영하고, 불필요한 내용과 반복이 있으면 감점한다. 최종 점수는 Python 코드가 계산한다.

예를 들어 F=4, U=3, C=4, T=3이면 가중합을 100점 기준으로 바꾼 값은 90점이다. 불필요한 내용에 대한 감점 5점이 있으면 85점이 된다. 이 점수와 별개로 사실 부합도와 명확성이 각각 3 이상이고, 적합하다는 판단을 받아야 한다. 종합 점수만 높다고 근거를 모두 수용하지는 않는다.

여기서 모델이 내용의 적절성을 판단하고, 코드는 그 판단값을 정해진 산식과 조건에 적용한다. 코드가 사업 문장을 읽어 다시 독립적으로 같은 평가를 하는 것은 아니다. 생성과 근거 평가는 같은 Gemini 요청에서 이루어지므로, 다른 모델의 독립 심사를 받은 결과로 이해해서도 안 된다.

## 여섯째, 프로그램이 확인할 수 있는 조건을 검사한다

응답이 도착하면 코드는 먼저 JSON 형식과 필수 항목을 확인한다. 다음으로 근거 ID가 입력에 실제로 있었는지, 선택한 문장 ID가 그 공시 청크에 속하는지, 등급이 허용 범위 안에 있는지 검사한다. 모델이 새로 만든 문단 번호나 인용 문구를 그대로 받아들이지 않는다.

각 설명 문장에는 조건을 통과한 공시 청크가 최소 하나 있어야 한다. 수치가 서술되면 원 단위 금액 표현을 입력 자료와 대조하는 검사도 있다. 인용 위치는 모델의 출력 숫자를 쓰지 않고 코드가 미리 계산해 둔 위치를 사용한다.

이 검사로 잘못된 자료 연결과 형식 오류를 줄일 수 있다. 다만 모든 인과관계나 산업 전체 일반화가 참인지 프로그램이 완전히 증명하는 것은 아니다. 근거 문장과 설명의 사업 의미를 맞추는 데에는 여전히 모델의 판단이 관여한다. 프롬프트, 검색 범위, 원문 각주, 코드 검사를 함께 두는 이유다.

검증이 실패하면 오류 내용을 전달하여 한 번 수정하도록 요청한다. 수정 결과도 실패하면 해당 산업의 불완전한 새 보고서를 최종 결과로 저장하지 않고 기존 보고서를 보존한다. 반대로 자료 부족을 적절한 빈 응답으로 표현했다면 반드시 오류라는 뜻은 아니다.

## 마지막으로, 화면이 읽을 설명과 각주를 저장한다

모든 검사를 통과한 문장은 각주 ID와 연결하여 보고서 자료에 저장한다. 각주에는 원문 청크 ID, 기업·시점·목차, 실제 인용 문장과 위치가 연결된다. 브라우저는 이 저장 결과를 읽어 설명과 작은 각주 버튼을 표시한다.

같은 자료와 같은 프롬프트로 생성한 결과는 다시 사용할 수 있도록 캐시에 보관한다. 여러 산업·기업·키워드 설명 작업을 동시에 진행하더라도 조회 결과와 사용량 관리는 함께 적용된다. 캐시를 쓰는 것과 새 문장을 생성하는 것은 다르며, `--refresh-llm`은 생성 결과 캐시를 생략하도록 하는 옵션이다.

이 단계의 결과는 “검사를 거친 설명 문장 + 그 설명의 원문 연결 정보”다. 단어를 고르는 과정은 [04](04_공시신호워드클라우드.md), 각주를 눌렀을 때 원문을 보여주는 과정은 [05](05_재무지표와원문출처.md), 화면에 출력하는 과정은 [06](06_시세수집과화면.md)에서 이어진다.

## 구현 상세: 파일과 정확한 처리 기준

앞부분의 흐름을 이해한 뒤 필요한 항목을 찾아 읽는 참고 영역이다. 처음 읽을 때 모든 함수명과 설정값을 외울 필요는 없다.

### 구현 의도: 사업 흐름을 설명하면서 근거 범위를 넘지 않는다

화면 설명은 검색 문구를 많이 나열하는 요약보다 “어떤 사업 활동이 어떤 방향으로 움직이는가”를 쉽게 전달해야 한다. 그러나 잘 읽히는 문장을 만들기 위해 기업의 계획을 성과로 바꾸거나, 한 기업의 활동을 산업 전체로 일반화하면 안 된다. 현재 프롬프트는 근거 일치 → 사업 이해에 중요한 내용 선택 → 쉬운 표현 순으로 판단하도록 한다.

형식과 근거 연결은 프롬프트만으로 맡기지 않는다. Gemini가 JSON으로 문장·근거·평가를 반환하면 코드가 허용 ID와 문장 위치, 점수 조건 등을 확인한다. 자연어 의미 판단은 모델, 숫자 계산과 자료 연결은 코드가 담당한다.

### Gemini에 실제로 들어가는 내용

#### 재무 자료

기업별 선택 기간의 연간 매출·영업이익·CAPEX·영업활동현금흐름, 코드가 계산한 변화율·영업이익률·FCF를 전달한다. 최신 분석 연도의 Q1·H1·Q3 누적 수치도 함께 넣는다. 연간·누적·연결/별도 기준을 명시한다.

이 자료는 사업 변화의 규모와 재무 흐름을 설명하는 보조 근거다. 모델이 화면의 분기 비율을 계산하도록 맡기지 않는다. 수치 입력 ID는 `fN`, 공시 청크는 `tN`으로 구분한다. 현재 공개 인사이트의 `refs`와 근거 평가 ID에는 공시 `tN`만 허용하므로 재무 행을 자연어 공시인 것처럼 각주로 붙이지 않는다.

#### 공시 자료

산업·기업 인사이트는 기간별로 선정한 검색 청크, 키워드 설명은 최신 연도 사업 내용 검색 결과를 사용한다. 이어서 다음 제한을 적용한다.

1. 본문을 줄바꿈과 문장 종결 부호로 나누고, 자연어 설명으로 사용할 문장을 찾는다.
2. 숫자·금액·표 형태가 섞인 문장을 근거 후보에서 제외한다. 기술명 `HBM3`의 숫자와 독립적인 숫자는 구별한다.
3. 원문 위치를 유지한 `text`, `start`, `end`와 문장 ID를 만든다.
4. 최신 FY → 과거 FY → 분기/반기 순으로 우선하되 기업별로 번갈아 담는다.
5. `CITATION_INPUT_CHAR_BUDGET` 기본 48,000자 안에서 청크 단위로 선택한다. 계산 기준은 원래 청크 전체 길이다. 청크 중간을 임의로 잘라 넣지 않는다.

자연어 판정은 최소 20자, 한글 설명의 길이·종결 형태 또는 영어 문장 조건, 숫자·표 구분 패턴을 사용하는 규칙이다. 완전한 언어 이해 필터가 아니며, 수치가 들어간 유용한 사업 설명도 제외할 수 있다. 정확한 단위·기준을 읽는 수치 입력과 문장 각주를 구분하기 위한 보수적인 정책이다.

#### 내부에서 보존하는 자료와 전송 자료의 차이

파이프라인 내부 `evidence`에는 원래 청크 본문과 그 안의 자연어 문장들이 있다. 하지만 실제 요청 직전 `llm.model_context()`가 `passages`를 가진 공시 항목의 **전체 `text`를 제거**한다. Gemini에는 기업·연도·목차·청크 ID와 자연어 문장 목록이 전달된다. 로컬 경로·일부 내부 연결 ID도 제거하고 벡터·API 키는 넣지 않는다.

따라서 “검색된 원문 청크를 내부에서 보존한다”와 “그 청크 전체를 Gemini에 보낸다”는 다른 말이다. 저장 입력 스냅샷도 실제 요청을 그대로 복사한 파일이 아니라 원문 연결을 확인하기 위한 내부 근거 기록이다.

가상의 공시 입력은 아래처럼 이해할 수 있다. ID와 본문은 설명용이며 실제 공시가 아니다.

```json
{
  "id": "t1",
  "kind": "filing",
  "chunk_id": "chunk-example",
  "company": "A기업",
  "year": 2025,
  "period": "2025-12",
  "section": "II. 사업의 내용",
  "heading": "생산능력",
  "passages": [
    {
      "id": "t1-p1",
      "text": "서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.",
      "start": 0,
      "end": 35
    }
  ]
}
```

`start`·`end`는 코드가 원문 문자열에서 계산한다. 이 예시의 문장은 35자이며 끝 위치는 해당 문장 다음 위치를 뜻한다. 임시 ID는 요청마다 새로 부여하므로 `t1`을 DB 고유 청크 ID로 사용해서는 안 된다.

### 프롬프트는 어떻게 결합되는가

기본 버전은 `new`, 식별자는 `bigin-user-2026-10-10-v4-single-keyword`이다. 기존 단일 생성 프롬프트는 유지한다. `--prompt-version new2`는 아래의 두 단계 생성, `--prompt-version old`는 이전 지침을 선택한다. 최종 작성 단계의 시스템 지침은 다음 결합이다.

```text
COMMON 공통 지침
+ 해당 기능의 INSIGHT / COMPANY / KEYWORD 지침
+ new2 선택 시 정리된 사실의 중요도를 판단하는 작성 지침
+ 선택 버전의 문장별 근거 선정 지침
+ 선택된 근거 평가만 반환하도록 하는 출력 지침
```

| 지침 | 핵심 내용 |
| --- | --- |
| 공통 | 입력 밖 기업 사실·수치·전망 금지, 시점·재무 기준 구분, 인과관계 창작 금지, 쉬운 한국어 |
| 산업 | 공통 사업 요인·방향을 우선하고 근거가 제한적이면 사업군·기업 범위로 좁힘 |
| 기업 | 선택 기업의 제품·고객·생산·투자·위험 중 핵심을 설명, 산업 상황을 그대로 대입하지 않음 |
| 키워드 | 용어 뜻과 관련 사업 현황을 함께 설명, 회계 분류 차이나 막연한 차이로 문장을 채우지 않음 |
| 근거 선정 | 공시 자연어 문장에 한정해 사실·이해 도움·명확성·시점을 평가하고 적격 근거 연결 |

산업·기업은 1-3문장, 키워드는 1-2문장이다. 근거가 부족하면 `sentences=[]`와 `insufficient_reason`을 반환한다. 정해진 항목을 채우기 위해 기회·위험·과거·미래를 모두 나열하도록 요구하지 않는다.

현재 정의서 원문은 [프롬프트_정의서_수정.txt](프롬프트_정의서_수정.txt), 실행 원문은 `prompts.py`와 `citation_selection.py`다. TXT가 런타임 입력 파일인 것은 아니다. 테스트가 상수와 정의서 일치를 검사한다.

`old`는 이전 문체·내용 지침과 F 50%·U 20% 평가를 보존한다. 기업 문장 수 상한도 현재 `new`와 다르다. 모델·검색·수치 처리까지 과거 전체 시스템으로 되돌리는 기능은 아니다. 원문 위치 후보 평가에는 현재 공통 선정 기준을 사용한다. CLI는 생략 시 `new`를 명시적으로 적용하므로 환경변수만 `old`로 설정해도 CLI 기본 옵션이 우선할 수 있다. 분석 명령에서는 `--prompt-version old`를 사용한다.

### 문장별 근거는 누가 어떻게 평가하는가

Gemini는 문장별 후보 청크에 0-4 정수 등급을 준다. 한 청크에서 여러 문장을 선택해도 근거 청크 하나로 평가한다.

| 항목 | 의미 | 현재 비중 |
| --- | --- | --- |
| F | 문장 주장의 주체·행위·방향·조건을 직접 뒷받침하는 사실 부합도 | 40% |
| U | 초보자가 실제 사업 현황·방향을 이해하는 데 도움이 되는 정도 | 30% |
| C | 주체·제품·조건과 맥락이 명확한 정도 | 20% |
| T | 시점과 현황·계획·진행·완료가 맞는 정도 | 10% |

관련 없는 내용과 반복은 각각 `none=0`, `some=5`, `substantial=10`점 감점이다. 코드가 계산하는 공식은 다음과 같다.

```text
점수 = max(0, 25 × (0.4F + 0.3U + 0.2C + 0.1T)
                 - 관련 없는 내용 감점 - 반복 감점)
적격 = suitable가 참이고 F ≥ 3, C ≥ 3, 점수 ≥ 75
```

예를 들어 F=4, U=3, C=4, T=3이고 관련 없는 내용 감점 5, 반복 감점 0이면 기본 90점에서 5점을 빼 85점이다. F·C 조건과 `suitable`까지 충족하면 사용할 수 있다. 점수가 높아도 F=2인 근거는 거절한다.

Gemini가 각 등급·적합 여부·이유를 판단한다. Python은 등급 범위와 가중합·감점·수용 조건을 계산한다. 코드가 사업 의미를 다시 읽어 독립적으로 F·U를 매기는 구조는 아니다. 생성 모델과 평가 모델도 같은 요청의 Gemini이므로 독립적인 두 번째 심사자가 있는 것처럼 해석하지 않는다.

### 반환 JSON과 검증 순서

설명 문장에는 `text`, `refs`, `assessments`가 있고, 전체 응답에 `sentences`, `insufficient_reason`이 있다. 평가에는 허용 청크 ID, 등급, 적합 여부, 감점 분류, 이유, `passage_ids`가 들어간다. 자연어 근거 ID의 허용 목록을 JSON Schema에 넣는다.

1. 응답이 JSON인지, 필요한 필드와 문장 수가 맞는지 확인한다.
2. `refs`·평가 ID가 입력 공시 청크 목록에 있는지 검사한다.
3. 선택 문장 ID가 해당 청크 안의 문장인지 확인한다. 모델이 만든 인용 문구나 위치 숫자를 그대로 믿지 않는다.
4. 등급·감점으로 점수를 계산하고 적격 조건을 적용한다.
5. 각 설명 문장에 적격 공시 청크가 최소 1개 연결됐는지 확인한다. 필요하면 여러 근거를 허용한다.
6. 원 단위 금액 표현이 나오면 기업·연도·보고서·회계 기준·재무 항목을 확인하고 해당 입력 수치와 반올림 허용 범위에서 검사한다. 다른 연도나 다른 항목의 같은 금액으로 통과시키지 않는다.
7. 선택한 문장의 원래 `start`·`end`를 저장 각주로 변환한다.

근거 부족을 올바른 빈 응답으로 반환하면 정상 결과다. 잘못된 ID·등급·구조는 검증 실패다. 같은 청크의 여러 문장을 인용하면 화면 각주 수가 근거 청크 수보다 많을 수 있다.

모든 후보의 평가를 강제하거나, 최종 선택이 전체 후보 중 최고 점수인지 검사하지 않는다. T의 별도 최소 등급도 없다. 산업 공통 흐름에 여러 기업 근거가 필요한 원칙은 프롬프트로 요구하지만 코드가 기업 수·인과관계·계획 해석을 모두 의미적으로 증명하지는 않는다. 금액 검사도 계정·기간별 완전한 회계 대사가 아니며 백분율·모든 자연어 숫자를 검증하는 기능은 아니다.

Google의 구조화 출력은 JSON 형식을 맞추는 장치이고 의미 정확성을 보장하지 않는다. 그래서 별도의 코드 검증을 둔다. [Gemini 공식 구조화 출력 안내](https://ai.google.dev/gemini-api/docs/structured-output).

### 요청 크기·대기·재시도는 어떻게 관리하는가

현재 생성은 Gemini REST `countTokens`와 `generateContent`를 사용한다. 기본 모델 이름은 `gemini-3.5-flash-lite`, 생성 온도는 1.0, 기능별 요청의 최대 출력은 8,192토큰이다. 출력에는 짧은 고객 문장 외에 근거 평가 JSON도 포함되므로 8,192가 고객 문장의 길이라는 뜻은 아니다. 실제 모델 사용 권한·계정 한도는 운영 환경에서 확인해야 한다.

`countTokens`는 공시뿐 아니라 시스템 지침·사용자 자료·응답 스키마를 포함한 요청을 센다. 동일 요청 토큰 수는 프로세스에서 최대 256개 재사용한다. 전송 전 다음 안전 예약량을 적용한다.

```text
예약량 = int(입력 토큰 수 × 1.05) + 1,024
기본 자체 한도: TPM 225,000 / RPM 10
```

로컬은 최근 60초 요청의 예약량과 개수를 잠금으로 관리한다. 초과하면 기다린다. 단일 요청 예약량 자체가 TPM보다 크면 대기로 해결되지 않으므로 오류를 낸다. 현재 경로는 그 오류 후 입력을 자동으로 재청킹해 재귀 분할하지 않는다. 자료 선정 예산과 실제 계정 한도를 조정해야 한다.

HTTP 408·429·500·502·503·504와 일시적인 통신 오류는 최대 3회 시도하며 지수 증가 대기와 작은 무작위 지연을 적용한다. 인증·권한 오류는 반복 호출하지 않는다. 생성 응답은 완료 상태와 일반 텍스트 부분을 확인하며 생각 과정용 부분은 출력 JSON으로 쓰지 않는다.

JSON·근거 검증 실패 시 원래 자료와 오류 정보를 넣어 **한 번의 수정 요청**을 허용한다. 수정 요청도 토큰 계산·예약을 거친다. 다시 실패하면 보고서 생성은 중단하고 기존 최종 보고서를 유지한다. 캐시나 진단 파일에는 업무 자료가 포함될 수 있으나 키를 저장하도록 만들지 않았다.

자체 예약은 공급자의 실제 한도를 대신하지 않는다. 다른 앱의 사용량·일일 한도·동시 프로젝트 사용은 별도로 영향을 줄 수 있다. [Gemini 공식 사용량 제한 안내](https://ai.google.dev/gemini-api/docs/rate-limits).

### 병렬 생성과 캐시를 함께 쓰는 이유

`generate_all()`은 최신 연도의 산업·기업 인사이트와 표시 키워드별 설명을 작업으로 만든다. 기본 동시 작업 4개, 허용 범위 1-4이며 `GEMINI_CONCURRENCY`로 설정한다. 병렬성은 API 대기 시간을 겹치기 위한 것이고 RPM·TPM 한도는 계속 적용된다.

같은 생성 실행에서는 `financial`, `search`, `select_evidence` 결과를 잠금으로 재사용한다. 작업마다 별도의 각주 사전을 만들고, 완료 결과를 부모 흐름이 병합한다. 같은 원문이 서로 다른 설명에 사용돼 평가 정보가 충돌하면 각주 ID에 구분 해시를 붙인다.

한 작업이 실패하면 대기 작업을 취소하고 해당 산업의 불완전한 새 보고서를 최종 저장하지 않는다. 이미 실행 중인 작업은 마무리될 수 있고 성공한 개별 생성 캐시는 남는다. 산업 전체 순회에서는 다른 산업의 성공 결과가 별도로 저장될 수 있다.

생성 캐시는 프롬프트 버전·근거 검증 버전·응답 검증 버전·출력 스키마·실제 지침·입력 문맥·provider·model의 해시로 구분한다. 기존 결과도 현재 입력으로 다시 검증한다. `--refresh-llm`은 이 결과 재사용을 생략한다. 벡터 캐시·워드클라우드 캐시까지 모두 초기화하는 옵션은 아니다.

### 각주로 변환한 뒤 화면에 전달하는 정보

검증된 `tN-pM`은 DB 청크 ID, 원문 quote, 문자 시작·끝, 기업·기간·목차, 접수번호, 요약 문장, 점수·선정 버전과 연결된다. 화면에는 문장과 저장 각주 ID만 공개한다. 등급·평가 이유는 내부 자료다. 원문 클릭 뒤 동작은 [05](05_재무지표와원문출처.md)을 따른다.

별도 `snapdart.query --llm`은 질문에 1-2문장으로 답하고 입력 ID를 검사하는 간단한 조회 도구다. 현재 화면 인사이트의 F/U/C/T 선정 절차와 동일한 검증 경로가 아니다. 이 명령의 답변을 화면 인사이트 수준의 각주 검증 결과로 취급하지 않는다.

## 문장 수 검증과 실패 진단 (2026-10-10 추가 요청 반영)

기본 new 프롬프트는 산업·기업 인사이트에서 적격 근거가 있는 **1-3문장**을 허용한다. 한 문장으로 충분하면 분량을 늘리지 않는다. 워드클라우드의 키워드 설명은 **1-2문장**이다. 한 문장이면 용어의 의미와 공시로 확인한 사업 현황을 함께 설명하고, 두 문장이 이해하기 쉬우면 두 내용을 나누어 설명한다. 사전적 정의만으로 채우지 않는다. 어느 기능이든 필요한 내용을 근거로 뒷받침할 수 없으면 `sentences=[]`와 비어 있지 않은 `insufficient_reason`을 반환할 수 있다. 0개 항목은 성공적으로 검증된 근거 부족 결과이지 분석 오류가 아니다.

문장 수는 마침표가 아니라 JSON `sentences` 배열의 항목 수로 센다. 각 항목에 요약 1문장을 작성하도록 지시한다. 코드가 한 항목의 문자열을 임의로 문장 분할하지는 않는다. 한 근거 청크가 여러 요약 문장을 뒷받침할 수 있지만 각각의 문장에 대한 적격 검증은 수행한다. 각주 근거 최소 1개, 자연어 20자 이상, suitable=True, F/C 각각 3점 이상, 최종 75점 이상과 원문 ID 검증은 바꾸지 않았다. 산업 전체로 과도하게 일반화하지 않는 원칙도 유지한다.

출력 스키마는 빈 배열 또는 허용 개수를 만족하는 배열을 `anyOf`로 명시한다. 빈 결과의 사유와 실제 근거 적격성은 응답을 받은 뒤 코드에서 다시 확인한다. 스키마에 개수를 명시한다고 내용의 타당성까지 보장되는 것은 아니다. 공식 참고: [Gemini 구조화된 출력](https://ai.google.dev/gemini-api/docs/structured-output).

검증 실패 시 한 번의 교정 요청에 실제 오류와 응답을 전달한다. 교정 지시는 항목 수와 근거 조건을 함께 지키도록 하며, 분량을 채우려고 반복하거나 사실을 만들지 못하게 한다. 키워드의 용어와 사업 현황을 설명할 적격 근거가 없으면 빈 배열과 구체적인 사유를 반환하도록 한다. 두 번째 검증도 실패하면 기존처럼 해당 섹터 보고서는 교체하지 않는다. 부분 성공 결과를 완성된 보고서처럼 게시하지 않는다.

로컬의 기존 진단 파일 저장을 보강하고 배포에도 같은 형식을 적용했다. `dart_remote/llm_diagnostics.py`가 섹터·기업·키워드·작업 종류, 실제 배열 항목 수, 허용 개수, 최초/교정 시도, 검증 오류, 모델 응답과 허용 근거 ID를 기록한다. 로그에는 작업과 오류를 표시하며 응답 전문은 출력하지 않는다. 기록은 서비스 결과 폴더 아래 `llm/llm_errors/<diagnostic_id>.json`에 저장한다. 기본 로컬 경로는 `data/service/remote/llm/llm_errors/`, 배포 Compose 기본 경로는 `/home/service/service_data/llm/llm_errors/`이고 `SERVICE_CACHE_DIR` 설정에 따라 바뀐다. 원격 MySQL에 쓰지 않으며 공개 HTTP 경로로 제공하지 않는다. 로그의 diagnostic_id와 파일명이 대응한다. 파일 저장이 불가능해도 교정 절차를 중단하지 않고 기록 실패 경고를 남긴다.

최대 4개 작업이 병렬 실행되므로 인접한 로그가 같은 작업을 뜻하지 않을 수 있다. 실패 기록의 섹터·기업·키워드로 구분해야 한다. 프로필 버전을 `bigin-user-2026-10-10-v4-single-keyword`로 올려 이전 생성 캐시와 구분한다. 기존 보고서 파일은 유지하며 새 기준을 화면에 반영하려면 분석을 다시 실행해야 한다. old 프로필은 그대로 유지한다.

## 키워드 설명의 한 문장 허용 (2026-10-10 최종 기준)

키워드 설명에서 문장 수를 정확히 2개로 강제하던 조건을 1-2개로 완화했다. 근거가 있는 한 문장으로 용어의 뜻과 공시의 사업 현황을 함께 전달할 수 있으면 그대로 사용한다. 두 문장으로 나누는 편이 이해하기 쉬울 때만 분리한다. 한 문장 허용은 사전적 정의만 제공해도 된다는 뜻이 아니다. 관련 사업 현황을 적격 공시 근거로 설명할 수 없으면 빈 결과와 부족 사유를 반환한다. 이 내용의 충실성은 프롬프트로 지시하고, 코드는 배열 개수와 기존 근거 적격 기준을 검증한다. 용어 해설과 사업 현황이 모두 포함됐는지 키워드 규칙으로 기계적으로 검사하는 별도 검증은 추가하지 않았다.

## LLM 반환값 처리 보완 (2026-10-10)

청크 ID와 문장 ID의 출력 구조, 연결 검사 방식은 그대로 유지한다. 아래 내용은 응답 처리와 재시도, 캐시 및 값 검증에 대한 보완이다. 문장 수는 산업·기업 1-3문장, 키워드 1-2문장 또는 근거 부족 사유를 동반한 빈 결과를 유지한다.

문장 항목·assessments·grades·refs·passage_ids 등의 자료형을 사용하기 전에 확인한다. null이나 잘못된 객체가 들어오면 AttributeError 대신 검증 오류로 기록하고 한 차례 교정한다. Gemini 후보·content·parts·text도 같은 방식으로 확인한다. HTTP 응답 자체의 JSON 해석 실패는 전송 오류로 보고 기존 공통 토큰 예약을 거쳐 최대 세 번까지 시도한다.

후보 비교와 근거 선정 기준은 유지한다. 추가 출력 지시는 최종 assessments에 refs로 선택한 근거의 평가만 담고 평가 이유를 짧게 작성하도록 요구한다. refs에 연결하지 않은 후보의 평가 상세는 출처 적격 검사와 고객용 각주에서 제외한다. 선택한 근거의 중복 ID·문장 ID·F/C 등급·점수·자연어 검증은 모두 유지한다. 형식조차 알 수 없는 평가 항목은 정상 응답으로 간주하지 않는다. 기존 근거 선정 지시문 자체는 바꾸지 않고 최종 출력 범위 지시를 추가했다.

근거 후보에서는 2025년, 2025년 10월 1일, 2025-10-01 등의 날짜를 문맥 정보로 허용한다. HBM3처럼 영문과 이어진 제품명도 기존처럼 허용한다. 원문을 고쳐 저장하거나 위치를 변경하지 않는다. 날짜 판별용 복사 문자열에서만 날짜를 제외하고 숫자를 검사한다. 금액·비율·수량·표·숫자 나열은 계속 제외한다. 모든 숫자나 제품 규격을 일반적으로 허용하는 규칙은 아니다.

MAX_TOKENS이면 잘린 응답을 성공으로 사용하지 않는다. 진단 파일에는 중간 응답을 보관하고, 교정 입력에서는 잘린 응답을 제외한다. 기존 출력 토큰 한도를 늘리지 않고 선택 근거의 평가만 제출하고 reason을 50자 이내로 줄이라는 추가 지시로 한 번 재시도한다. 일반 질문 조회는 해당 스키마에 맞는 간결한 JSON을 요구한다. 재시도도 RPM·TPM 공통 예산을 적용하며 다시 실패하면 기존 보고서를 보존한다. SAFETY·BLOCKLIST·PROHIBITED_CONTENT·SPII·RECITATION 등 알려진 정책/인용 제한은 같은 요청으로 재시도하지 않고 원인을 기록한 후 중단한다. 정책 우회나 안전 설정 변경을 하지 않는다. 응답 후보가 없고 차단 사유도 없는 경우 역시 진단을 남기고 중단한다. 종료 이유의 공식 정의는 [Gemini API 문서](https://ai.google.dev/api/generate-content)를 참고한다.

생성 캐시가 손상됐거나 현재 검증에 실패하면 그 요청의 캐시 파일만 제거하고 재생성한다. 다른 생성 캐시나 최종 보고서는 삭제하지 않는다. 새 캐시는 기존 원자적 저장으로 기록한다. 검증 버전과 스키마까지 캐시 해시에 포함하므로 코드의 검증 정책이 바뀐 결과를 이전 캐시와 구분할 수 있다. 기존 보고서는 전체 생성이 성공하기 전까지 유지한다.

금액 검사는 원 단위 표현에 적용한다. 금액 앞의 기업명·연도·보고서 기간·연결/별도 표현과 재무 항목을 읽고, 생략된 기업·연도·기간은 인용 공시의 범위에서 유일하게 확인되는 경우에만 사용한다. 후보 재무 자료의 회계 기준도 하나로 확인돼야 한다. 범위가 모호하거나 해당 수치가 없으면 교정을 요청한다. 매출액·영업이익/손실·CAPEX·영업활동현금흐름을 구분하며, 다른 항목이나 연도의 같은 숫자 및 공시 본문의 숫자 일치만으로 통과시키지 않는다. 반올림 허용은 유지하고 마이너스 및 영업손실 표현을 처리한다. 백분율·모든 수치·복잡한 복수 기간 비교까지 완전하게 해석하는 기능은 아니다. 불명확한 금액 설명을 통과시키기보다는 정성 설명으로 좁히도록 교정하는 보수적인 방식이다.

DB 및 실제 Gemini 호출 없이 가상 응답으로 검증한다. 공유 처리 코드는 dart_remote/response_validation.py이며 로컬·배포에 동일하게 적용한다.

## 2026-10-10: new2의 사실 정리와 인사이트 작성

`new` 또는 옵션 생략 시에는 기존 공통·산업·기업·키워드 프롬프트와 단일 생성 방식을 사용한다. `new2`는 같은 Gemini 모델에 서로 다른 지침으로 두 번 요청한다. 다른 모델을 설치하는 기능은 아니다. 기업·산업 인사이트와 워드 클라우드의 키워드 설명에 모두 적용하며, 일반 `snapdart.query`의 짧은 질문 답변은 이 보고서 생성 경로와 별개다.

첫 요청은 중요한 근거 사실을 산업에서 최대 10개, 기업 및 키워드에서 최대 5개 정리한다. 이는 목표 개수가 아니라 상한이며 근거가 적으면 더 적게 반환할 수 있다. 각 사실에는 설명 내용, 현황·계획·진행·완료 등의 실행 상태, 실제 입력 청크 및 원문 문장 ID를 연결한다. 기업명·보고서 기간·DB 청크 ID는 코드가 원래 입력에서 다시 붙인다. 모델이 원문 위치나 기업 메타데이터를 새로 만들게 하지 않는다.

이 단계의 검증은 형식·개수·허용 ID·자연어 원문 연결을 검사한다. 사실의 의미가 완벽히 증명됐다는 뜻은 아니다. 따라서 사실 정리 결과는 잠정 자료이며 최종 문장을 작성할 때 원문과 다시 대조한다. 첫 단계가 형식 검증에 실패하면 자동 교정 요청을 추가하지 않고 중단한다. 근거가 없다는 정상 결과라면 빈 문장과 부족 이유를 저장하고 두 번째 요청은 생략한다.

두 번째 요청은 전체 사실을 나열하지 않고 사업 이해에 중요한 정도와 근거의 직접성을 판단하여 핵심을 선택하거나 같은 흐름의 사실을 요약한다. 서로 다른 사실을 합치며 확인되지 않는 공통 원인·성과·전망을 만들지 않도록 지시한다. 화면 문장 수는 산업·기업 1-3문장, 키워드 1-2문장으로 유지한다. 최종 문장에는 기존 F/U/C/T 평가와 감점을 다시 적용하고, 사실 정리에서 선택되지 않은 원문을 각주로 붙이면 거부한다. 사용자 화면에는 중간 사실 목록이나 평가 점수가 아니라 기존 형식의 문장과 원문 각주가 전달된다.

`insight_plan.py`가 사실 정리 지침·스키마·ID 검사·최종 근거 범위 검사를 담당하고, `prompts_new2.py`가 기존 new 지침에 작성 단계 지침을 결합한다. `pipeline.generate()`가 두 요청과 캐시를 연결한다. 사실 정리와 완성 결과는 별도 캐시에 저장한다. 완성 캐시가 있으면 두 요청 모두 생략하고 검증 후 재사용한다. 최종 작성만 실패한 뒤 재실행하면 정상 사실 정리 캐시는 재사용할 수 있다. `--refresh-llm`은 두 캐시 모두 재사용하지 않는다.

정상 생성은 최대 두 요청, 최종 작성의 검증 교정까지는 최대 세 요청이다. HTTP 429·503 등 일시적인 통신 오류의 기존 재시도는 별도이며 각 요청 모두 공유 RPM·TPM 한도를 적용한다. 요청 단계가 늘어 생성 시간과 사용량은 증가할 수 있다. `new`·`new2`·`old`는 캐시를 구분하지만 화면 보고서는 마지막으로 전체 생성에 성공한 결과 하나를 표시한다.

## 2026-10-10: 구체적인 오류를 이용한 교정과 문맥 보충

현재 new/new2 근거 검증 버전은 `claim-evidence-v6-detailed-errors`다. 점수 계산과 F≥3·C≥3·최종 점수≥75 기준은 유지한다. 오류에는 해당 문장 번호, 선택 근거 ID, 모델이 제출한 등급, 코드 계산 점수, 미달 조건을 넣는다. 선택한 근거의 평가가 빠진 오류와 실제 점수가 부족한 오류를 구분한다. 여러 문장의 부적격 평가를 모아 전달할 수 있으며 형식이 잘못되어 계산할 수 없는 응답은 우선 형식 오류로 처리한다. 금액 검증 오류에도 해당 문장 번호를 기록한다.

교정 지침은 등급만 높여 통과시키지 말고 문장을 원문 범위로 좁히거나 더 직접적인 원문을 선택하도록 요구한다. 부적격 근거를 지울 때는 남은 근거가 모든 주요 주장을 뒷받침해야 한다. 최종 교정도 실패하면 기존 보고서를 보존한다. 상세 정보는 비공개 진단 JSON의 `issues`에 저장하고 각 단계·프롬프트 버전·사실 개수도 기록한다.

new/new2는 인용 가능한 자연어 문장 앞뒤에서 각각 최대 120자의 원문 문맥을 추가한다. 보충 문맥의 기본 총량은 4,000자이고 `CITATION_CONTEXT_CHAR_BUDGET`으로 0-8,000자 범위에서 조절한다. 보충 내용은 이해용이며 새로운 각주 ID가 아니다. 각주 문장·시작 위치·끝 위치는 기존 원문 그대로 유지하고, 문맥만으로 새 주장을 만드는 것을 금지한다. 모델 요청에는 여전히 전체 보고서나 청크 전체 본문을 넣지 않는다.

키워드 설명은 최신 연도의 최초 검색을 유지하되, 같은 기업·같은 키워드·같은 보고서 종류의 이전 분석 연도 자료를 최대 4개 검색 범위에서 각 1개 추가한다. 분석 연도에 공백이 있으면 직전 달력 연도가 아니라 이전에 선택된 분석 연도가 된다. 본문 후보 48,000자 예산과 기업별 분산 선정이 다시 적용되므로 모든 추가 자료가 실제 요청에 포함된다고 보장하지 않는다. 관련 검색 결과라는 이유만으로 증가·감소의 증거로 취급하지 않으며, 비교 근거가 부족하면 현재 현황으로 설명을 제한한다. 산업·기업 인사이트는 기존의 연도별 근거 선정과 이전 연도 자료를 유지한다. old의 자료 선정은 보존한다.

관련 회귀 검증은 `tests/test_new2_insights.py`, `tests/test_llm_diagnostics.py`, `tests/test_current_llm.py`, `tests/test_deploy_parity.py`에 있다. DB·실제 Gemini 없이 모의 자료로 경로·ID·개수·오류·캐시를 검증한다. 테스트 통과는 실제 문장의 의미 정확성이나 품질 향상 폭을 측정한 결과는 아니다.


## 화면에 표시할 프롬프트 버전 선택

분석 생성 옵션 `--prompt-version`과 화면 표시 설정 `REPORT_PROMPT_VERSION`은 독립적입니다. 기본 표시 버전은 `new`입니다. 분석 전체와 데이터 버전 검증이 성공한 후에만 섹터별 `report/prompt-new.json`, `report/prompt-new2.json`, `report/prompt-old.json`을 갱신합니다. 기존 `report/current.json`도 호환성을 위해 유지합니다. DB 스키마, 검색, 프롬프트, 화면의 응답 구조는 변경하지 않습니다. 각 보고서의 문장과 각주 근거는 함께 저장됩니다.

기존 `llm` 폴더의 개별 응답 캐시는 그대로 재사용합니다. 과거에 덮어써진 완성 보고서는 개별 캐시만으로 앱 시작 시 자동 조립하지 않습니다. 필요한 버전으로 분석을 한 번 실행하면 유효한 캐시를 재사용하여 완성 보고서를 저장합니다. 누락되거나 현재 입력·검증 규칙에 맞지 않는 캐시는 기존 정책대로 다시 생성됩니다. 이때 `--refresh-llm`을 지정하면 캐시를 강제로 다시 생성하므로 재사용 목적이라면 지정하지 않습니다.

기존 완성 보고서는 인사이트에 기록된 프롬프트 버전이 명확하게 일치할 때만 읽습니다. 이후 분석을 실행할 때 기존 완성 보고서도 해당 버전의 저장 공간이 비어 있다면 보존합니다. 이미 덮어써져 없는 과거 보고서를 복구하지는 않습니다. 요청 버전의 보고서가 없으면 그 섹터는 분석 결과 없음으로 처리하며 다른 버전으로 대체하지 않습니다. 기존 데이터 지문 검사도 유지하므로 DB가 바뀌었다면 분석을 다시 수행해야 합니다. LLM 없이 만든 공시 발췌 보고서는 버전별 성공 AI 보고서를 덮어쓰지 않습니다.

로컬 실행 예시:

```powershell
python -X utf8 app.py --prompt-version new2
```

배포 환경에서는 `deploy/.env`에 다음 값을 설정한 뒤 앱 컨테이너를 다시 생성합니다. 이미 실행 중인 앱의 환경설정은 재시작 과정에서 적용합니다.

```dotenv
REPORT_PROMPT_VERSION=new2
```

```bash
docker compose up -d --force-recreate app
```

코드 변경을 처음 반영할 때는 `docker compose build app`으로 이미지를 먼저 다시 빌드합니다. 분석 생성은 기존과 같이 `python -m snapdart.analyze --llm --prompt-version new2` 또는 `docker compose run --rm app python -m cloudapp.cli build --llm --prompt-version new2`로 실행합니다. 선택 버전은 산업·기업·워드 클라우드·각주 조회·홈 화면의 보고서 준비 상태에 일관되게 적용됩니다. 시세 캐시는 버전 간 공용입니다.
