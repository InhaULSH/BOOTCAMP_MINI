# 05. 재무 지표와 원문 출처

[문서 목록](README.md) · 기준: 2026-10-08

## 이 문서에서는 무엇을 알아보는가

서비스는 사업 설명과 함께 매출·이익·투자·현금흐름을 그래프로 보여준다. 사용자가 수치를 눌렀을 때는 그 숫자가 어디에서 왔는지 확인할 수 있어야 한다. AI 설명의 각주도 원래 공시 문장까지 이어져야 한다. 이번에는 **숫자를 만드는 과정**과 **그 숫자·문장의 출처를 되짚는 과정**을 나누어 살펴본다.

숫자 계산과 문장 작성의 담당자는 다르다. 현재 화면의 지표 계산은 Python 백엔드가 정해진 산식으로 수행하며, 브라우저는 계산 결과를 그린다. Gemini는 전달받은 자료로 사업 상황을 설명한다. AI가 매출액을 추정해서 그래프 값을 채우는 구조가 아니다.

## 첫째, 같은 이름의 숫자라도 기준이 같은지 확인한다

매출액이라는 항목을 찾았더라도 어느 기업의 어느 기간을 뜻하는지 확인해야 한다. 연간 매출, 반기 누적 매출, 단일 분기 매출은 서로 다른 숫자다. 원과 백만원도 단위가 다르다. 값만 보고 비교하면 같은 금액을 천 배 또는 백만 배 다르게 읽을 수 있다.

연결 재무제표와 별도 재무제표도 구별한다. 연결은 종속기업 등을 함께 반영하는 기준이고, 별도는 해당 법인을 보는 기준이다. 현재 서비스는 연간 이력에서 연결 기준을 우선하고 그 기준의 자료가 없으면 별도 기준을 시도한다. 전년 비교를 할 때는 기준이 같아야 한다.

DB에는 매출·영업이익 같은 공통 이름에 맞춘 재무 자료가 있다. 이를 표준화된 재무 정보라고 한다. 서비스는 기업·연도·보고서·기준으로 이 자료를 조회하고, 등록된 항목 이름과 계정 ID로 값을 찾는다. 계정은 재무제표의 한 항목을 뜻한다.

같은 조건으로 서로 다른 값이 나오면 프로그램은 임의로 하나를 고르지 않고 오류로 처리한다. 값이 없으면 0으로 만들지 않는다. 0은 실제로 아무 금액이 없다는 뜻이지만, 누락은 확인할 수 없다는 뜻이기 때문이다.

## 둘째, 누적 실적을 개별 분기 실적으로 바꾼다

분기·반기 보고서의 숫자는 그해 처음부터 해당 시점까지 합한 누적 값일 수 있다. 반기 누적 매출을 그대로 2분기 매출로 그리면 1분기까지 합친 값을 한 분기의 실적으로 오해하게 된다.

가상 A기업의 2025년 누적 매출이 아래와 같다고 하자. 단위는 설명을 위해 모두 억원으로 맞췄으며, 실제 기업 자료가 아니다.

| 보고서에 있는 누적 매출 | 기간의 의미 | 가상 금액 |
| --- | --- | ---: |
| 1분기 | 1월부터 3월까지 | 100 |
| 반기 | 1월부터 6월까지 | 220 |
| 3분기 | 1월부터 9월까지 | 360 |
| 사업보고서 연간 | 1월부터 12월까지 | 510 |

개별 분기 매출은 1분기 100, 2분기 220-100=120, 3분기 360-220=140, 4분기 510-360=150이다. 이는 누적 값을 분기 값으로 만드는 원리를 설명한 예다. 현재 서비스는 DB에 저장된 단일 분기 값만 읽는다. DB 담당자가 검증하여 저장한 계산값도 사용할 수 있지만, 저장값이 없으면 서비스가 누적 차이를 다시 계산하지 않는다.

필요한 누적 값이 하나 빠지면 차이를 계산할 수 없다. 예를 들어 3분기 누적 매출이 없으면 연간 510이 있어도 4분기만의 매출은 알 수 없다. 현재 코드는 이런 값을 비워 두고 그래프에서도 빠진 구간으로 다룬다. 알고 있는 연간 실적을 임의로 네 등분하지 않는다.

## 셋째, 화면에 필요한 지표를 계산한다

이번에는 가상의 A기업 2025년 4분기 매출이 150억원, 영업이익이 15억원, 설비 투자 지출이 20억원, 영업활동현금흐름이 30억원이라고 하자. 앞 표의 누적 차이로 만든 4분기 매출 150억원과 연결되는 예시다.

영업이익률은 영업이익을 매출로 나누므로 15/150 × 100 = 10%다. 설비 투자 지출을 CAPEX라고 하며, 매출 대비 CAPEX는 20/150 × 100으로 약 13.3%다. 영업활동현금흐름에서 CAPEX를 뺀 값을 여기서는 FCF로 계산한다. 30-20=10억원이므로 매출 대비 FCF는 약 6.7%다.

성장 슬롯은 이제 첫 표시 분기를 100으로 맞추는 매출 지수가 아니라 전년 동분기 매출 성장률이다. 가상 A기업의 2024년 4분기 매출이 120억원이고 2025년 4분기가 150억원이면 (150/120 − 1) × 100 = 25%다. 2024년 연간 매출 400억원과 2025년 연간 매출 510억원으로 계산한 연간 성장률 27.5%와는 기간이 다르다.

화면의 4개 슬롯은 유지하되 산업별 의미를 바꾼다. 모든 지표는 %로 표시한다.

| 산업 | 성장 | 수익성 | 투자 또는 건전성 | 여력 또는 자본여력 |
| --- | --- | --- | --- | --- |
| 반도체 | 매출 성장률 | 영업이익률 | CAPEX / 매출액 | FCF Margin |
| 자동차 | 매출 성장률 | 영업이익률 | CAPEX / 매출액 | FCF Margin |
| 헬스케어 | 매출 성장률 | 영업이익률 | R&D / 매출액 | FCF Margin |
| 철강 | 매출 성장률 | 영업이익률 | CAPEX / 매출액 | FCF Margin |
| 은행·금융지주 | 순이자이익 성장률 | ROE | 대손비용률 proxy | 자기자본비율 |

| 지표 | 분기 기준 산식 |
| --- | --- |
| 매출 성장률 | (현재 분기 매출액 / 전년 동분기 매출액 − 1) × 100 |
| 영업이익률 | 분기 영업이익 / 분기 매출액 × 100 |
| CAPEX / 매출액 | 분기 CAPEX / 분기 매출액 × 100 |
| R&D / 매출액 | 분기 연구개발비 / 분기 매출액 × 100 |
| FCF Margin | (분기 영업활동현금흐름 − 분기 CAPEX) / 분기 매출액 × 100 |
| 순이자이익 성장률 | (현재 분기 순이자이익 / 전년 동분기 순이자이익 − 1) × 100 |
| ROE | 분기 순이익 × 4 / 평균 자기자본 × 100 |
| 대손비용률 proxy | 분기 신용손실비용 × 4 / 평균 대출채권 × 100 |
| 자기자본비율 | 분기 말 자본총계 / 분기 말 자산총계 × 100 |

은행의 평균 자기자본·평균 대출채권은 직전 분기 말 잔액과 현재 분기 말 잔액의 산술평균이다. 1분기에는 전년 말 잔액이 필요하다. 연환산은 분기 순이익·신용손실비용을 4배 하는 방식이며 연간 실적 예측을 뜻하지 않는다. 금융지주 4개사는 CFS, 카카오뱅크는 OFS로, `company_financial_profiles`에 등록된 기준과 비교 범위를 사용한다. 다른 기준의 금액을 섞지 않고 성장률·비율을 비교한다. 순이익은 `NET_INCOME`을 사용한다. 자기자본비율은 자본총계 / 자산총계이며 CET1·BIS 비율이 아니다. NIM·CET1·NPL·연체율은 이번 그래프에서 제외한다.

헬스케어에서는 세 번째 슬롯에 CAPEX 대신 연구개발비를 사용한다. 다만 네 번째 FCF Margin은 다른 비은행 산업과 동일하게 영업활동현금흐름에서 CAPEX를 빼서 계산한다. R&D를 FCF의 차감 항목으로 바꾸지 않는다. 연구개발 비용 계정이 없다고 개발 자산이나 투자 현금흐름을 대신 넣지도 않는다.

전년 동분기 값, 평균 잔액의 두 시점 또는 비율의 분모가 없으면 결과를 비워 둔다. 성장률의 전년 값과 비율의 분모는 양수여야 한다. 영업손실·음수 FCF처럼 유효한 음수 분자는 그대로 반영한다. 표시 기간은 기존 분석 기간 전체이며, 비교·평균 계산에 필요한 전년도 자료를 추가로 읽더라도 화면 기간을 자동으로 늘리지는 않는다.

## 넷째, 표준 재무 자료가 없을 때의 보완 범위를 정한다

현재 서비스가 기본적으로 읽는 것은 DB에 적재된 재무 행이다. 예전 폴더의 `financial_연도.json` 파일을 실행할 때마다 여는 방식은 아니다.

해당 보고서의 재무 자료가 통째로 적재되어 있지 않으면, DB에 보관한 원본 XML의 재무 표를 읽어 보완할 수 있다. XML은 공시의 문단과 표 구조를 태그로 표현한 원본 형식이다. 여기서는 문서를 새로 수집하는 것이 아니라 이미 저장된 원본을 읽는다.

다만 특정 지표 하나가 없다고 무조건 XML로 채우지는 않는다. 보고서 단위 재무 적재 기록이 있는 경우에는 일부 값이 빠져 있어도 누락으로 남긴다. 서로 다른 경로에서 읽은 숫자를 항목마다 섞다가 기간이나 연결·별도 기준이 달라지는 일을 줄이기 위한 선택이다.

XML을 읽는 경우에도 표의 기간 제목, 단위, 연결·별도 구분, 정확한 계정 이름을 확인한다. 표에서 보이는 첫 숫자를 자동으로 선택하지 않는다. 원문이 없거나 표의 기준을 확정할 수 없으면 값을 추측하지 않는다.

## 다섯째, 그래프의 수치를 눌렀을 때 계산 재료를 보여준다

A기업의 4분기 매출 150억원을 확인하려면 150이라는 결과만 보여주는 것으로는 부족하다. 누적 차이로 계산했다면 연간 510억원과 3분기 누적 360억원이 계산 재료였다는 사실도 전달해야 한다. 현재 수치 출처 경로는 이러한 구성요소를 반환한다.

직접 분기 값을 사용했다면 해당 자료를 연결하고, 누적 차이를 사용했다면 현재·직전 누적 자료를 연결한다. FCF는 현금흐름과 CAPEX 두 항목을 사용하므로 각각의 재료가 필요하다. 출처를 보는 목적은 계산 결과를 되짚을 수 있게 하는 것이다.

현재 화면에는 구현 범위의 차이가 있다. 표준 재무 행은 원래 계정명과 접수번호, 관련 문구, DART 링크 등을 연결하지만 모든 숫자의 정확한 원본 표 셀을 확보하는 것은 아니다. XML 보완 경로는 표 구조와 셀을 포함한 HTML을 만들 수 있으나, 현재 분기 팝업은 그 HTML을 직접 표시하는 경로와 연결되어 있지 않다.

따라서 현재 기능을 “모든 그래프 점에서 완성된 원본 표가 뜬다”고 설명하면 안 된다. 화면이 실제로 보여주는 범위와 원문 처리 코드가 확보한 범위를 구별해야 한다. 아래의 AI 문장 각주 원문 창은 다른 경로를 사용한다.

## 여섯째, AI 문장의 각주에서 원문으로 이동한다

[03](03_인사이트생성과프롬프트.md)에서 Gemini가 선택한 인용 문장은 DB의 청크 ID와 원문 안의 문자 위치에 연결되어 저장되었다. 사용자가 각주를 누르면 서버는 이 저장 정보를 읽는다.

가상의 A기업 원문 “서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.”를 인용했다면, 서버는 해당 청크의 지정 위치에 지금도 그 문장이 있는지 확인한다. 본문이 바뀌었는데 예전 위치를 그대로 강조하면 다른 내용을 근거처럼 보여줄 수 있기 때문이다.

확인한 뒤에는 DB의 연결 정보를 따라 정확한 원본 문서를 읽는다. 비슷한 기업명이나 접수번호를 보고 문서를 추측하지 않는다. 원문·청크·연결 정보의 버전과 문서 크기, 해시를 검사한다. 해시는 같은 파일 내용인지 확인하는 데 사용하는 계산값이다.

이처럼 “어느 문장을 썼는지”와 “어느 원본 문서인지”를 모두 확인해야 각주가 신뢰할 만한 자료 연결이 된다. 원문이 현재 자료와 맞지 않으면 무관한 위치를 대신 강조하지 않는다.

## 일곱째, 원문 형식을 읽고 인용 위치를 찾는다

XML에는 화면에 그대로 보여주기 어려운 태그와 표 구조가 있다. 코드는 원문을 읽어 문단·제목·표로 바꾸고, 인용 문장이 어디에 있는지 찾는다. 기본적으로 엄격한 읽기 방식을 사용하며, 형식이 일부 잘못된 경우에는 제한된 복구 읽기를 시도한다.

복구가 성공했다고 무조건 통과시키지는 않는다. 복구 과정에서 본문이 빠지지 않았는지 비교하고, 원본 안의 외부 자료를 임의로 불러오지 않도록 제한한다. 단순히 잘못된 문자를 모두 지워 오류만 없애는 방식은 아니다.

문구가 원문에 한 번만 있으면 위치를 정하기 쉽다. 그러나 같은 문장이 본문과 요약, 여러 목차에 반복될 수 있다. 이때 목차와 소제목으로 후보를 좁힌다. 그래도 여러 위치가 남으면 Gemini에 후보 주변 문맥을 주어 기존 설명과 맞는 위치를 평가하게 하는 예외가 있다.

이 예외는 새 사업 설명을 작성하는 작업이 아니라 이미 저장한 각주의 위치를 정하는 작업이다. 그래서 일반 페이지 조회는 저장 설명을 읽더라도 일부 원문 조회에는 Gemini 호출이 생길 수 있다.

## 마지막으로, 주변 문맥과 함께 강조해서 보여준다

문장 하나만 떼어 보여주면 그 말이 계획인지, 조건이 붙은 설명인지 알기 어려울 수 있다. 현재 원문 창은 인용 위치가 들어 있는 제목 구간에서 약 2,000자 주변 내용을 보여준다. 인쇄 페이지의 앞뒤 한 페이지를 자르는 방식은 아니다.

구간에 표가 걸치면 표 전체를 포함할 수 있어 표시량이 더 커질 수 있다. 코드는 안전하게 만든 제목·문단·표 HTML 안에서 해당 인용 부분을 강조하고, 브라우저는 이를 별도 원문 창에 표시한다. 원본에 들어 있는 임의의 스크립트를 그대로 실행하는 방식은 아니다.

이 단계의 결과는 “원문 위치를 확인한 내용과 주변 맥락”이다. 숫자 출처와 문장 각주는 서로 다른 경로지만, 둘 다 결과를 원래 자료까지 되짚을 수 있게 하려는 목적을 갖는다.

## 구현 상세: 파일과 정확한 처리 기준

앞부분의 흐름을 이해한 뒤 필요한 항목을 찾아 읽는 참고 영역이다. 처음 읽을 때 모든 함수명과 설정값을 외울 필요는 없다.

### 구현 의도: 숫자의 기준과 문장의 위치를 보존한다

재무 값이 있다는 것만으로 비교 가능한 것은 아니다. 연결·별도, 연간·누적·분기, 원·백만원, 시점 잔액이 다르면 같은 지표 이름이라도 다른 값이다. 현재 조회 계층은 기준을 고정하고, 파생 지표는 코드가 계산하며, 확인할 수 없는 값은 빈 값으로 둔다.

출처도 수치와 자연어를 구분한다. 숫자는 계정·기간·단위·재무 기준과 연결하고, AI 문장은 공시 청크 안의 정확한 문장 위치와 연결한다. 유사한 문서가 있다는 이유만으로 임의 위치를 강조하지 않는 것이 원문 기능의 목적이다.

### 재무 수치를 찾는 순서

기본 입력은 기업·연도·보고서·재무 기준·기간 유형이다. `standardized_financials`에서 값을 읽어 다음 공통 지표를 찾는다.

| 내부 키 | 찾는 내용 | 재무제표 범위 |
| --- | --- | --- |
| `revenue` | 매출액·수익 계정 | 손익 IS/CIS |
| `operating_income` | 영업이익·영업손익 | 손익 IS/CIS |
| `operating_cashflow` | 영업활동현금흐름 | 현금흐름 CF |
| `inventory` | 재고자산 | 재무상태 BS |
| `capex` | 표준화된 유형자산취득(CAPEX) | 현금흐름 CF |

KRW 기준으로 표준 계정 이름을 먼저, 없으면 등록된 계정 ID를 사용한다. 같은 기업·기간·기준의 후보 값이 여러 개여도 모두 같은 값이면 출처들을 보존한다. 값이 다르면 첫 행을 고르는 대신 충돌 오류를 낸다.

표준 뷰가 계정명 일치로 연결되면서 일부 `영업이익(손실)` 행을 누락하는 상황을 보완하기 위해, `financial_facts`에서 `dart_OperatingIncomeLoss` 또는 정확한 영업손익 별칭을 읽는 한정된 경로가 있다. 매출총이익·계속영업이익을 영업이익으로 바꾸어 쓰지 않는다. 이 경로는 표준 뷰에서 누락된 영업이익 사실을 되찾는 것이며 XML 보완과 다르다.

### 은행·헬스케어 지표의 추가 조회

은행 그래프는 `financial_metric_values`에서 `review_status='approved'`, `unit='KRW'`인 행을 조회한다. 이 테이블에는 버전 열이 없으므로 `source_rcept_no`가 현재 버전의 활성 `filings` 행과 기업·연도·보고서까지 일치하는지도 검사한다. 회사별 `preferred_fs_div`와 `comparison_scope`가 맞는 행만 계산에 넣으며, 임의로 OFS·CFS를 대체하지 않는다.

순이자이익·순이익·신용손실비용은 `NET_INTEREST_INCOME`, `NET_INCOME`, `CREDIT_LOSS_EXPENSE`를 사용한다. 자본·자산·대출채권은 `TOTAL_EQUITY`, `TOTAL_ASSETS`, `LOANS_AT_AMORTISED_COST`의 시점 잔액이다. 승인된 대출채권 값이 없으면 같은 기준의 `LOANS_AT_AMORTISED_COST_NOTE`를 시도한다. 이자수익을 순이자이익으로, 충당금 잔액을 신용손실비용으로 바꾸어 쓰지 않는다.

헬스케어 R&D는 현재 버전의 활성 `financial_facts` 중 원화 손익 계정에서 읽는다. `ifrs-full_ResearchAndDevelopmentExpense`, `dart_OrdinaryDevelopmentExpense` 또는 정확한 연구개발 비용 이름으로 찾고 분기값을 구성한다. 후보 값이 서로 다르면 해당 조회 결과를 비운다. 일반 재무 Repository의 충돌 오류 처리와 이 추가 조회의 결측 처리는 구별한다.

표준 뷰에서 영업활동현금흐름이 누락되는 경우에는 `financial_facts`의 정확한 영업활동현금흐름 계정 ID로 보완한다. 이는 기존 JSON 적재 행을 찾는 경로로, XML 보완을 새로 허용하는 조건이 아니다.

은행 출처 요청은 성장률의 현재·전년 동분기 순이자이익, ROE·대손비용률의 분자와 평균 잔액 두 시점, 자기자본비율의 자본·자산을 연결한다. R&D 요청은 연구개발비 원천 행과 매출 자료를 연결한다. 계정명·원 단위 값·재무 기준·보고서·DART 링크를 반환하며, 모든 항목의 원본 표 셀을 자동으로 확보한다는 뜻은 아니다. 현 일반 매출 성장률 출처 창은 선택 분기의 매출 구성요소를 보여주며 전년 동분기까지 모두 묶는 전용 출처 창은 아니다.

### JSON 자료와 XML 보완의 경계

서비스는 디스크의 `financial_연도.json`을 직접 읽지 않는다. 그 JSON에서 적재된 `financial_facts`와 `coverage.financial_exists`로 보고서 단위 재무 자료 존재를 확인한다.

```text
요청 기준의 표준 수치 행 조회
  ├─ 행 있음 → 표준 수치 사용
  └─ 행 없음
      ├─ 보고서의 JSON 적재 기록 있음 → 누락 값 유지
      └─ 보고서의 JSON 적재 기록 없음 → 원본 XML 재무 표 보완
```

“특정 지표가 없으면 XML로 채운다”는 방식이 아니다. 다른 재무 기준의 행이나 매핑되지 않은 계정만 있더라도 그 보고서의 JSON이 존재하면 XML 보완을 하지 않는다. 기존 정제 경로의 수치와 독립적으로 읽은 XML을 항목별로 섞으면 다른 기간·연결 기준을 혼합할 수 있어 보완 범위를 좁힌 것이다.

보고서가 없어서 XML을 읽어도 확인 가능한 계정만 반환한다. 원본 부족·기간 불명확·충돌은 빈 값과 설명으로 남기며 DB에 다시 적재하지 않는다.

### XML 재무 표를 안전하게 읽는 기준

원본 XML은 선택 기업·연도·보고서의 현재 공시와 연결된 문서에서 읽는다. 접수일·접수번호를 기준으로 문서를 정하고, 원본의 활성 상태·버전·바이트 수·SHA-256을 확인한다. 임의로 다른 접수번호의 표를 선택하지 않는다.

표는 각 셀의 행·열 위치와 `rowspan`·`colspan`을 보존한다. 병합 셀을 논리 격자로 펼쳐 현재 기간 헤더를 찾되 출력에는 원래 표 셀을 유지한다. 재무제표 제목·연결/별도·기간·단위·계정명을 함께 검사한다.

- 재무상태표는 기말 시점, 손익·현금흐름은 해당 보고서의 기간을 확인한다.
- 같은 손익 표 안의 3개월 값과 누적 값을 구분한다. 기간 열이 모호하면 선택하지 않는다.
- `원`, `천원`, `백만원`, `억원`을 원 단위로 환산한다. 주당이익의 원 단위가 본표의 백만원 단위를 덮어쓰지 않도록 한다.
- 쉼표·괄호·△ 등 숫자와 음수 표현을 처리한다. 유형자산 취득 지출은 CAPEX의 양수 규모로 표현한다.
- 정확한 등록 계정 이름과 기간을 사용한다. 후보가 여러 개면 임의 첫 값을 채택하지 않는다.

추출된 수치는 원본 문서·접수번호·목차·표·계정 셀·기간 헤더·단위와 연결된다. 캐시는 문서 해시·버전·기간·재무 기준과 추출 코드 버전에 따라 달라진다. LLM이 표의 수치를 추측하는 경로는 없다.

### 연간 값과 화면 분기 값을 어떻게 계산하는가

보고서의 연간 이력은 CFS를 우선하고 해당 기준 자료가 없으면 OFS를 시도한다. 전년도 비교는 정확히 직전 연도이고 재무 기준이 같은 경우에만 한다.

```text
변화율 = (현재값-전년값) / 전년값 × 100  # 전년값 > 0일 때
영업이익률 = 영업이익 / 매출 × 100      # 매출 > 0일 때
CAPEX 비중 = CAPEX / 매출 × 100
FCF = 영업활동현금흐름 - CAPEX
FCF 비중 = FCF / 매출 × 100
```

전년도 영업이익이 음수나 0이면 이 변화율은 계산하지 않는다. 적자에서 흑자로 전환한 규모를 일반적인 성장률로 보여주면 해석을 오도할 수 있기 때문이다. 손익 개선 자체가 없었다는 뜻은 아니다.

현재 화면의 분기는 연간 이력의 기준을 사용해 저장된 `quarterly` 값만 읽는다. 아래 산식은 DB가 검증하여 분기값을 만들 때의 원리이며 서비스에서 실행하는 대체 계산이 아니다.

```text
Q1 = 1분기 누적
Q2 = 반기 누적 - 1분기 누적
Q3 = 3분기 누적 - 반기 누적
Q4 = 연간 - 3분기 누적
```

가상으로 누적 매출이 Q1 100, H1 220, Q3 360, FY 510이면 개별 분기 매출은 100·120·140·150이다. H1의 220을 2분기 매출로 그대로 표시하지 않는다. DB에 저장된 분기값이 없으면 빈 구간으로 둔다. CAPEX가 음수이면 기존 방침대로 해당 분기 값을 비운다.

현재 화면은 성장 슬롯만 전년 동분기 대비 성장률로 계산하고, 나머지 슬롯은 해당 분기의 비율을 계산한다. 섹터별 지표는 앞의 표와 같으며 모든 슬롯을 전년 대비 변동률로 바꾸는 것은 아니다. 화면 산식과 중앙값은 [06](06_시세수집과화면.md)을 따른다.

### 수치 출처 팝업에 무엇을 돌려주는가

`quarter_source()`는 선택 분기의 값이 어떤 원천 기간으로 만들어졌는지 반환한다. 저장된 분기값의 해당 보고서와 출처를 표시한다. 저장된 계산값이면 산식과 원본 근거 정보를 따른다. 서비스에서 누적 차이를 새로 만들지는 않는다. FCF는 영업활동현금흐름과 CAPEX 각각의 구성요소를 제시한다.

출처에서는 다음 차이가 있다.

| 수치 경로 | 백엔드가 확보하는 출처 | 현재 화면의 표시 범위 |
| --- | --- | --- |
| 표준 재무 JSON 적재 행 | 원래 계정명·접수번호·관련 청크·DART 링크 | 관련 문구·표준 값·링크. 정확한 셀 구조를 항상 확보하지 않음 |
| XML 보완 수치 | 원본 표·병합 구조·계정/기간 셀과 강조 HTML | 백엔드가 `document_html`을 제공하지만 분기 팝업의 `tableMarkup`은 이를 직접 사용하지 않음 |

현재 표 렌더러는 `source.table`이 있을 때 행·병합 셀·강조를 표시한다. 현재 원격 수치 경로는 일반적으로 `table=None`을 반환한다. 따라서 “모든 재무 점을 누르면 완성된 원본 표가 뜬다”는 설명은 현재 구현과 다르다. XML 보완에 정확한 표 HTML을 만드는 코드가 있다는 사실과 해당 HTML을 분기 팝업에서 표시한다는 사실을 구별한다.

이 문서 개정은 이 차이를 설명하는 작업이며 화면 코드를 변경하지 않았다. 자연어 각주 원문 창은 아래의 다른 렌더링 경로를 사용한다.

### AI 각주가 정확한 청크·문장을 가리키는 방식

생성 단계에서 선택한 `tN-pM`은 DB의 청크 ID와 원문 문자열의 시작·끝 위치로 변환된다. 영구 각주 ID에는 산업·청크·시작 위치·인용 문구를 반영하고, 각주 사전에 기업·기간·접수번호·목차·요약 문장도 저장한다.

각주 조회는 저장된 보고서에 등록된 ID만 받는다. 현재 청크를 다시 읽어 `chunk_text[start:end] == quote`를 검사한다. 본문이 바뀌었는데 이전 위치를 그대로 강조하지 않기 위한 것이다. 저장 인용 문구가 현재 자연어 선정 기준에 맞지 않으면 재생성이 필요한 상황으로 처리한다.

### 청크에서 원본 XML까지 연결하는 과정

접수번호만으로 XML을 추측하지 않고 `chunk_source_documents`와 `filing_source_documents`를 연결한다. 선택 청크에 활성 원본이 정확히 하나 연결됐는지 확인한다. 청크는 현재 버전이어야 하며, 원본과 연결의 버전은 검증된 벡터 SQLite·FAISS 해시가 현재와 모두 같은 경우에만 이전 생성 버전을 허용한다. 접수번호·실제 XML 바이트 수·SHA-256 검사는 유지한다.

원본은 인코딩을 읽고 잘못된 앰퍼샌드·문자 참조·일반 문장의 꺾쇠 표기를 최소한으로 보정한 뒤 엄격 파싱을 우선한다. DTD·모호한 선언과 허용되지 않는 제어문자를 본문에서 임의 삭제해 통과시키는 정책은 아니다. 엄격 파싱이 실패하면 lxml 복구 파싱을 시도하되 외부 엔티티·외부 DTD·네트워크 접근을 막는다. 복구 결과의 텍스트와 태그 제거 기준 텍스트를 공백 정리 후 비교해 내용 손실을 감지한다. 복구 성공만으로 무조건 신뢰하지 않는 방식이다.

이 과정은 원천 문서를 다시 전처리·청킹·DB 적재하는 기능이 아니다. 서비스가 이미 보관된 원본을 조회해 안전하게 보여주는 과정이다.

### 원문의 같은 문장이 여러 곳에 있으면 어떻게 하는가

XML의 본문 텍스트와 인용 문구를 NFKC와 공백 제거 기준으로 비교한다. 정규화한 위치를 실제 문자열 위치로 되돌릴 수 있도록 대응 정보를 유지한다. 목차·소제목이 일치하는 구간으로 후보를 좁힌다.

그래도 위치가 여러 개면 후보마다 주변 문맥을 만든다. Gemini에 요약 문장과 후보 문맥을 주고 F/U/C/T 평가를 요청한다. 코드는 후보 ID·평가 범위·적격 조건을 검사한 뒤 적격 최고 점수를 선택하고, 동점이면 앞쪽 후보를 고른다. 결과는 요청 내용에 따라 캐시한다.

이 경로는 새로운 산업 인사이트 생성이 아니라 기존 각주 위치를 정하는 용도다. 자연어 의미를 완전히 독립적으로 검증하는 심사도 아니다. 적격 위치를 정할 수 없거나 원문 검증이 실패하면 엉뚱한 곳을 강조하지 않고 이유와 DART 전체 링크를 제공한다.

### 원문을 어느 범위까지 보여주는가

확정한 인용 위치를 포함하는 가장 좁은 제목 구간 안에서 약 2,000자 주변 내용을 구성한다. XML에 인쇄 페이지 정보가 있다고 가정하지 않으므로 “앞뒤 한 페이지”가 현재 기준은 아니다. 표시 구간에 표가 걸치면 그 표는 전체를 포함해 표 구조를 유지하며 이 경우 2,000자를 넘을 수 있다.

HTML은 허용한 제목·문단·표 요소만 만들고 원문 문자들을 이스케이프한다. 원본 XML의 임의 속성·스크립트를 실행하지 않는다. 인용 위치는 `<mark>`로 표시한다. 프런트는 이 HTML을 sandbox iframe의 `srcdoc`로 열며 코드의 콘텐츠 보안 정책도 적용한다.

단일 문장과 주변 문단을 함께 보여주는 이유는 주체·계획·조건을 확인할 수 있도록 하기 위해서다. 정해진 크기를 넘는 전체 사업보고서를 매번 전송하는 비용을 줄이면서도 표를 잘라 읽기 어렵게 만들지 않도록 했다.

### 검증의 범위와 테스트

수치 계정·기준 일치, 문구의 문자 위치, 원본 바이트의 무결성을 확인하는 장치는 서로 다른 오류를 막는다. 원래 공시가 사실인지, LLM 설명의 모든 의미가 적절한지, 전체 XML의 모든 형태를 완벽히 처리하는지까지 보증하지 않는다. 특히 표준 수치의 셀 출처와 분기 팝업의 연결 범위는 위 제한을 따른다.

### v11 인계 규칙 반영

은행 그래프는 `review_status=approved`인 원화 값과 현재 공시 접수번호만 사용한다. 우리금융지주의 혼합 대출채권은 승인된 `_NOTE` 대안을 기존 우선순위에 따라 사용한다. 검토 필요 Q4를 연간 값에서 Q3를 빼서 다시 만들지 않는다. 일반 기업과 R&D도 저장된 분기값이 없는 경우 표시를 비운다. 기존 4개 지표 화면과 결측 표시 원칙은 유지하며, 없는 값을 0으로 채우지 않는다. 재무 표준 뷰의 v11 공식 태그 매핑을 사용하고 현재 재무 버전 필터는 그대로 유지한다.

## 2026년 10월 10일 서버 점검: 2023년 그래프가 비는 경우

네이버 서버의 실제 실행 코드와 현재 MySQL 버전 `2026-10-09-dart25-h1h3-v11`을 확인했다. 25개 분석 기업의 2023년 분기 그래프 계산 결과를 조회했으며, 현재 DB에는 2022년 활성 공시와 2022년 재무 팩트가 없다. 2023년 매출 또는 순이자이익 수치가 있어도 전년 동분기인 2022년 비교값이 없으면 성장률은 비워 둔다. 이것을 2023년 매출 자체가 없다는 뜻으로 해석하면 안 된다. 은행의 2023년 1분기 ROE와 대손비용률 proxy도 평균 자기자본·대출채권 계산에 필요한 2022년 4분기 말 값이 없어 표시되지 않는다. 2023년 공시 안에 비교 전기 숫자가 전혀 없다는 뜻은 아니며, 그 전기 숫자의 기간·기준을 검증해 별도로 적재한 상태가 아니라는 의미다.

부분 누락은 별개다. 유한양행의 R&D는 2023년 1-3분기 단일 분기 값이 있으나 사업보고서에서는 연간 값만 확인되었고, 나머지 헬스케어 4사의 현재 재무 팩트에서는 서비스가 인식하는 연구개발 계정이 확인되지 않았다. 원익IPS의 2023년 4분기와 풍산의 2023년 1-3분기는 영업활동현금흐름이 비어 있어 FCF Margin을 계산할 수 없다. POSCO홀딩스의 2023년 4분기는 매출액이 비어 있어 매출액을 분모로 사용하는 비율도 비어 있다. 이 기업들의 공시 XML은 존재한다. 따라서 원문에도 해당 정보가 없다고 단정해서는 안 된다.

현재 XML 재무 보완은 `Repository.financial()`에서 해당 보고서의 JSON 기반 재무 자료 전체가 없을 때만 실행한다. JSON 기반 행 또는 coverage의 `financial_exists=1`이 있으면 일부 계정이 비어 있어도 XML을 계정별로 섞어 채우지 않는다. 연간·누적 값을 임의로 분기 값으로 재계산하여 upstream의 검토·누락 결정을 되돌리지 않는 정책도 유지한다. 연구개발 주석까지 별도로 읽어 분기 R&D를 구성하는 기능은 이 경로에 없다. 따라서 위 부분 누락은 XML 보완 조건 밖에 있는 사례다.

에이치브이엠은 2023년 재무 자료뿐 아니라 활성 공시·원본 XML도 없었다. XML 보완 경로는 선택되지만 ‘해당 기간 원본 공시가 없습니다’라는 결과를 반환한다. 이 경우는 원본 자료부터 추가로 확보해야 한다. 이번 작업에서는 누락 이유를 점검했으며 원격 DB 수치나 재무 보완 정책을 변경하지 않았다.

## 원문 화면 변환 결과 재사용 (2026-10-10)

각주를 누를 때마다 기존 원문 조회를 실행하여 청크 연결, 데이터 버전, XML 크기와 SHA-256을 검증한다. 검증을 통과한 뒤 XML 해시·근거 문장·절·소제목·요약 문장이 모두 같은 경우 HTML 변환 결과를 재사용한다. 최대 64개·8MB로 제한하고, 강조 위치를 찾지 못한 결과와 오류는 보관하지 않는다. 따라서 반복 조회에서 XML 해석과 HTML 생성 비용을 줄이지만, 원문 BLOB의 DB 전송 자체를 생략하지는 않는다. 기존 최대 2,000자와 표 전체 표시 기준은 유지한다.

## 자연어 근거와 금액 검증 보완 (2026-10-10)

각주 자연어의 20자·점수 기준은 유지하면서 날짜가 포함된 사업 설명을 허용했다. 금액·비율·수량 나열과 표는 여전히 각주 근거에서 제외한다. 분석 입력의 재무 수치는 유지한다. 요약에 원 단위 금액이 나타나면 기업·연도·보고서·회계 기준·재무 항목을 맞춰 확인하고, 범위가 모호하면 교정한다. 청크 ID와 문장 ID의 연결 구조는 변경하지 않았다. 자세한 재시도 및 검증 범위는 인사이트 문서를 참조한다.

XML 기반 통합 테스트에서 분기 근거의 보고서 종류가 `values.report_type`에 들어오는 실제 입력을 확인했다. 금액 검증은 최상위 `report_type`이 없으면 그 값을 읽는다. 중복 원문 위치의 평가도 객체·배열·등급·boolean 자료형을 확인하여 빈 값에 의한 예외가 정상적인 교정 경로를 벗어나지 않도록 했다. 점수·위치 선택 프롬프트와 근거 ID 구조는 유지한다. 검증 범위와 한계는 [08](08_XML기반오프라인통합검증.md)에 정리했다.
