# 01. 서비스 구조와 데이터 조회

[문서 목록](README.md) · 기준: 2026-10-08

## 이 문서에서 이해할 과정

DB에 자료가 저장된 다음 서비스가 가장 먼저 하는 일은 **무엇을 분석할지 정하고 그 범위에 맞는 자료를 꺼내는 것**이다. 이 문서에서는 반도체 산업의 A기업 자료를 읽는 상황을 따라간다. A기업과 연도는 설명용 예시이며 실제 DB 상태를 뜻하지 않는다.

## 1단계. 분석 명령으로 작업을 시작한다

서비스 코드가 폴더에 있고 DB에 자료가 있다고 해서 분석이 저절로 시작되지는 않는다. 관리자가 “지금 이 산업의 보고서를 만들어라”라는 명령을 실행해야 한다. 명령을 받은 Python 프로그램은 필요한 조회·검색·생성 작업을 순서대로 호출한다.

예를 들어 반도체를 지정하면 프로그램은 반도체 보고서를 만드는 작업을 시작한다. 기업이나 연도를 추가로 지정하면 분석 범위를 더 좁힐 수 있다. 지정하지 않은 경우에는 현재 운영 가능한 기업과 DB에 있는 전체 연도를 사용한다. 이때 운영 가능하다는 것은 데이터 관리 측에서 서비스에 사용할 수 있다고 표시한 기업이라는 뜻이다.

이 단계가 끝나면 프로그램에는 “어떤 산업의 어떤 기업들을 어느 기간으로 읽을 것인지”라는 작업 범위가 생긴다. 아직 사업을 해석한 문장이나 그래프가 만들어진 것은 아니다.

## 2단계. DB에 등록된 산업과 기업의 관계를 확인한다

서비스는 산업 이름만 보고 해당 기업을 추측하지 않는다. DB에 저장된 “이 기업은 이 지수의 구성기업이다”라는 관계를 읽는다. A기업이 현재 반도체 구성기업이고 운영 가능한 상태라면 반도체 분석 대상에 들어갈 수 있다.

왜 이 과정이 필요할까? 같은 회사가 여러 산업에 연결될 수 있고, 산업을 구성하는 기업도 바뀔 수 있기 때문이다. 프로그램에 기업 목록을 고정해서 써두기보다 DB의 현재 관계를 읽으면 새로운 산업이나 기업을 같은 흐름으로 처리할 수 있다.

기업에는 이름 외에 여러 번호가 있다. DART 기업번호는 공시·재무를 연결할 때 쓰고, 거래소 종목코드는 주가를 찾을 때 쓴다. 같은 기업을 가리키지만 용도가 다르다. 사람이 “A기업”이라고 선택하더라도 프로그램은 필요한 조회에 맞는 번호로 연결해야 한다.

산업도 화면에서 쓰는 이름, DB 구성기업 관계를 찾는 코드, 시세를 확인하는 지수 식별자가 다를 수 있다. 현재 코드는 이 역할을 나누어 관리한다. 새로운 산업을 추가했을 때 이름 하나가 모든 조회에서 동일하게 쓰인다고 가정하지 않기 위한 것이다.

## 3단계. 사용할 자료의 묶음과 연도를 정한다

원격 DB는 자료가 갱신될 수 있다. 공시 본문을 새로 넣었는데 검색 벡터는 이전 상태라면, 검색한 문구와 원문이 다른 문제가 생길 수 있다. 서비스는 이런 상황을 구분하기 위해 **데이터 버전**, 즉 현재 사용할 자료 묶음의 번호를 읽는다.

현재 사용할 버전은 하나여야 하고, 데이터 관리 측에서 확인을 마친 상태여야 한다. 버전이 여러 개이거나 확인되지 않았다면 서비스는 분석을 진행하지 않는다. 이는 새 자료와 옛 자료를 섞어 그럴듯한 결과를 만드는 일을 막는 출발점이다.

이어서 해당 버전에 어떤 연도의 자료가 있는지 확인한다. 예시처럼 2023-2025년이 준비돼 있다면 그 연도들을 사용할 수 있다. 이전 버전에만 있던 연도를 현재 자료처럼 끌어오지는 않는다.

여기서 “자료가 있다”와 “모든 지표가 빠짐없이 있다”는 다르다. 사용 가능한 연도가 확인돼도 일부 보고서·계정·청크는 빠져 있을 수 있다. 서비스는 이런 준비 상태를 함께 읽고 누락 내용을 남긴다.

## 4단계. 숫자와 문장을 서로 다른 방식으로 읽는다

A기업의 매출액을 찾는다면 프로그램은 기업·연도·보고서·재무 기준에 맞는 매출 항목을 조회한다. 반면 생산능력 확대 계획을 찾는다면 여러 공시 문단 중 그 내용과 관련된 문구를 검색해야 한다. 그래서 자료를 읽는 단계부터 숫자와 문장을 구분한다.

재무 기준이란 숫자가 무엇을 포함하고 어느 기간을 나타내는지에 관한 조건이다. 예를 들어 연결 재무제표는 기업집단을 함께 보는 기준이고, 별도 재무제표는 해당 법인을 보는 기준이다. 반기 누적 실적은 그 해 처음부터 반기 말까지의 합이며, 단일 분기 실적은 한 분기만의 값이다. 이런 기준을 섞으면 같은 기업의 값이어도 비교가 달라진다.

프로그램은 이 조건들을 SQL이라는 DB 조회 문장으로 전달한다. SQL의 역할은 “이 조건에 맞는 저장 행을 달라”고 요청하는 것이다. 사업의 의미를 이해하거나 AI 설명을 작성하는 역할은 아니다.

조회한 결과는 Python 안에서 항목 이름과 값의 묶음으로 다룬다. 가령 기업명은 A기업, 연도는 2025, 보고서 종류는 사업보고서, 매출은 해당 숫자라는 식이다. 이후 계산·검색·AI 입력 단계가 이 묶음을 사용한다.

## 5단계. 조회를 담당하는 코드를 통해 다음 작업에 전달한다

이 프로젝트는 여러 기능이 DB를 제각각 조회하지 않도록 공통 조회 코드를 둔다. 그 역할을 하는 것이 `Repository`다. 이름은 어렵게 보일 수 있지만 여기서는 **산업과 기업의 자료를 정해진 방법으로 꺼내 주는 담당 코드**라고 이해하면 된다.

보고서 생성 코드는 Repository에 연간 재무나 문서 목록을 요청하고, 검색 코드는 청크를 요청한다. 화면 코드도 필요한 분기 재무를 요청한다. 요청 목적은 다르지만 같은 기업·기간·버전 규칙을 사용한다.

숫자가 없으면 확인할 수 없는 상태로 반환하고, 같은 조건에 서로 다른 숫자가 나오면 충돌로 처리한다. 자동으로 첫 번째 숫자를 선택하면 잘못된 값이 그래프와 설명으로 이어질 수 있기 때문이다.

이 단계의 결과는 아직 최종 보고서가 아니라, 다음 단계가 사용할 재무 값·공시 목록·검색 대상 청크·준비 상태다. 공시의 어떤 조각이 설명에 필요한지는 [다음 문서의 검색 과정](02_공시검색과벡터검증.md)에서 결정한다.

## 조회 이후 전체 작업을 연결해서 보기

조회한 재무 자료는 계산 단계에서 지표와 이력으로 정리한다. 공시 청크는 검색 단계에서 관련 내용을 고른다. 워드클라우드는 대상 공시의 단어를 집계한다. Gemini는 그 결과를 전달받아 설명을 작성한다. 검증한 설명과 각주를 다른 결과들과 묶어 저장하면 비로소 서비스 보고서가 된다.

이때 보고서는 DB의 원천 자료와 별도로 저장한다. 원천 DB는 어떤 공시와 숫자가 있었는지를 보존하고, 앱의 보고서는 그 자료를 사용해 어떤 결과를 만들었는지를 보존한다. 둘을 분리하면 원천 자료를 변경하지 않고도 설명을 다시 만들 수 있다.

다시 읽을 때에는 기존 보고서가 현재 자료 기준으로 만들어졌는지 확인한다. 현재 데이터 버전과 산업 설정 등을 대표하는 값을 계산해 비교하는데, 이를 문서 뒤쪽에서는 **자료 지문**이라고 부른다. 모든 원문을 매번 새로 읽는 것이 아니라, 보고서가 어떤 기준으로 만들어졌는지 확인하기 위한 표시다.

## 이 과정을 설계한 이유

이 서비스는 DB 적재 작업과 서비스 조회 작업을 분리했다. 조회 중 잘못된 원천 자료를 임의로 고쳐 쓰지 않고, 범위·기준·누락을 다음 단계에 전달한다. 그래야 검색·AI·화면에서 생긴 문제를 추적할 수 있다.

또 산업·기업 목록을 DB에서 읽고 같은 조회 코드를 사용한다. 반도체 이외의 산업을 추가할 때 기본 흐름을 다시 만들 필요를 줄이려는 설계다. 다만 다른 산업의 회계 계정·용어·지표까지 모두 자동으로 알게 되는 것은 아니므로 해당 자료를 확인하는 작업은 여전히 필요하다.

## 구현 상세: 파일과 정확한 처리 기준

앞부분의 흐름을 이해한 뒤 필요한 항목을 찾아 읽는 참고 영역이다. 처음 읽을 때 모든 함수명과 설정값을 외울 필요는 없다.

### 구현 의도: 자료 조회와 설명 생성의 책임을 나눈다

산업이나 기업을 늘릴 때마다 개별 보고서용 코드를 복사하면 같은 기능을 여러 곳에서 고쳐야 하고, 서로 다른 기준으로 숫자를 비교하기 쉽다. 현재 서비스는 산업 목록·구성기업·기간을 DB에서 발견하고, 공통 조회 계층이 같은 기준으로 수치와 공시를 반환하게 한다. 화면과 Gemini는 그 결과를 소비한다.

원격 MySQL은 원천 자료 저장소이고, 앱 저장소는 생성 보고서 저장소다. 조회 코드가 수집·정제 작업을 겸하지 않도록 읽기 전용으로 구성했다. 자료가 잘못 맞춰져 있으면 서비스가 임의로 복구하거나 사실을 만들어 넣지 않고 오류 또는 누락으로 드러낸다.

### 코드 구조와 구성요소의 경계

```text
BOOTCAMP_MINI/
├─ app.py                         로컬 HTTP 서버
├─ snapdart/
│  ├─ analyze.py                  분석 실행 명령
│  ├─ data_access/
│  │  ├─ pipeline.py              보고서 조립·LLM 연결
│  │  ├─ prompts.py / prompts_old.py
│  │  ├─ query.py                 질문의 조회 의도·범위 지정
│  │  └─ catalog/repository/sources.py  공통 계층 연결
│  ├─ llm.py                      Gemini 요청·검증·사용량 제어
│  ├─ dashboard.py                보고서에 시세·표시 지표 결합
│  └─ ui_project.py               현재 화면용 JSON 변환
├─ dart_remote/                   로컬·배포 공유 구현
├─ web/                           HTML·CSS·JavaScript
├─ config/sectors.json             산업별 검색 주제·표시 설정
└─ deploy/
   ├─ cloudapp/                   FastAPI·CLI·배포 연결 계층
   ├─ dart_remote/                공유 구현의 배포본
   ├─ web/ · config/              동일 화면·설정의 배포본
   └─ Dockerfile · compose.yaml   Linux 실행 환경
```

| 담당 파일 | 핵심 역할 |
| --- | --- |
| [catalog.py](../../dart_remote/catalog.py) | 현재 버전·산업 목록·지수 식별자·구성기업 변경 지문 |
| [db.py](../../dart_remote/db.py) | 환경설정·연결 풀·읽기 전용 SQL |
| [repository.py](../../dart_remote/repository.py) | 기업·연도 선택, 재무 계정·공시 청크·검색 결과 조회 |
| [pipeline.py](../../snapdart/data_access/pipeline.py) | 재무 이력·공시·워드클라우드·인사이트 조립 |
| [artifacts.py](../../dart_remote/artifacts.py) | 원격 DB와 분리된 보고서·시세·캐시 저장 |

로컬 `snapdart/data_access`의 일부 파일은 공통 모듈을 가져오는 연결 계층이다. 배포 `cloudapp`에도 대응 계층이 있다. 실제 검색·원문 처리 원칙은 `dart_remote`에 모아 같은 결과 계약을 사용한다. HTTP 서버 방식과 배포의 공유 사용량 제어는 환경에 따라 다르다.

### DB에서 각각 어떤 자료를 읽는가

아래는 실제 조회하는 주요 테이블·뷰다. 전체 DB 스키마를 새로 정의한 목록은 아니다.

| 자료 | 주요 테이블·뷰 | 용도 |
| --- | --- | --- |
| 현재 버전 | `data_versions` | 현재 버전이 하나이고 검증됐는지 확인 |
| 산업·지수 | `krx_indices` | 활성 산업·표시명·공식 지수 식별자 |
| 기업·현재 구성 관계 | `companies`, `krx_index_constituents` | 산업에 속하는 운영 기업과 식별자 |
| 보고서별 준비 상태 | `coverage` | 사용 가능한 연도와 누락 자료 설명 |
| 표준화 재무 | `standardized_financials` 뷰 | 기준이 정리된 계정 값과 출처 |
| 원래 재무 사실 | `financial_facts` | JSON 적재 여부, 영업이익·영업현금흐름 계정 보완, 헬스케어 R&D |
| 은행 지표 수치 | `financial_metric_values` | 승인된 원화 순이자이익·순이익·신용손실비용·기말 잔액 |
| 은행 재무 기준 | `company_financial_profiles` | 연결/별도 우선 기준과 비교 범위 |
| 문서·검색 본문 | `filings`, `chunk_metadata` | 공시 목록·청크·기간·목차·검색 가능 여부 |
| 벡터·모델 정보 | `chunk_embeddings`, `embedding_metadata` | 저장 벡터와 모델·버전·차원 확인 |
| XML·연결 정보 | `filing_source_documents`, `chunk_source_documents` | 각주의 원본과 재무 XML 보완 |

예전에 사용한 `financial.db`·`filings.db`나 Qdrant는 현재 웹 서비스의 기본 조회 경로가 아니다. MySQL의 수치·청크·벡터·원본 연결을 읽는다. 다른 테이블이 추가돼 있어도 조회 코드가 사용하지 않으면 서비스에 자동 반영되지 않는다.

### 산업과 기업을 정하는 과정

`catalog.sectors()`는 `data_versions`에서 `is_current=1`인 행을 읽는다. 정확히 하나이고 `validated`가 참이어야 한다. 활성 `krx_indices`를 순회하며 현재 구성기업 중 운영 가능한 기업이 있는 산업을 목록에 넣는다. 이름만 등록된 산업을 분석 가능한 산업으로 간주하지 않는다.

| 식별자 | 예시의 의미 | 사용 위치 |
| --- | --- | --- |
| 산업 ID·이름 | `반도체` | 화면 URL·앱 보고서 구분 |
| `membership_code` | `KRX_SEMI` 같은 구성 관계 코드 | 기업 관계 조회·산업 어휘 선택 |
| `index_code` | DB 공식 지수 코드 등 | 저장 지수 일치 검사 |
| `corp_code` | DART 기업 고유번호 | 공시·재무 DB 연결 |
| `stock_code` | 거래소 종목코드 | 기업 카드·주가 수집 |

지수 식별자는 DB `official_index_code` → 설정 `index_code` → DB 구성 관계 코드 순으로 선택한다. 시세 API에 요청할 정확한 지수명은 DB `index_name`에서 읽는다. 구성 관계 코드와 시세 코드가 같은 문자열이라고 가정하지 않는다.

`Repository.companies()`는 현재 구성기업 중 `is_operational`이고 종목코드가 있는 기업을 선택한다. 설정의 표시 순서를 우선하고, 나머지는 종목코드로 정렬한다. 특정 기업 요청은 이 목록 안에서 이름·종목코드·DART 번호가 정확히 일치해야 한다. 임의 문자열이 다른 산업의 기업으로 조회 범위를 넓히지 않는다.

산업 보고서의 기본 범위는 운영 기업 전체다. 산업 워드클라우드는 별도로 지수 비중 상위 최대 5개 기업을 선정한다. 기업이 늘어났을 때 두 범위를 같다고 설명하면 안 된다.

### 섹터별 화면 지표의 추가 조회

기존 공통 재무 이력과 별도로 화면의 4슬롯 지표는 `graph_metrics.py`에서 계산한다. 일반 기업은 Repository 분기 금액을 사용하고, 헬스케어는 원재무 연구개발 비용을 추가한다. 은행은 회사별 재무 기준을 읽은 뒤 승인된 `financial_metric_values`를 조회한다. 이 표에는 버전 열이 없으므로 현재 버전의 활성 공시와 출처 접수번호가 연결되는 행만 사용한다. 상세 산식과 제한은 [05](05_재무지표와원문출처.md), 실제 화면 계약은 [06](06_시세수집과화면.md)에 있다.

### 기간과 재무 기준을 고정하는 과정

`analysis_years()`는 현재 버전 `coverage`의 연도를 읽는다. `--years` 생략 시 전체 연도, 지정 시 사용 가능한 연도 안의 요청 기간이다. 현재 버전에는 없고 과거 버전에만 자료가 있으면 오류를 설명한다. 과거 버전의 자료를 조용히 섞지 않는다.

보고서 유형은 `Q1`·`H1`·`Q3`·`FY`이고 별칭 `HY`는 `H1`으로 바꾼다. 재무 기준은 연결 `CFS`와 별도 `OFS`, 기간 유형은 연간 `annual`, 누적 `cumulative`, 단일 분기 `quarterly`, 시점 잔액 `point_in_time`이다. 기업·연도가 같아도 기준이 다르면 서로 다른 값이다.

수치 조회는 기업·연도·보고서·재무 기준·기간 유형을, 검색은 구성기업·연도·보고서·검색 가능 여부·현재 버전을 맞춘다. LLM이 조건을 결정하는 것이 아니라 조회 코드가 결정한다.

### 보고서 생성의 처리 순서

`pipeline.build()`는 다음 순서로 동작한다.

1. Repository를 만들고 연도와 기업을 확정한다.
2. 기업별 연간 재무를 읽어 비율·변화율·FCF와 출처를 계산한다.
3. 해당 연도 공시 목록을 읽고, 기업 소개는 설정 프로필 또는 기본 설명을 사용한다.
4. 유효 수치로 연간 중앙값과 기업 상대 위치를 계산한다. 누락을 0으로 넣지 않는다.
5. 워드클라우드를 계산하거나 같은 입력의 캐시를 읽는다.
6. 연도별 FY 검색에서 자연어 문장을 찾아 기본 발췌와 각주를 만든다.
7. LLM 모드이면 산업·기업 인사이트와 키워드 설명을 생성한다. 최신 연도 키에 전체 선택 기간을 종합한 설명을 저장한다.
8. 종료 시 새 Repository의 지문과 시작 지문을 비교하고 일치하면 보고서를 저장한다.

전체 기간 분석은 모든 연도의 수치와 검색 근거를 범위에 넣는다는 뜻이다. 모든 연도에 동일한 Gemini 작업을 따로 실행하거나 모든 청크를 전송한다는 뜻은 아니다.

### 저장 보고서에서 화면으로 이어지는 데이터

| 주요 필드 | 내용과 사용 |

| `wordcloud`, `keyword_insights` | 최신 연도 신호·키워드 설명 |

### 설계 고려사항과 현재 한계

읽기 전용 연결 풀은 반복 연결 비용을 줄이고 원천 변경을 막기 위한 것이다. 기본 풀 5개·추가 연결 0개이며 연결 확인과 재사용 시간 제한을 둔다. SQL은 `SELECT`로 제한하고 읽기 전용 트랜잭션을 시작한 뒤 종료 시 되돌린다. 조건 값은 바인딩한다. 이 제한이 DB 사용자 권한·네트워크 통제를 대체하지는 않는다.

자료 지문은 데이터·인덱스 버전, 구성 관계, 검색 주제·프로필·순서, 검색 방식·모델 등을 포함한다. 구성기업이 바뀌었는데 같은 보고서를 계속 사용하는 일을 막기 위한 것이다. 모든 원천 행의 본문을 다시 해싱하는 방식은 아니므로 내용 변경 시 원천 버전도 갱신해야 한다.

각 SQL은 독립적인 읽기 트랜잭션이다. 분석 전체가 하나의 장기 DB 스냅샷에서 실행되는 것은 아니다. 검색 전후와 저장 전에 버전을 다시 검사하지만, 버전을 유지한 채 원천을 바꾸는 잘못된 적재까지 완전히 막지는 못한다.

산업별 보고서는 `current` 하나다. 특정 기업·기간만 분석하면 그 산업의 현재 보고서를 교체할 수 있다. `new`·`old` 생성 캐시는 분리되지만 두 보고서를 동시에 보여주는 비교 화면은 없다. 요청 기간·프롬프트 선택을 단순한 미리보기로 생각하지 않아야 한다.

새 산업은 공통 조회 흐름을 사용할 수 있다. 전문 용어·목차·회계 계정·기업 소개·시세 제공 여부는 실제 자료로 검토해야 한다. 이 구조가 금융업 전용 KPI까지 이미 구현했다는 뜻은 아니다.

## 화면 조회 최적화 (2026-10-10)

기업 화면은 `/api/project?sector=산업&code=종목코드`로 선택 기업의 상세 정보와 그래프만 요청한다. 같은 산업의 다른 기업은 이동 메뉴에 필요한 ID·이름만 반환한다. 산업 화면에는 여전히 모든 기업의 상세 정보가 반환된다. 첫 화면과 기업 이동 기능은 그대로다.

그래프 계산 결과는 화면 응답과 별도의 메모리 캐시에 보관한다. 재무 계산 방식과 누락값 처리 방식은 바뀌지 않는다. 키에는 DB 접속 설정의 해시, 섹터 메타데이터, 기업의 연도별 회계 기준과 분석 연도가 포함된다. 보고서 파일 상태가 바뀌면 다시 계산하며, 기본 유효시간은 `UI_CACHE_SECONDS=30`초다. 최대 128개·16MB로 제한한다. GCS 사용 시 이 캐시는 생략한다. 반환값은 복사하므로 화면 처리 중 변경이 다음 요청에 영향을 주지 않는다.

DB 조회·검증 자체를 없앤 것이 아니다. 기존 요청 단위 SQL 재사용과 짧은 메타데이터 캐시를 유지하며, DB 데이터와 스키마에는 쓰기 작업을 수행하지 않는다.
