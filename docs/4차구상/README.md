# DART BIG:IN 서비스 구현 설명서

이 설명서는 **공시·재무 자료를 DB에 넣은 뒤, 그 자료가 어떻게 분석 문장과 그래프로 바뀌는지** 처음부터 설명한다. DB 조회, AI 검색, API, 웹 화면의 연결 방법을 미리 알고 있다고 가정하지 않는다.

구현 기준은 2026-10-10의 로컬 코드와 배포 코드다. 먼저 쉬운 설명으로 흐름을 이해하고, 구체적인 파일·함수·설정이 필요할 때 각 문서 뒤쪽의 구현 상세를 읽으면 된다.

## 1. DB에 자료가 있으면 바로 분석 화면이 만들어지는가

DB에 데이터를 적재했다는 것은 서비스가 사용할 재료를 보관했다는 뜻이다. 예를 들어 어느 기업의 매출액, 사업보고서 문단, 그 문단을 검색하기 위한 벡터가 저장돼 있을 수 있다. 그러나 저장된 자료만으로 “이 기업이 어떤 사업을 확대하려 하는지”라는 설명 문장이 자동으로 만들어지지는 않는다.

서비스는 이 재료를 꺼내어 대상 기업과 기간을 맞추고, 필요한 문단을 찾고, 숫자를 계산하고, AI에 설명을 요청해야 한다. AI가 작성한 결과를 확인한 뒤에는 나중에 다시 읽을 수 있게 저장한다. 마지막으로 웹 화면이 그 결과를 받아 글·그래프·각주로 보여준다. 이렇게 여러 작업이 앞 단계의 결과를 다음 단계로 넘기는 전체 과정을 **파이프라인**이라고 부른다.

이 서비스의 파이프라인을 가장 먼저 이해할 때에는 아래 여섯 단계로 생각하면 된다.

```text
DB에 보관된 자료
  → 분석할 기업·기간에 맞는 자료를 꺼낸다
  → 사업 설명에 필요한 공시 문구를 찾고 숫자를 정리한다
  → Gemini가 전달받은 자료로 짧은 설명을 작성한다
  → 코드가 설명의 형식과 근거 연결을 확인한다
  → 확인한 보고서를 저장한다
  → 웹 화면이 보고서와 시세를 받아 표시한다
```

여기서 Gemini는 설명을 작성하는 AI다. DB 전체를 스스로 열어보는 주체는 아니다. 어떤 자료를 꺼낼지, 어떤 문단을 전달할지, 그래프 수치를 어떻게 계산할지는 서비스 코드가 맡는다.

## 2. 이 문서 전체에서 따라갈 한 가지 예시

반도체 산업에 속한 가상의 **A기업**을 예로 사용한다. 사용자는 산업 화면에서 A기업이 어떤 사업을 하고 있는지 살펴보고 싶어 한다. DB에는 A기업의 2023-2025년 공시와 재무 자료가 적재돼 있다고 가정한다.

공시에는 다음 문장이 있다고 하자.

> 서버용 제품 수요에 대응하여 생산능력 확대를 계획하고 있습니다.

이 문장은 사업의 방향을 설명하는 재료가 된다. 한편 재무 자료는 섹터별 성장·수익성·투자 또는 건전성·여력 그래프를 만드는 재료가 된다. 예시의 분기 수치는 필요할 때 해당 문서에서 별도로 제시한다.

모든 A기업 문구와 수치는 이해를 위한 가상 자료다. 실제 기업의 공시나 현재 서비스 결과를 옮겨 적은 것이 아니다. 다른 산업과 기업도 같은 처리 순서를 따르되 실제 조회 범위와 용어는 그 대상에 맞춰 달라진다.

## 3. 처음에는 보고서 생성과 화면 조회를 나누어 이해한다

관리자가 분석 명령을 실행하면 서비스는 DB에서 자료를 읽고 공시를 검색해 보고서를 만든다. 이때 Gemini 설명을 생성하고 근거를 확인한다. 이를 **보고서 생성 과정**이라고 생각하면 된다.

사용자가 나중에 웹페이지를 열면 서비스는 앞서 저장한 보고서를 읽어 화면에 전달한다. 같은 산업 설명을 방문할 때마다 Gemini에게 새로 작성시키지 않는다. 이를 **화면 조회 과정**이라고 생각하면 된다.

두 과정을 분리하면 페이지를 열 때마다 분석 완료를 기다리는 일을 줄일 수 있다. 생성된 결과를 다시 확인하거나 실패한 생성 작업과 화면 오류를 구분하기도 쉬워진다. 다만 화면에 필요한 현재 산업 목록과 분기 수치 등을 읽으므로 저장 보고서만 있으면 DB 없이 작동하는 구조는 아니다.

각주를 누르는 일은 또 하나의 짧은 조회 과정이다. 서비스는 저장된 근거 정보를 따라 원문을 찾아 보여준다. 같은 문장이 여러 곳에 나와 정확한 위치를 정하기 어렵다면 Gemini가 위치 후보를 평가하는 예외가 있다. 일반 페이지 조회와 이 예외 호출을 구별한다.

## 4. 자료를 꺼내는 단계에서 하는 일

서비스는 먼저 반도체 산업에 어떤 기업이 속하고, 그중 현재 분석 가능한 기업이 무엇인지 확인한다. 이어 어느 연도와 보고서의 자료를 사용할지 정한다. 이 작업은 기업·기간이 다른 자료가 한 분석에 섞이지 않도록 하는 출발점이다.

그다음 숫자 자료와 문장 자료를 나누어 읽는다. 매출액처럼 명확한 항목은 DB의 정리된 재무 값에서 찾는다. “생산능력 확대 계획”처럼 문장으로 설명된 내용은 공시 검색으로 찾는다. 두 자료의 조회 방식이 다른 이유는 숫자의 정확한 항목과 문장의 의미를 찾는 일이 서로 다르기 때문이다.

서비스가 DB에 “A기업의 2025년 자료를 달라”고 요청하는 데 사용하는 언어를 **SQL**이라고 한다. 이 프로젝트에서는 미리 작성한 Python 코드가 조회 조건을 만들고 SQL을 실행한다. DB 조회를 Gemini에게 맡기는 구조가 아니다. 이 단계는 [01 자료 조회](01_서비스구조와데이터조회.md)에서 자세히 설명한다.

## 5. 공시에서 필요한 문장을 찾는 단계

공시 문서는 길기 때문에 검색하기 좋게 나눈 조각을 사용한다. 이 조각을 **청크**라고 부른다. 청크에는 본문뿐 아니라 기업명·연도·보고서 종류·목차·고유번호가 붙어 있다. 그 덕분에 검색한 문구가 어느 문서에서 왔는지 추적할 수 있다.

문장의 뜻을 비교하기 위해 문장을 숫자 배열로 바꾼 것이 **벡터**다. 이 변환 작업을 **임베딩**이라고 한다. 현재 DB에는 공시 청크의 벡터가 이미 저장돼 있다. 검색할 때는 찾고 싶은 내용을 같은 모델인 BGE-M3로 벡터로 바꾸고 저장 벡터와 비교한다.

따라서 검색 결과는 “사업 설명에 사용할 만한 공시 조각”이다. 이 단계 자체가 사용자에게 보여줄 최종 AI 문장을 만드는 것은 아니다. 관련 자료를 찾아 AI에게 전달하는 연결 방식을 **RAG**라고 부른다. 여기서는 검색에 BGE-M3를, 설명 작성에 Gemini를 사용한다. [02 공시 검색](02_공시검색과벡터검증.md)에서 예시를 따라 이해할 수 있다.

워드클라우드의 단어 선정은 이 문구 검색과 별도로 진행한다. 코드는 대상 공시에서 단어를 찾아 언급 비율과 변화를 계산한다. 산업 화면에서는 여러 기업에 얼마나 고르게 나타나는지를, 기업 화면에서는 얼마나 다양한 문맥에 나타나는지를 추가로 본다. 단어를 고른 뒤 그 단어의 설명에 필요한 공시를 다시 검색하여 Gemini에 전달한다. 단어를 계산하는 코드와 설명을 쓰는 AI의 역할을 나눈 이유와 변경된 기준은 [04 워드클라우드](04_공시신호워드클라우드.md)에서 설명한다.

## 6. Gemini가 설명을 작성하고 코드가 확인하는 단계

서비스는 검색 결과 중 사용할 자연어 문장과 정리된 재무 자료를 모은다. 여기에 “제공한 근거 안에서만 설명하라”, “계획을 완료된 성과로 바꾸지 말라” 같은 지침을 붙인다. AI에게 주는 이 작업 지침을 **프롬프트**라고 한다.

Gemini는 자료와 지침을 받아 짧은 설명과 그 설명에 사용할 근거를 반환한다. 예를 들어 A기업의 생산능력 확대 계획을 설명하면서 어느 공시 문장을 참고했는지 함께 표시한다.

반환한 결과는 아직 그대로 화면에 보내지 않는다. 코드가 근거 번호가 실제 입력에 있는지, 선택 문장이 해당 청크 안에 있는지, 근거 평가가 수용 기준을 충족하는지 확인한다. 이 확인이 모든 사업 해석의 의미를 독립적으로 증명하는 것은 아니지만, 없는 자료를 각주로 붙이는 등 명확한 연결 오류를 막는다. [03 인사이트 생성](03_인사이트생성과프롬프트.md)은 AI와 코드의 역할을 나누어 설명한다.

## 7. 보고서를 저장한 뒤 화면으로 보내는 단계

검증을 마친 문장, 각주 정보, 재무 이력, 키워드 결과를 묶은 것이 이 서비스의 **보고서**다. 여기서 보고서는 사람이 읽는 PDF 한 장이 아니라 프로그램이 다시 읽을 수 있는 분석 결과 묶음이다.

저장과 전달에는 **JSON**이라는 형식을 사용한다. JSON은 “이 항목의 이름은 무엇이고 값은 무엇인가”를 정해 적는 데이터 형식이다. 예를 들어 `company`에 A기업 이름, `sentences`에 설명 문장을 넣는 식이다. Python과 브라우저가 같은 항목 이름을 기준으로 자료를 주고받기 위해 사용한다. [Python 공식 JSON 설명](https://docs.python.org/ko/3.12/library/json.html).

사용자의 브라우저는 자료를 요청하고, 서버 프로그램은 필요한 자료를 읽어 응답한다. 이 프로젝트의 `/api/project`는 현재 화면이 쓸 산업·기업 자료를 요청하는 창구다. 이처럼 프로그램이 다른 프로그램에 정해진 방식으로 기능이나 자료를 요청하는 접점을 **API**라고 한다. [MDN의 브라우저·서버 설명](https://developer.mozilla.org/ko/docs/Learn_web_development/Extensions/Server-side/First_steps/Client-Server_overview).

브라우저의 JavaScript는 응답 JSON을 받아 설명 카드를 채우고 그래프를 그린다. 각주를 누르면 별도의 원문 조회 API에 요청한다. [06 화면 출력](06_시세수집과화면.md)은 사용자의 클릭부터 실제 화면까지 이 연결을 설명한다.

## 9. 다시 정리해서 기억할 관계

DB는 자료를 보관한다. 조회 코드는 분석 범위를 정해 자료를 꺼낸다. BGE-M3와 검색 코드는 필요한 공시를 찾는다. Gemini는 전달 자료로 설명을 작성한다. 검증 코드는 설명과 근거의 연결을 확인한다. 웹 서버와 브라우저는 저장 결과를 사용자에게 보여준다.

이 관계를 이해하면 “검색이 실패했다”, “AI가 잘못된 근거 번호를 반환했다”, “화면에서 데이터가 보이지 않는다”가 서로 다른 단계의 문제라는 점도 이해할 수 있다. 뒤 문서에서는 각 단계가 무엇을 받아 무엇을 다음 단계에 전달하는지 이어서 설명한다.

[사용자 수정 프롬프트 정의서](프롬프트_정의서_수정.txt)는 현재 기본 `new` 프롬프트 원문이다. 실행 시 TXT를 읽는 방식이 아니라 코드 상수를 사용하며, 테스트가 양쪽의 일치를 확인한다. [DB와 FAISS 구조 설명 PDF](DB구조와_FAISS구조가_다른_이유.pdf)는 역할 분리의 배경 자료다. 실제 FAISS 실행 방식과 필수 DB 조건은 01·02를 따른다.

`docs/3차구상`과 `docs/history`에는 이전 자료가 보존돼 있다. 그 자료에 나오는 SQLite 두 개, Qdrant, 해시 벡터, 연간 변동률 화면, 근거 두 개 의무 선택, 과거 근거 가중치는 현재 기본 경로의 설명 기준으로 사용하지 않았다. 현재 저장소에 `data_new/`가 있다고 가정하지도 않는다.

### 설명서의 확인 범위

코드에서 확인한 기본값·공식·실행 경로를 기술했다. DB의 현재 기업 수·청크 수, API 계정 한도, 클라우드 서버 가동 상태는 문서 작성만으로 보증하지 않는다. 테스트와 실제 운영 연결의 확인 범위는 07에서 구분한다. 설계 이유는 요구사항과 구현을 함께 해석한 것이며, 미구현 개선 가능성은 현재 기능과 구분해 표시했다.

실제 XML을 청킹·임베딩하고 재무 값을 추출하여 원격 DB 없이 실행한 Linux/Windows 검증과 보완한 오류는 [08 오프라인 통합 검증](08_XML기반오프라인통합검증.md)에 정리했다. 모의 Gemini 응답 검증과 실제 모델의 생성 품질은 구분한다.
