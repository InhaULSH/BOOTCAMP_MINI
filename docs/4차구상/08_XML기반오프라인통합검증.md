# 실제 XML을 이용한 오프라인 통합 검증

검증일: 2026-10-10. 원격 MySQL과 실제 Gemini API에는 접속하지 않았다. 서비스의 데이터 구조, 파이프라인 단계, 프롬프트, 근거 ID 연결, 화면 기능은 유지했다. 현재 코드의 오류 처리와 자료형 검증을 확인하기 위한 테스트다.

## 1. 어떤 자료로 시험했는가

`data/xml_origin/manifest.json`에 등록된 삼성전자·SK하이닉스·한미반도체·주성엔지니어링·원익IPS의 실제 XML을 사용했다. 기업별 2023-2025년 사업보고서와 2025년 3분기보고서, 총 20건이다.

| 검증용 자료 | 생성 방법 | 개수 |
| --- | --- | --- |
| 공시 문서 | 원본 XML을 임시 폴더에 복사하고 기존 안전한 XML 파서로 읽음 | 20건 |
| 자연어 청크 | 사업의 내용에 있는 문단을 겹침 없이 최대 600자로 나누고, 보고서별 관련성이 높은 2개를 선택 | 40개 |
| 청크 벡터 | 기존 BGE-M3 인코더를 사용하여 실제 임베딩, 1,024차원과 정규화 검사 | 40개 |
| 질문 벡터 | 같은 모델로 HBM·설비투자 등 검증 질문을 실제 임베딩 | 6개 |
| 표준화 재무 행 | 기존 XML 재무 추출기로 계정·단위·기간·연결/별도를 확인하고 원 단위로 정리 | 188행 |

600자는 이 테스트의 CPU 작업량을 제한하기 위한 설정이며, 운영 청킹 기준을 바꾼 것이 아니다. 40개 청크는 대표 표본으로 전체 공시 코퍼스가 아니다. 모델은 `BAAI/bge-m3`, revision은 `5617a9f61b028005a4858fdac845db406aefb181`이다. 모델 다운로드 없이 기존 로컬 캐시를 사용했다.

재무 행에는 기업·연도·보고서·회계 기준·기간 유형과 원본 XML 접수번호 및 표의 위치를 남겼다. 직접 확인한 3개월 손익 값과 누적 현금흐름은 구별했다. 값이 없는 분기를 연간 값에서 임의로 계산하여 채우지 않았다.

예를 들어 삼성전자 2025년 연결 사업보고서 XML에서 추출한 검증용 매출액은 `333,605,938,000,000원`, 영업이익은 `43,601,051,000,000원`이었다. 이는 이번 XML에서 읽은 값이며 현재 원격 DB와의 일치 여부를 확인했다는 의미는 아니다.

## 2. DB에 접속하지 않고 어떻게 연결했는가

검증 전용 저장소 객체가 기업·공시·재무·청크를 메모리에서 공급하도록 DB 조회 경계만 대체했다. 운영 `Repository`의 재무 계정 선택·검색·근거 검색·결과 변환은 그대로 실행했다. DB 엔진 생성은 금지하고, 원본 XML 조회와 모델 확인에 필요한 SQL 결과만 가상의 읽기 결과로 공급했다. MySQL 테이블을 만들거나 수정하지 않았다.

Windows에서 실제 생성한 BGE-M3 벡터를 Linux 검증 컨테이너에도 공급했다. Linux에서는 실제 FAISS `IndexFlatIP`, Windows에서는 실제 NumPy 행렬 연산을 수행했다. FAISS와 NumPy의 상위 5개 결과 및 유사도가 일치하는지 확인했다. 정규화한 벡터의 내적을 코사인 유사도로 사용하는 방식은 [FAISS 공식 설명](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)을 따른다.

Linux 테스트 중에는 질문 벡터와 모델 확인용 청크 벡터를 사전 생성 결과로 공급했다. 따라서 Linux에서 BGE-M3를 직접 로딩하는 과정, 서버의 모델 캐시 경로·메모리·다운로드 권한은 검증 범위 밖이다.

운영 보고서 생성 코드로 산업·기업 인사이트와 키워드 설명 총 18개 작업을 실행했다. 최대 동시 작업 수는 기존 기본값인 4개를 사용했다. 실제 산업·기업·키워드 프롬프트, 근거 후보와 재무 입력, 결과 검증, 각주 생성, 캐시 저장, 보고서 게시 과정을 거쳤다. Gemini HTTP 응답과 토큰 계산 결과만 모의했다. 각 재시도에도 사용량 예약 함수가 호출되는지 확인했다.

워드클라우드 점수 계산은 이 통합 테스트에서 직접 실행하지 않고, 실제 청크의 키워드 포함 여부를 센 검증용 결과를 공급했다. 기존 워드클라우드 알고리즘은 별도 회귀 테스트로 확인했다. 모의 응답은 실제 공시 문장을 선택한 정상 값 또는 그 값을 변형한 오류 값이며, Gemini가 실제로 생성한 답변은 아니다.

FastAPI 화면 API는 [공식 TestClient 방식](https://fastapi.tiangolo.com/tutorial/testing/)으로 실행했다. 실제 웹 소켓이나 인터넷 서버 연결 없이 라우트·예외 처리·JSON 응답을 확인했다. Linux 실행에는 `--network none`을 적용했다.

## 4. 발견하여 보완한 문제

**배포 인사이트 캐시 저장 경로와 함수 누락.** `deploy/cloudapp/pipeline.py`가 `SERVICE`와 `atomic()`을 사용하지만 정의하거나 가져오지 않아 생성 중 `NameError`가 발생했다. 로컬과 동일하게 경로를 가져오고 임시 파일을 이용한 원자적 저장 함수를 복원했다. 보고서 구조와 저장 정책은 그대로다.

**분기 재무 입력의 보고서 종류 판별 오류.** 인사이트 생성 코드가 분기 재무 근거의 `report_type`을 `values` 안에 넣는데 금액 검증은 최상위에서만 읽고 없으면 사업보고서로 처리했다. 이 때문에 정상적인 3분기 금액도 모호한 범위로 거부됐다. 기존 최상위 값이 있으면 우선 사용하고 없으면 기존 `values.report_type`을 읽도록 로컬·배포를 수정했다. 입력 구조나 ID를 변경하지 않았다.

**중복 원문 위치 평가의 자료형 검사 누락.** 일부 평가가 `null`이면 `AttributeError`가 발생하여 한 차례 교정하는 경로를 벗어났다. 문자열 `suitable`도 boolean으로 확인하지 않아 통과할 수 있었다. 객체·배열·ID·등급 객체·boolean 여부를 확인하고 잘못된 값은 `ValueError`로 정상적인 교정·실패 처리에 넘긴다. 점수 공식과 위치 선정 프롬프트는 유지했다.

이미 폐기된 `search_server` 모듈을 가져오던 배포 테스트도 제거했다. 현재 FAISS/NumPy 검색은 `dart_remote/mysql_vectors.py` 경로에서 검증한다. 새로운 검색 서버를 추가하거나 기존 서비스 기능을 제거한 것은 아니다.

같은 오류의 재발을 막기 위해 분기 입력과 원문 위치의 자료형 검사에 회귀 테스트를 추가했다. 로컬·배포의 생성·근거·재무 이력·캐시 저장 함수도 코드 구조 수준에서 비교한다. 두 환경의 LLM 모듈 import 위치 차이는 의도적인 차이로 구분한다.

## 5. 최종 결과와 한계

| 검증 | 환경 | 결과 |
| --- | --- | --- |
| XML 기반 통합 검증 | Linux Docker, Python 3.12.15, FAISS 1.15.1 | 72개 통과 |
| 동일 통합 검증 | Windows, Python 3.12.13, NumPy | 70개 통과 |
| 프로젝트 회귀 테스트 | Windows | 183개 통과 |
| 현재 배포 서비스 회귀 테스트 | Windows에서 배포 패키지 실행 | 7개 통과 |

잘못된 응답을 의도대로 거부하거나 교정하는 경우도 통과에 포함한다. 테스트 중 경고가 출력된 것은 이러한 실패 시나리오를 의도적으로 공급했기 때문이다. Linux와 Windows의 통합 검증 개수 차이는 Linux에서 추가로 FAISS 검색과 FAISS/NumPy 결과 비교를 실행하기 때문이다.

현재 검증의 중요한 한계도 재현했다. **근거 ID와 점수·자료형이 적합하더라도, LLM이 근거와 관계없는 요약을 쓰면서 스스로 높은 점수를 주면 코드 검증을 통과할 수 있다.** 검증 통과는 의미의 정확성까지 독립적으로 입증했다는 뜻이 아니다. 이번에는 파이프라인과 기능을 바꾸지 말라는 조건에 따라 추가 LLM 검증 단계를 도입하지 않았다. 실제 모델 응답의 내용 평가가 별도로 필요하다.

실제 Gemini의 생성 품질·RPM/TPM·지연, 원격 MySQL의 현재 데이터·SQL 실행·네트워크, 네이버 클라우드 서버 설정, 전체 공시 데이터의 부하, 브라우저의 시각적 렌더링, 다른 산업의 XML 표본은 이번 검증 범위에 포함하지 않는다. 실제 네이버 서버나 Ubuntu 24.04에 접속한 결과가 아니라 별도 Linux 컨테이너에서 배포 코드를 실행한 결과다.

## 6. 재현 코드와 임시 자료

재현 코드는 `tests/offline_xml_fixture.py`, `tests/offline_xml_server.py`, `tests/offline_server.Dockerfile`이다. 첫 파일은 실제 XML로 검증용 자료를 만들고, 두 번째 파일은 그 자료로 서버 경로를 시험한다. 모델이 로컬에 캐시되어 있어야 하며 없으면 다운로드하지 않고 실패한다.

```powershell
# 프로젝트 루트에서 실행. 이 경로는 테스트 전용이다.
.\.venv\Scripts\python.exe -X utf8 tests/offline_xml_fixture.py --output tmp/offline-xml
.\.venv\Scripts\python.exe -X utf8 tests/offline_xml_server.py --fixture tmp/offline-xml --report tmp/offline-results/windows.json
```

Linux에서 재현하려면 테스트 이미지에 소스 코드와 이 검증용 자료를 각각 읽기 전용으로 연결하고 `--network none`으로 실행한다. `deploy/cloudapp`, `deploy/dart_remote`, `deploy/config`, `deploy/web`과 테스트 코드만 연결한다. `.env`, 가상환경, 실제 서비스 저장 파일은 전달하지 않는다.

이번 작업의 테스트용 XML 복사본·벡터·재무 행·생성 캐시·진단 로그·코드 복사본은 종료 후 삭제한다. 원본 `data/xml_origin`과 운영 모델 캐시·서비스 자료는 보존한다. 위 재현 코드와 이 결과 문서는 유지한다.
